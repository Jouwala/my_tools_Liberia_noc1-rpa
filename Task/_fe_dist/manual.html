设计篇

01 项目总览

一句话定位

my_app 是一个单机的网络运维数据平台：把 eFlow、各制式网管（UME/CNN/iPRAN/MW/EMS）、FineBI、FTP、邮箱等上游系统的数据按时抓回来，落进数据库，再产出看板、Excel 报表和定时邮件/微信通知。

它服务的是"每天要看板、要发报表、报表不能漏"的 NOC 运维场景，不是一个通用 BI 工具，也不是给外部用户注册的 SaaS。

能力边界

它做什么

  • 41 个定时任务驱动数据采集与报表投递（backend/task_registry.py:72-403）。
  • 23 个功能页在一个 SPA 里，中英文可切换（frontend/src/App.tsx:68-70,182-206）。
  • 数据可下钻：看板上点指标弹出明细（TT&WO / 告警 / 丢包 / NUR / MS SLA / GIS 均为该模式）。
  • 提供通用表能力：任意表浏览、字段画像、Excel/CSV 导入导出、视图模板（TableBrowser）。
  • 自动补漏：失败任务自动重试、漏跑任务自动补投（backend/services/auto_retry.py:75-82）。
  • 进程自愈：后端与 worker 各由看门狗托管，心跳超时即强杀重拉。

它不做什么（避免误解）

  • 没有多用户体系：没有注册、没有角色权限、没有审计日志。详见 05-security-and-credentials.md。
  • 不对外提供 HTTPS：后端直接明文 HTTP 监听，TLS 需由前置 nginx 终结。
  • 不做数据编辑：数据是"抓进来只读"的，页面上没有业务写回上游的能力（仅凭据、收件人、排程等配置可写）。
  • 不是高可用服务：单实例锁（db/instance.lock）保证同机只跑一份，没有集群与故障转移。

  1. 建库/连接重试 — 数据库不可用时不直接崩，重试后再判定。
  2. 抢单实例锁 db/instance.lock（main.py:145-171）— 已有实例则拒绝启动，防止两个后端写同一库。

  • SQLite 侧 PRAGMA：busy_timeout=30000、synchronous=NORMAL（:76-89）——回退到 SQLite 时才不会 database is locked。

backend/dialect_helpers.py（:73-168）

04 任务与调度系统

my_app 的"心脏"。41 个定时任务负责全部数据采集与报表投递，页面上看到的数据新鲜度、失败告警、补跑行为都在这里定义。

另有两个模块级说明文件更贴近代码：backend/WORKER.md（worker 进程架构、容错、启停、环境变量）与 backend/task_registry.md（注册表字段与对外接口）。本章是归口叙述，改动这两处代码时请同步更新三份文档。

一条任务的一生

APScheduler 到点 (backend 进程内)
   └─► enqueue_task()  写 task_queue 一行（task_runner.py:153）
         └─► worker 进程 UPDATE ... RETURNING 原子认领（worker.py:196-217）
               └─► run_task() 执行真正的 service 函数（task_runner.py:379）
                     └─► _finish() 回写终态 + task_execution_log（worker.py:219）

关键点：

  • 注册是代码注册表，不是配置文件。41 条声明集中在 backend/task_registry.py:72-403 的 TASK_SPECS，启动时 register_all_tasks()（:405-429）逐条登记，采用懒加载包装（:58-64）——每条二选一给 func（需要特殊包装）或 loader（("module.path","func_name") 元组）。
  • cron 可以被库里覆盖：默认值写在 default_cron，实际排程读 task_schedule_config 表（task_runner.py:241-296），所以在"任务管理"页改排程会立即生效且重启不丢。
  • 另有一套任务配置文件框架 services/task_configs_registry.py:1-30，优先级 环境变量 > 配置文件 > 默认值，用于任务的业务参数（不是排程）。
  • 状态回传是纯 HTTP 轮询，没有 WebSocket：/api/tasks、/api/tasks/{id}/status|history|stats。
  • 降级模式：未设 MY_APP_TASK_QUEUE=1 时，任务退回调度器进程内线程执行（task_runner.py:527-553），不经过队列、也不由 worker 认领。生产启停脚本会注入该开关（backend_watchdog.py:137）。

分组动机写在 worker_watchdog.py:41-44：按"上游会话是否互斥/是否写同一库"分组，同组串行等价于旧的单 worker 行为，组间并行。

05 访问控制与凭据

这一章既说明"现在怎么防护"，也如实记录已验证存在的风险。上线或移交前请先读完本章。

结论先说

my_app 没有用户账号体系。 没有注册、没有登录态、没有角色权限、没有操作审计。任何能访问到 :7038 或前端入口的人，都等于拥有系统的完整操作能力（包括触发任务、改凭据、导出全表数据）。

唯一的接口防护：require_protected

backend/security.py:17-26：

  • 请求来自回环地址 → 直接放行；
  • 请求来自远程 → 要求请求头 X-API-Token 等于环境变量 MY_APP_API_TOKEN；
  • MY_APP_API_TOKEN 未设置时，远程请求一律 403（这是"默认拒绝"，比配了弱 token 更安全）。

挂载范围很窄，只有 4 个 router 共 18 处装饰器：routers/tasks.py、routers/upload.py、routers/task_configs.py、routers/cm_flows.py。

🔴 已验证风险 1：Token 校验在反向代理后失效。 生产链路是 nginx → vite preview → /api 反代到 7038，前端 baseURL: '/api'（frontend/src/api.ts:4）。经同源反代后，后端看到的 request.client.host 恒为 127.0.0.1，于是所有请求都命中"回环放行"分支。也就是说：只要访问走 nginx，Token 形同不存在。 现实缓解手段只剩网络层：:7038/:7090 不对外网开放、内网访问范围可控。若要把系统放到更大范围，必须先改造防护（校验 X-Forwarded-For 真实来源或全站接入认证），不要指望这个 Token。

🔴 已验证风险 2：其余绝大多数接口无防护。 凭据读写、表数据导出、GIS/看板查询、设置保存等都不在 require_protected 覆盖范围内。

  3. 越序只对契约相邻对判定——曾经对时间轴上所有相邻跳判倒挂，结果 「告警清除 → FO Process」被判越序，实测 120 单里 86 单如此。但告警自愈本就 早于文书流程，这是常态不是异常，误判会淹没真问题。现只保留 _ORDER_PAIRS 里的 4 对。

  4. 根因错位不能全量入偏离——NOC 的 root_cause（POWER/RAN/Fiber/Planned work…） 与系统 alarm_reason_type（实测本库 99% 是 TRM）是两套不同粒度的分类法， 直接比对会让几乎 100% 的单子"错位"、报告失去区分度。现偏离只收 语义确凿冲突的 POWER<-TRM（复盘报告 §4 已用 2,529 张单验证过的系统性误填）； 其余组合仍在正文「根因对比」表里并列展示，只是不判偏离。

    注：概览/下钻页的「错位率」口径不变（_mismatch_of 仍返回 其它 类）， 那里是人工逐条复核的列表场景，宽口径更合适。两者用途不同，勿强行统一。

  5. WO 的现场步骤是 JSON 数组，不是 Operation Time: 文本——start_trip_detail / arrive_site_detail / leave_site_detail 存的是 [{"opname":"Start Trip","operator":"FE_FE_133","operationtime":1790149109856,...}]， 只有 accept_detail / process_detail / confirm_detail 才是文本格式。 原实现统一套文本解析器，实测 9,950 条 start_trip_detail 全部解析为空， 「现场处置」这一跳永远显示缺失。修复：新增 _parse_wo_json_step()， 两条路径都走；operationtime 是 epoch 毫秒，用 _norm_wo_time() 转换； 展示名优先取 candidateoperator[0].name（否则报告上只有 FE_FE_133 这种工号，无法点名）。

  6. 时间轴必须按真实发生顺序排，不能按契约顺序硬排——WO 派单、现场到场、告警清除 三者在真实世界里会交错。实测 TT202609230005：WO 在 00:27 派、现场 07:38 到场、 告警 07:27 清除；若按契约顺序把「现场处置」排在「告警清除」之前再算相邻跳间隔， 就会出现 -7.00 小时的负间隔，读者会以为数据错了。修复：构建完成后按时间升序 重排（无时间戳的缺失跳沉底），并重算 gap_from_prev_s（沿用排序前的间隔同样会错）。

  7. 时间归因必须覆盖全窗口，缺口要显式暴露——末段终点若写死 confirm，遇到 「未走完流程（无 Confirm）」的单子，分段之和会远小于总历时，出现说不清去向的黑洞 （实测 TT202609220068 差 4.6h）。修复：末段终点缺失时回落到全流程终点，并返回 unaccounted_s / unaccounted_note；跑 200 单回归，仅 4 单有缺口（最大一单 TT202609220123 缺 fo_accept，缺口 8.84h，note 已如实说明）。 同时 time_spent.total_seconds 与 timeline_meta.total_seconds 统一为同一口径， 避免页面「总历时」与「合计」两个数字打架。

  8. 「存在 WO」不等于「现场有人」——不要把 WO 创建时间当现场处置时间—— 旧实现把 eflow_wo.created_time 当作现场处置的时间戳、actor 写死 human、 ok = has_wo，于是报告里出现「现场处置 ｜ 人工 ｜ 2026-09-22 16:53:51」这种 无依据的结论。实测该单（WO202609220068）的 WO 由 fe_robot 自动创建， 真正的现场动作在次日 08:44（Stanley Biney(FE_FE_101) 出发/到场）， 比 WO 创建晚了 16 小时——原写法连时间都是错的。 根因：eflow_tt 没有独立到场字段，eflow_wo 的出发/到场/离场明细又常为空。 修复：以 start_trip_detail / arrive_site_detail / leave_site_detail 明细为唯一证据； 取不到时 actor=unknown、不给时间、status=unproven，并在说明里点明 「WO 由 fe_robot（系统自动）创建，不能据此推定现场有人」。 200 单回归实测：86 张有 WO 的单里只有 18 张有真实现场明细，另 68 张从 "现场处置 人工"改判为"未证实"——这是本次修正影响面最大的一处。

    顺带修正：告警清除的说明不能笼统写「有现场动作明细」。上例告警在 16:55 就清了， 现场动作却在次日 08:44，两者相隔 16 小时。现按先后关系分别输出 「告警先清除，现场动作在其后」/「现场动作早于告警清除」。

  9. 机器人操作人不能被记成「人工」——fo_accept_detail 的 Operator: 可能是 FE Robot(fe_robot)（机器人自动接单），但旧实现把 fo_accept / fo_process 的 actor 写死 human，报告里就出现「FO Accept 接单 ｜ 人工 ｜ FE Robot(fe_robot)」 这种自相矛盾的结论。修复：新增 _is_robot_operator() / _actor_of()， 命中 fe_robot / auto_robot / assign_rule / system / robot / auto_ 即判为 system， 并在说明里补「（机器人自动接单）」。 200 单回归实测：fo_accept 165/200 是机器人，fo_process 163/200 是机器人。 注意 _is_robot_operator 是子串匹配（要能认出 FE Robot(fe_robot) 这种展示名）， 所以不要拿它去判站点名之类的业务文本。

  10. 写死的分段端点会把最大的一块时间藏起来——旧实现固定 4 段 （detect/assign/handle/close，端点全是文档流程节点），遇到"机器人秒填文书、 人在第二天才到现场"的单子就全错。实测 TT202609220139： WO 派单 2026-09-22 16:53:51、现场到场 2026-09-23 08:44:25， 中间等现场响应 15.81 小时；但 fo_process 被机器人秒填在同一秒， 这段等待全挤进"提交 → 确认关单"，而窗口终点又取 last_modified_time （停在 16:56，早于现场动作）→ 整段落在窗口之外， 页面显示"总历时 18 分钟"，与时间轴上横跨 16 小时的记录直接矛盾。 修复：① 窗口终点取所有已知活动的最晚时间；② 分段改由真实事件链生成。 修正后该单总历时 16.10h，瓶颈如实显示为「现场响应等待 15.81h（98.2%）」。

  11. create_detail 的字段之间用句点分隔，模糊匹配会把句点当值—— Assign To:. Assignee Group:. 用"值到下一个大写词"的正则去取， 得到的是 '.' 而不是空，于是报告写成"建单即指派到人：."。 修复：用字段名联合前瞻 (A|B|C):(.*?)(?=(?:A|B|C):|$) 逐字段取值， 再 strip(".") 并把空串归一为 None。

  • 访问者就在服务器本机（/api/portals 的 client_is_local=true，或页面主机名是回环）→ 点「登录」自动改走服务器端直接鉴权，弹出来的窗口就在他自己桌面上（不必手动切「服务器」）；

实现注意（判定「已登录」）：

  1. 不能只看 URL——RAIS 的 hash 路由切到 #/homepage 是瞬时的，必须等首屏真正渲染出内容 （PORTALS['rais']['ready_js']）。
  2. eFlow 必须等启动页真正落到门户源再写 localStorage.csrftoken：Chrome 一启动 DevToolsActivePort 就有，此时页面还在 about:blank（origin=null）， localStorage.setItem 会抛 SecurityError → 整页渲染 Your session is error. Please login again.（窗口打开了但没登录）。
  3. 成功判定要「正证据 + 连续两次」（PORTAL_READY_JS + _SESSION_ERR_RE）：正文 ≥120 字、 无会话错误文案、无可见 input[type=password]；只判 URL 或「innerText 非空就 break」 会把中间态/会话错误页误报成「已登录」。
  4. 不能在 Chrome 启动页还 loading 时就 Page.navigate 改 hash，否则会得到一个 readyState=complete 但 JS 从未执行的空白页，且不会自愈。

25. UME iMonitor 大屏（?page=imonitor）— 原版门户页面嵌入

把 UME 门户（172.17.208.1:28808）的原版监控大屏 guard-imonitor-iui 的 #/screen/screen-view?screen_id=1 原样嵌进 myapp，并自动完成 em-portal 登录。 形态与 vmaxCxoDashboard 同属「原版页面嵌入」，但这个页面必须登录，且不能直连上游。

  • 页面：frontend/src/pages/ImonitorScreen.tsx（不是 LegacyToolFrame——需要工具条与登录编排）
  • 反代：nginx/portal_ume_in_8088.conf（线上生效的那份在 nginx 安装目录的 conf/portal_ports.conf）
  • 门户注册：portal_login_service.py 的 PORTALS['ume_in'] + PROXY_PREFIXES['ume_in']
  • 凭据：credential_store key=ume_in（与客户业务 KPI 看板同一套 em-portal 账号）

为什么必须走反代，不能直接 iframe 上游

  1. 同源才能带会话：浏览器要带门户 Cookie 才能打开大屏，而 Cookie 只能由门户自己种； myapp(80) 与门户(172.17.208.1:28808) 不同源 → 既种不了也读不了。
  2. 上游禁止被嵌：上游返回 Content-Security-Policy: frame-ancestors 'self'， 直接 iframe 会被浏览器拦死（Chromium 报 Framing ... violates ... frame-ancestors 'self'）， 页面只剩一个 chrome-error。反代必须 proxy_hide_header Content-Security-Policy（连 XFO/HSTS 一起摘）。
  3. 上游有 frame-bust（三处，实测确诊）：
    • 登录页内联 if (self === top) {} else { top.location = self.location; }
    • login.min.js：top!=self&&(top.location=self.location)
    • security.min.js：登录成功后 redirectToUrl(top.location, home) 前两者可被 nginx sub_filter 改掉；三者都靠 iframe sandbox（不含 allow-top-navigation） 从浏览器层封死——没有它，用户刚点过 myapp（激活窗口约 5 秒内）时登录页就可能把整个 myapp 标签页导航走、冲掉外壳。两处都要保留，别只留一处。

登录时序（首次访问自动发生）

iframe 载入大屏 → SPA 调 /api/guard-imonitor-service/v1/largescreen/screen?_id=1
→ 401 → SPA 自己跳到 /api/oauth2/v1/authorize?redirect_uri=/iui/guard-imonitor-iui/
→ 注入脚本(/api/portals/inject.js?system=ume_in)填表并提交，同时 postMessage 通知宿主
→ login_rsa 200 → 门户把浏览器送到 redirect_uri 的根路径（hash 必丢）
→ 宿主收到 postMessage 后等 3s 把 iframe 重指回 #/screen/screen-view?screen_id=1

实测：3.0s 出 401 → 3.0s 提交登录 → 6.1s 大屏接口 200 并出图。

⚠️ 最后一步不能省：门户登录成功只回落到 redirect_uri 根路径，#/screen/screen-view?screen_id=1 这段 hash 路由在跳转中必然丢失。这也是 build_inject_js 里那条 myapp-portal-autologin postMessage 的唯一用途。自愈循环上限 4 次（MAX_AUTO_RELOGIN），工具条手动「刷新/重新登录」会重新武装。

其它注意

  • 自动刷新：本页登记在 AR_SOFT_REFRESH_PAGES，顶栏到点时外壳广播 myapp-refresh、 由页面在 iframe 内原地重载（跨端口 iframe 重挂载会整页闪白）。
  • 端口号有三处必须一致：页面 PORTAL_PORT / PROXY_PREFIXES['ume_in'] / nginx conf。 tests/test_imonitor_screen.py 会离线核对这三处。
  • Cookie 按主机共享、不分端口，所以门户 Cookie 名带端口后缀（Z-AUTH-CODE-28808 等）。 同主机的 ccn_ume（10.121.1.2:28808，反代 8082）与 ume_in（172.17.208.1:28808，反代 8088） Cookie 名相同，两个门户不要在同一浏览器里同时登录。
  • 离线测试：python tests/test_imonitor_screen.py（不连门户、不起浏览器）。

36 张卡片由 backend/services/task_configs_registry.py 注册。规则：

  • 页面显示的默认值不是抄写的：每张卡的 defaults_factory 从服务模块常量现读（例如 _main_kpi_defaults、_sp_defaults），所以页面上的默认值就是代码在用的值，不会与代码漂移。
  • 优先级：环境变量 > 配置文件（页面编辑） > 代码默认。覆盖都发生在模块导入期，因此由 HOST/PORT 拼出来的派生常量（PM_REFERER、HISTORY_REFERER、LOGIN_URL/DASHBOARD_URL、ALARM_REFERER）必须写在覆盖块之后，否则页面上改主机没用。
  • 保存链路：PUT /api/task-configs/{id}（backend/routers/task_configs.py:72-80）→ schema 校验（task_config_files.py:204-249）→ 合并（:272）→ 原子写 → _restart_config_workers()（routers/task_configs.py:33-57）杀掉 backend/worker_{u,n,v,m,c}.pid，看门狗秒级重拉 → 下次任务运行即用新值。不碰 worker_watchdog.pid（误杀它=改完配置任务再也不跑）。
  • table 类型是整表替换（task_config_files.py:272-288）：保存时页面必须把所有行带回；在页面上删掉一行就是真删。行里非 schema 的键（keep_columns、payload 等内部字段）会原样保留。
  • 逗号整数字段（itemsposition/itemsposition1/itempositionbusiness）在 schema 里标了 int_list:true，填字母会在保存时被挡下（task_config_files.py:223-228）。原因：服务在导入期用 int() 解析它们，一个字母会让整个模块 import 失败——现象是任务直接不起，而不是"这项没生效"。
  • 回到纯代码默认：删掉对应的 *_config.json 即可，卡片下次打开时由 factory 从代码取真值。反过来，文件一旦存在就以文件为准：代码里改了默认值而磁盘上还有同名旧文件，页面和服务仍用文件值——这是"改了不生效"最常见的原因。
  • 改注册表/校验代码本身（不是改配置值）时，要重启后端 API 进程：它在启动时 import 一次注册表，uvicorn 没有开 --reload。只改配置值不需要重启 API（保存即重启 worker）。
  • 凭据不进配置文件：密码/Token 由「凭据管理」页签（credentials 表）管理，卡片上只有主机、端口、路径、模板、天这类非敏感项。
  • 守卫：python tests/test_task_config_live_effect.py（必须用后端实际运行的那个 python，本机是系统 Python 3.12）。它对每张卡走真实写入口写哨兵、再在全新解释器里读服务真正会用的值，覆盖"死字段 / 派生量算早了 / 坏值没挡住 / 字段被静默丢弃"四类问题，跑完自动还原配置文件。改卡片时请跟着跑一次。

1. 平台简介

面向网络运维的自动化数据平台：定时从 eFlow、各制式网管（RAN/iPRAN/CNN/MW UME、CN EMS）、FineBI、FTP、邮箱等上游系统采集与同步数据，统一入库后以看板、表格与报告的形式呈现。

典型链路：定时任务采集 → 数据入库（PostgreSQL 主库 + 各任务独立 SQLite）→ 看板展示 / Excel 报表与邮件、WhatsApp 分发 → 告警与工单闭环分析。

服务场景是「每天要看板、要发报表、报表不能漏」的 NOC 运维：41+ 个定时任务、20+ 个功能页、失败自动重试与漏跑补投、进程级看门狗自愈。

它做什么

  • 41+ 个定时任务驱动数据采集与报表投递（backend/task_registry.py 统一注册）
  • 所有功能页在一个 SPA 内，中英文可切换，看板指标可点击下钻
  • 通用表能力：任意表浏览、字段画像、Excel/CSV 导入导出、视图模板
  • 自动补漏：失败任务自动重试、漏跑任务自动补投；进程自愈：看门狗托管 + 心跳强杀重拉

它不做什么（能力边界）

  • 没有多用户体系：没有注册/角色/审计，任何能访问入口的人都拥有完整操作能力
  • 不对外提供 HTTPS：TLS 需由前置 nginx 终结；上游证书校验默认关闭
  • 不做数据编辑：数据「抓进来只读」，页面无业务写回上游的能力（仅凭据/收件人/排程等配置可写）
  • 不是高可用服务：单实例锁（db/instance.lock）保证同机只跑一份，无集群与故障转移

3. 任务管理详解

3.1 一条任务的一生

① 调度到点 APScheduler 在后端进程内按 cron 到点触发（backend/task_runner.py）。默认 cron 写在 task_registry.py 的 TASK_SPECS，实际排程读 task_schedule_config 表——所以在页面改排程立即生效且重启不丢。

② 入队 enqueue_task() 向主库 task_queue 写一行待执行记录。

③ worker 认领 对应分组的 worker 进程用 UPDATE…RETURNING 原子认领该行（backend/worker.py）。MY_APP_TASK_QUEUE=1 未设置时退化为调度器进程内线程执行。

④ 执行 run_task() 调用真正的 service 函数（task_registry.py 里每条任务声明 func 或 loader=("模块路径","函数名") 懒加载）。业务函数抛异常即记为失败——不要在业务代码里吞异常。

⑤ 回写终态 _finish() 回写任务终态并写 task_execution_log 执行历史（队列与执行日志保留 3 天）。失败时经微信 + 邮件双通道通知。

3.2 Worker 分组：组内串行、组间并行

组 约束原因

v VMAX 门户（本机 8790 单会话代理）：三个任务共用同一会话必须串行；2026-09-18 从 n 组拆出，不再被 1.5~2h 长任务堵住

3.4 可靠性机制（超时 / 重试 / 自愈）

机制 说明
僵尸 running 回收 无 per-task 超时（设计缺口）。worker 每 300s 扫描：running 超 30 分钟（STALE_RUNNING_SECONDS）且 PID 已死亡的记录按失败回收。
失败自动重试 auto_retry_failed 每 10 分钟扫描：失败任务先判断数据缺口是否已被后续成功执行补上，未补上且未超 MAX_ATTEMPTS=2 才重投；超过 24h 硬上限直接放弃。
漏跑补投 时效窗口内应触发却完全没有执行记录的任务自动补投一次（MISS_GRACE_MIN=15 宽限；邮件类默认排除，由 EWS 补发机制负责）。
陈旧 pending 过期 pending 超 6 小时无人认领（典型原因：漏登记 worker 分组）会被置 failed 并补写执行日志，释放被它占住的单飞名额，让下一次调度能正常入队（否则一条陈旧记录会挡住该任务之后的每一次调度）。
失败通知 任务失败经微信 + 邮件双通道告警（services/weixin_notifier.py 支持 openclaw/wecom/serverchan/pushplus）。
漏跑/停摆主动告警 db_freshness_check 每小时算四类健康异常（未归组 / 超出周期无执行记录 / 队列滞留 / 上次成功后逾期无新成功），由 services/task_health_alert.py 按「新异常通知一次、恢复通知一次、持续超 24h 再提一次」推微信+邮件，不必等看板没数据了才人工发现（2026-09-18 上线）。
进程自愈 backend_watchdog / worker_watchdog 托管进程：端口探活、崩溃退避重拉（连崩 10 次放弃并告警）；心跳 log/heartbeat_*.json 超 3 分钟未更新判定 hung 强杀重拉。
保留期 task_queue 与 task_execution_log 保留 3 天（task_runner.py / worker.py 自动清理），无需手工。

5.2 日常巡检（5 分钟）

  • 任务管理页：有没有 failed、有没有长期 pending（失败聚合视图比翻列表快）
  • 页头同步标签：GIS / TT&WO / Dashboard 的「最近同步」是否在预期窗口内
  • 数据总览页：表数量与行数是否明显异常
  • 命令行：五个关键进程是否都在、心跳 heartbeat_*.json 是否新鲜（超 3 分钟会被强杀重拉）
  • 数据库新鲜度由 db_freshness_check 每小时 :15 自动巡检，滞后会给出调用链与排查方向；任务本身漏跑/停摆（未归组、无执行记录、队列滞留、成功逾期）也会在同一巡检里主动微信+邮件告警，不需要人工等看板空了才发现

5.3 日志速查

日志文件（log/） 内容
log/worker_runtime*.log 任务执行主日志——排障首选，按 task_id 搜堆栈（每组 worker 一个文件：_u/_n/_v/_m/_c）
log/backend_runtime.log 后端业务日志（API、调度、代理）
log/backend_watchdog.log / worker_watchdog.log 进程拉起与崩溃退避记录（连崩 10 次放弃并告警）
log/start_hidden_result.txt 上一次启动的逐条结果——启动失败先看这个
log/heartbeat_*.json 后端与 worker 心跳（15s 一次，超 3 分钟判 hung）
log/*_console.log(.err) 各子进程 stdout/stderr

⚠️ 全仓库没有日志轮转，log/ 只会一直涨，需人工定期清理；部分日志报错原文含账号，外发前先扫一遍。

5.4 备份（三处都要备，缺一不完整）

  • 远程 PostgreSQL（主库）: pg_dump 备份业务数据与 task_queue/task_execution_log/task_schedule_config；pg_to_sqlite_sync 每小时 :45 已提供一份镜像到 db/app.db
  • db/app.db（SQLite）: credentials 凭据表（明文）不随 PG 走——只备份 PG 会丢凭据，只备份 app.db 会丢业务数据，两者都要
  • data/ + backend/data/: 各任务报表产物与 settings.json（丢 settings.json 会退回内置默认远程主机）
  • backend/services/*.json: 上游连接参数与 TT 规则表等，属代码资产随仓库走

5.5 定期清理：什么能删、什么别动

可以清理

  • 运行日志 log/*.log（大文件先停服务再清，避免句柄占用；没有日志轮转，会一直涨）
  • 一次性调试产物：log/edge_cleanup*.txt、killlog*.txt、backend/restart_dbg.log 等
  • 历史空库 data/app.db、data/my_app.db（0 字节）；旧构建目录 frontend/dist、dist2、dist3（删前确认 nginx 未指向）

不要动

  • db/app.db —— 含凭据表（明文）与 PG 快照镜像，约 954MB，绝对不是垃圾文件
  • backend/services/auth_cache/ —— 上游站点会话 cookie（等同有效登录态），不得外发
  • data/ 下各任务目录 —— 报表产物与任务专用 SQLite
  • backend/services/eflow_rules/eflow_TT_rules.xlsx —— 正式 TT 规则表（根目录同名文件只是副本）

6. 常见问题

看板数据没有更新？

① 先到「任务管理」查看对应任务的最近执行结果与失败聚合；② 检查顶栏「自动刷新」间隔是否被调成关闭；③ 注意部分数据本身低频同步：实时告警每 30 分钟、微波拓扑每天 05:15、丢包每天 06:30、事件总览每小时整点。仍不对可看「数据库数据新鲜度巡检」的执行日志，它会输出调用链与排查方向。

页面数字与预期口径不一致？

注意各页口径：电池看板默认只统计 24 小时内新鲜读数；MS SLA 看板以实时计算为准（可能与快照文件不一致）；丢包看板只展示最近 7 个完整自然日；CXO 看板内嵌快照，重跑同步任务才更新。

任务长期停在 pending 不执行？

多半是该任务未被归入任何 worker 组（GROUP_TASK_MAP），队列里永远无人认领——这是本项目已发生过四次的事故模式（finebi_report_sync、whatsapp_send_ext、sp_email_details，以及 2026-09-18 查出的 olib_soc 看板增量与 vmax_multi_data_sync）。新增任务必须在 worker_watchdog.py 的 GROUP_TASK_MAP 登记分组；陈旧 pending 占住的单飞名额 6 小时后会被 worker 自动过期释放。2026-09-18 起这类停摆不再靠人肉发现：db_freshness_check（每小时）会把未归组 / 无执行记录 / 队列滞留 / 成功逾期四类健康异常按翻转去重主动微信+邮件通知。

任务反复 failed？

到 log/worker_runtime*.log 找该 task_id 的堆栈（排障首选日志；每组 worker 一个文件，任务所属组见执行认领日志）。上游不可达 → 先到「系统设置 → 凭据」点「测试连接」；口令变了 → 更新凭据。auto_retry_failed 每 10 分钟自动重试（MAX_ATTEMPTS=2，超 24 小时放弃），无需手动反复点执行。

任务一直「执行中」不动？

调度器没有 per-task 超时（设计缺口）。僵尸运行态由 worker 每 300 秒扫描回收（30 分钟 + PID 存活核对），无需手工干预；若任务真在长跑（如 Playwright 探测），可在任务管理页手动「停止」。

邮件没发出去？

EWS 邮箱故障时邮件任务会失败，email_recovery（每 20 分钟）会在恢复后自动补发近 3 小时内失败的邮件——先查它的执行历史，而不是手动重跑原邮件任务。邮箱空间满由 mailbox_cleanup（每小时）守卫。

如何在大屏/另一个标签页打开看板？

右键点击左侧菜单项 → 「在新标签页打开」；或直接访问直链 http:///myapp/?page=。配合顶栏「自动刷新」即可长期挂机展示。

上传的数据质量如何确认？

「数据上传」页入库后会给出问题面板与质量评分；确认无问题后可到「表浏览器」查看数据与字段画像，再用「分析仪表盘」出图。

忘记某个指标/术语的定义？

多数看板的指标旁有口径说明图标（Metric Explain）；更完整的术语表与逐页手册见项目文档 docs/manual/（01-overview 术语表、11-feature-guide 功能页手册）。
