# 掉站工单派给谁，到底由什么决定？

## 一句话

**由根因（`root_cause`）决定，不由掉站类型 CSD / PSD 决定；判定基准是告警发生时刻（含规则内置 4 小时延迟），不是派单时刻。**

---

## 常见误解

### 误解 1：以为掉站类型决定派给谁

**事实：CSD 和 PSD 派给三方的比例几乎完全一样。**

| 掉站类型 | 工单数 | 派 G:3rd_Power | 占比 |
|---|---|---|---|
| CSD（Complete Site Down） | 14,292 | 8,202 | **57.4%** |
| PSD（Partial Site Down） | 2,882 | 1,651 | **57.3%** |

两者相差 0.1 个百分点 —— **掉站类型对派单归属基本没有影响。**

### 误解 2：以为按「派单时刻」的站点状态判定

**事实：判定基准是告警发生时刻。且 4 小时延迟是规则内置的，不是派单晚了。**

eFlow 历史告警（API `fm-history/v1/hisalarms/pageinfo`）里的硬证据：

| 字段 | 值 | 说明 |
|---|---|---|
| `Assign RuleName` | **SITEOUTAGE_REGULAR_COOL** | 自动派单规则（REGULAR=普通站，COOL=站点电源类型） |
| `Assign Delay` | **14400s（= 4 小时）** | **规则内置延迟**，不是异常 |
| `Assign Start Time` | 2026-08-22 06:28:06 | = 告警发生(02:28:06) + 4h，**分秒吻合** |
| `Assigned Type` | Assign-Append | 自动追加 |

**派单时间 = 告警时间 + 规则延迟（4h）**。这是设计行为：给网络 4 小时自愈窗口，
没恢复才派单。所以拿「派单晚了几小时、状态已变化」去质疑派单，方向就错了。

### 误解 3：以为告警时 2G/3G 同时掉站（本案实际时间线）

站 3618（Lango Number2）在 2026-08-22 的全部 4 条告警（eFlow 历史告警 API 实查）：

| 告警 | 制式 | 发生 | 恢复 | 与 TT047 关系 |
|---|---|---|---|---|
| SITE DOWN DUE TO POWER OFF | 2G | 08-22 **02:27:21** | 08-28 20:57:42 | 触发 TT047 |
| Complete site down (CSD) | 2G | 08-22 02:27:23 | 08-28 20:54:40 | 未关联 |
| 2G SITE DOWN | 2G | 08-22 02:34:25 | 08-28 20:54:40 | 未关联 |
| **3G SITE DOWN** | **3G** | **08-22 13:31:07** | **08-23 08:21:27** | 17:31 Assign-Append 追加进 TT047 |

读法：

- **告警时（02:27）只有 2G 掉站，3G 当时是好的**
- **派单时（06:28）2G 还掉着，3G 根本还没掉**（3G 是 7 小时后才掉的）
- 3G 恢复于次日 08:21；2G 一直掉到 8/28（= 工单总时长 6d18h30m）
- TT 上的 `impacted_service=2G,3G` 是因为 3G 告警后来被 **追加** 进了这张 TT，**不代表告警/派单时刻的掉站状态**

> 本案中本地员工的三句话：「告警时 2/3 同时掉」「派单时 3G 起来了」「应按 PSD 派给我们」——
> 前两句与告警流水不符，第三句即使成立也不改变归属（见误解 1）。

## 真正的派单依据：根因

全库 `eflow_tt` 按 `root_cause` 统计派单归属（2026-09-01 数据）：

| 根因 `root_cause` | 总单数 | 派三方电源组 | 派 ZTE_NOC_FO | 三方占比 |
|---|---|---|---|---|
| **POWER** | 14,432 | 10,547 | 1,702 | **73.1%** |
| Auto-recovery | 3,848 | 59 | 358 | 1.5% |
| RAN | 728 | **0** | 345 | **0%** |
| MW | 391 | **0** | 137 | **0%** |
| Fiber | 365 | **0** | 140 | **0%** |
| Uknown | 373 | 118 | 171 | 31.6% |
| Planned work | 111 | 65 | 30 | 58.6% |

**读法**：
- 根因是 **POWER（电源）** → 大概率派三方电源组 `G:3rd_Power`
- 根因是 **RAN / MW / Fiber** → **一单都不派三方**，全部自维

> ⚠️ POWER 类仍有约 27% 派往别处，说明根因不是唯一条件（规则名里的
> REGULAR/COOL 是站点属性维度）。确切规则以 eFlow 配置中心的派单规则为准。

## 案例：TT202608220047（Lango Number2）完整结论

| 项 | 值 |
|---|---|
| `root_cause` / `sub_root_cause` | POWER / Power Solar（太阳能蓄电池耗尽） |
| `ticket_severity` / `sla_status` | P3 / Failed |
| 派单规则 | SITEOUTAGE_REGULAR_COOL，内置延迟 4h |
| 派往 | G:3rd_Power（三方电源组） |
| 2G 掉站窗口 | 08-22 02:27 → 08-28 20:57（6d18h30m，全险时长） |
| 3G 掉站窗口 | 08-22 13:31 → 08-23 08:21（派单后才掉，次日恢复） |

**没派错。** 三条独立证据链：

1. **根因**：POWER 类 73.1% 派三方，本单根因正是 POWER
2. **规则**：SITEOUTAGE_REGULAR_COOL 自动派单，4h 内置延迟，派单时间分秒吻合
3. **时间线**：判定基准 02:27（当时 2G 全断 + CSD 告警 + 电源原因）；
   3G 的变化发生在派单之后，逻辑上不可能影响派单判定

**给本地员工的解释口径**：4 小时是系统规则（等自愈），不是派慢了；
派单看的是告警那一刻（2G 全断、电源原因），3G 是派单之后才掉、次日就恢复的，
TT 上的"2G,3G"是事后追加进来的，不代表派单时的状态。

## 遇到「派错了」的投诉，先查这三样

```sql
SELECT tt_no, alarm_occur_time, created_time, root_cause, sub_root_cause,
       root_cause_description, sub_alarm_name, last_processer_group
FROM eflow_tt WHERE tt_no = 'TT号';
```

1. **`root_cause` 是什么** —— POWER 类派三方属正常
2. **`alarm_occur_time` 与 `created_time` 差多久** —— 接近 4 小时是规则延迟，正常
3. **`sub_alarm_name` 里的 CSD/PSD** —— 仅供参考，不决定归属

再深一层（查各制式告警的真实发生/恢复时间）：

```bash
python "D:\01_RPA\Task\eflow_Q&A\tools\eflow_hisalarm_by_tt.py" TT202608220047
```

本地 `history_alarm` 表只滚动保留 48 小时（`eflow_alarm_config.json: his_alarm_hours`），
更早的告警该工具会直连 eFlow API 按时间窗拉取后按单号过滤。
