## 一、清理 22 小时孤儿 DELETE + 15 小时 DROP INDEX（锁风暴收尾）

接 10-28 日志末尾的「新发现」：`ipran_ume.Metro_ring_me_15mins` 上有个孤儿 DELETE。

**实际状况比日志记录的严重得多 —— 整张表已被堵死**（`pg_stat_activity` 实测）：

| pid | 状态 | 已持续 | 语句 |
|---|---|---|---|
| 69340 | active / `IO: BufFileRead` | **21h48m** | `DELETE ... ctid NOT IN (SELECT MIN(ctid) ...)` |
| 38576 | active / `Lock: relation` | **15h48m** | `DROP INDEX IF EXISTS "u_Metro_ring_me_15mins"` |
| 8 个 | `Lock: relation` 排队 | 15h46m ~ 1h46m | `SELECT COUNT(*)` / `SELECT ...` 全表 |

**关键机制（这次才看清）**：DELETE 持的 `RowExclusive` **不挡 SELECT**（两者兼容）。
真正的队头阻塞者是 `DROP INDEX` —— 它要 `AccessExclusive`，与任何锁互斥；PG 锁队列是
FIFO，它一等，后面所有读请求全排在它后面 → **表对所有人不可用**，还占着 11 个连接。

**处置（顺序很重要）**：
1. 先 `pg_cancel_backend(38576)` 取消 `DROP INDEX` → 队列头移除，8 个读立刻
   `wait_event` 变 `None` 开始真正执行（它们的 `xact_start` 显示 15h，但那是**事务开始**
   时间，不是执行时间，一直在等锁）。
2. 确认唯一索引 `u_Metro_ring_me_15mins` **仍在**（cancel 后 DDL 回滚），110 万行 / 379MB。
3. 再 `pg_cancel_backend(69340)` 清掉孤儿 DELETE（从未提交，回滚不丢数据）。
4. 结果：活跃会话 12 → 1，等锁 0。

**根因纠正**：10-28 日志说「4 处 `ctid NOT IN (SELECT MIN(ctid)...)` 反模式没清」，
**实际 4 处 10-28 20:43~20:44 就全改完了**（`dialect_helpers.dedupe_rows`，
`ipran_ume_kpi_service.py:996` / `ms_sla_sync.py:316` / `mw_ume_kpi_service.py:842` /
`sync_from_eflow_api.py:361`）。那条 22 小时的 DELETE 是**旧进程跑旧模块**残留 ——
Python 不热重载，改完没重启 worker，10-29 12:46 起的任务仍在执行改前的 SQL。
**教训：改 `backend/services/**` 后不重启 worker 组 = 改动等于没上线，且会留下僵尸查询。**

## 三、`sync_pg_to_sqlite` 单表锁窗口二次优化（本次主要代码改动）

10-28 只解决了「跨表」累积（每表结束 commit），**单表内部锁窗口仍 = 读 PG + 写 SQLite**，
`battery_reading` 105 万行最坏实测 399.5s。

**改法**：`sync_table` 里 `SELECT` 的 `execute()` 返回后**立刻** `_end_pg_read_txn()`，
不等数据写完 SQLite。

**依据（已实测验证）**：psycopg2 普通（非命名）游标在 `execute()` 时已由 libpq 把整个
结果集**同步**拉回客户端，因此 commit 之后游标仍可继续 `fetchmany`。
实测 `TMP/t_sync_lockwindow.py`：`execute` 0.06s → `commit` 0.00s → 之后 `fetchmany`
正常取完全部行。

**对照实测 `TMP/t_sync_lock_ab.py`**（`battery.battery_reading`，113.5 万行）：

| | 总耗时 | PG 锁窗口 |
|---|---|---|
| 旧（边读边写） | 8.8s | **9.1s** |
| 新（读完即放锁） | 6.2s | **0.6s** |

锁窗口缩短 **93%**，行数一致（1,135,590）。

**刻意不用 `fetchall`**：三张百万行表（`lte_pl.packet_loss_data` 140 万 /
`ipran_ume.Metro_ring_me_15mins` 110 万 / `battery.battery_reading` 105 万）整体转
Python 对象峰值内存约 **900MB**，会顶爆 worker。仍保持 `fetchmany(BATCH_SIZE=5000)`
分批消费客户端缓冲，并在 `finally` 里显式 `cur.close()` 及时释放该缓冲
（否则下一张表读取时与上一张残留缓冲内存叠加）。

**已上线**：`restart_workers.py --groups p`（pid 50344 → 57808），下轮 `:45` 生效。

### magpie「Sessions」页只显示部分客户端的原因

- Sessions 的来源**不是插件**，是 `~/.config/magpie/settings.json` 的 **`sessionReads.agents.<clientId>: bool`** 逐个开关；GUI 入口在 **Settings → Privacy**（源码 `if (view === "settings" && tab === "privacy") loadSessionReads()`，内部 API `/api/sessions/reads`，只在 GUI 侧，3425 端口访问会 404）。
- 结构：`sessionReads = { asked: bool, agents: { claude/claude-desktop/codebuddy/codex/cursor/dsh/grok/minimax-code/qoder/qoder-cn/workbuddy/zcode } }`。只有 `true` 的客户端会话才会出现在 Sessions 列表，未勾选不是「读不到」而是「没授权」。
- 2026-10-30 17:10 已把 `claude`、`workbuddy`、`dsh` 置 true（原仅 `qoder`、`zcode`），备份 `settings.json.bak-20261030-sessionreads`；改文件后需重启 magpie 或在 GUI Privacy 页确认。

## VMAX 流量卡「子页签不显示」复盘（用户三次反馈同一现象）

**现象**：查 `231777777322`，用户说「还是没有显示要求的子页签」。参考图是上游 CCA「流量信息」面板的
**两级页签**：`数据 | 语音` + `流量 | 视频 | 网页 | 游戏 | OTT语音 | OTT视频 | TCP指标 | 控制面`。

**三个原因叠加，之前只查了后两个，漏了第一个**：
1. **用户看的是「信令详单」页签**，不是「用户概览」——页签在概览的「流量信息」卡里。
2. **空态时组件整体短路返回**（真正的 bug）：
   `VmaxFlowCategoryTabs` 开头 `if (!flow) return <Text>{t('vmaxq.noFlow')}</Text>`，
   外层 `VmaxCcaCards` 又有 `result.flow ? <Tabs/> : <Text>noFlow</Text>` —— 两处都短路，
   页签条根本不进 DOM。**页签结构是「这个面板长什么样」的信息，不该随数据有无消失。**
   修法：页签条恒渲染，空态说明放进页签**内部**。
3. **用户浏览器是旧构建**：截图里时间窗是 `00:00 → 15:04`（旧的「今天 00:00」默认），
   新版应是最近 3 小时（`14:11 → 17:11`）。**判断用户看的是不是新版本，看默认时间窗即可**，
   比问「你刷新了吗」可靠。

**顺带补齐**：参考图第一级的 `数据 | 语音` 之前没做。上游**不支持**语音
（`Traffic info of service type [VOICE] is not supported`），但保留这一档并在选中时说明，
不静默隐藏（隐藏会让用户以为上游没这个维度）。

**验证方式（可复用）**：Playwright 无头浏览器 + `device_scale_factor=1` 截图卡片元素，
比 `browser_take_screenshot` 可靠 —— MCP 那个浏览器窗口窄到 1024px，**8 个页签会竖着堆叠**，
看起来像没做；1600px 宽视口下才是正常的一行。探针脚本落 `TMP/`、用完即删。

**教训**：用户说「没显示」时，先确认他看的是**哪个页签**、**哪一屏**、**是不是新构建**，
再改代码。前两次都在代码里找原因，实际第一次的答案是「你在另一个页签」。
