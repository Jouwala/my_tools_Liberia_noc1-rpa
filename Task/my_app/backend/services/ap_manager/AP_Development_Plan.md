# AP（Action Plan）模块开发方案

**文档版本：** 1.0\
**日期：** 2026-10-30\
**目标：** 将 Action Plan（行动计划／整改任务）能力集成到现有
Workflow，实现任务下发、接收、执行、提交审核、审核关闭的完整闭环。

------------------------------------------------------------------------

## 1. 项目目标与设计原则

AP
模块用于把问题、风险或管理要求转化为可跟踪、可审核、可追溯的整改任务。

### 1.1 核心目标

-   支持向指定个人或指定部门下发 AP。
-   支持负责人接收任务、确认任务并更新执行进度。
-   支持上传整改说明、图片和文件等完成凭证。
-   执行人提交完成申请后，必须由审核人审核。
-   审核通过后 AP 才能关闭；审核退回后，执行人继续整改。
-   通过 Web 页面和邮件通知推动任务流转。
-   保留完整操作历史，支持管理统计和审计追溯。

### 1.2 设计原则

1.  **集成现有 Workflow：**
    优先复用现有用户、部门、角色、认证、邮件和附件能力，不另建一套独立系统。
2.  **后端控制流程：**
    前端只负责展示和发起操作；权限校验、状态转换和数据一致性必须由后端执行。
3.  **审核后关闭：** 执行人不能直接把任务改成已完成。
4.  **过程可追溯：** 关键操作记录操作人、时间、操作类型和变更内容。
5.  **通知与业务解耦：** 邮件发送失败不应导致 AP 下发失败。
6.  **可扩展：** 为后续模板、自动升级、SLA、批量下发和报表分析预留空间。

## 2. 业务流程

### 2.1 标准闭环

``` text
创建 AP
   |
   v
填写任务信息、执行对象、审核人、截止时间
   |
   v
下发 AP（Assigned）
   |
   v
接收人确认（Acknowledged）
   |
   v
执行整改（In Progress）
   |
   v
填写完成说明、上传凭证
   |
   v
提交审核（Pending Review）
   |
   +----------------------+
   |                      |
   v                      v
审核通过                审核退回
   |                      |
   v                      v
Completed              Rejected
   |                      |
   v                      v
任务关闭                继续整改
                          |
                          +----> In Progress
```

### 2.2 个人任务与部门任务

**个人任务：** - 创建人直接指定一个或多个执行人。 -
每个执行人收到站内通知和邮件。 - 执行人确认、更新进度并提交完成申请。 -
多执行人任务可选择完成规则： -
`ALL_REQUIRED`：所有指定执行人都必须完成。 -
`SINGLE_OWNER`：由主负责人完成即可，其他人员作为协作人。

**部门任务：** - 创建人指定目标部门。 -
默认由部门负责人接收任务，再分配具体执行人。 -
部门负责人可以查看本部门全部 AP。 -
可指定一个主负责人，也可分配多个执行人。 -
建议保留部门级责任人与实际执行人两个概念，避免"任务下发给部门但无人负责"的情况。

### 2.3 审核规则

-   AP 创建时指定审核人，或由系统按部门／任务类型规则自动分配。
-   执行人提交审核后，任务进入 `Pending Review`。
-   审核通过：进入 `Completed`，记录审核人、审核时间和审核意见。
-   审核退回：进入
    `Rejected`，必须填写退回原因；执行人重新整改后再次提交。
-   原则上，审核人不能审核自己提交的完成申请；如业务确需例外，应由管理员配置并记录原因。

## 3. 状态设计

  状态               含义                 主要触发动作
  ------------------ -------------------- --------------------------
  `Draft`            草稿，尚未下发       创建或保存草稿
  `Assigned`         已下发，等待接收     AP Manager 下发
  `Acknowledged`     执行人已确认接收     执行人确认
  `In Progress`      正在执行整改         开始执行或退回后重新整改
  `Pending Review`   已提交，等待审核     执行人提交审核
  `Completed`        审核通过，任务关闭   审核人批准
  `Rejected`         审核退回，等待整改   审核人退回
  `Overdue`          逾期标记             根据截止时间计算

**重要说明：** `Overdue`
建议作为独立的逾期属性，而不是覆盖业务状态。例如，一个处于 `In Progress`
的任务可以同时是逾期任务。这样可以避免任务逾期后丢失原有流程状态。

建议在数据库中保存业务状态 `status`，并根据 `due_at`、`completed_at`
计算 `is_overdue`，或由定时任务维护逾期标记。

### 3.1 合法状态转换

  当前状态           操作           目标状态         操作权限
  ------------------ -------------- ---------------- -------------------------------
  Draft              下发           Assigned         AP Manager / 创建人（按权限）
  Assigned           确认接收       Acknowledged     被指派人／部门负责人
  Acknowledged       开始执行       In Progress      执行人
  In Progress        提交审核       Pending Review   主负责人／授权执行人
  Pending Review     审核通过       Completed        Reviewer
  Pending Review     审核退回       Rejected         Reviewer
  Rejected           重新开始整改   In Progress      执行人
  Draft / Assigned   取消           Cancelled        AP Manager / 授权管理员

所有状态转换均需由后端校验，不允许通过直接修改请求参数绕过流程。

## 4. 核心功能页面

### 4.1 AP Dispatch（AP 下发）

供 AP Manager 创建、编辑和下发任务。

主要字段： - AP 标题 - AP 分类 - 问题描述／整改要求 -
目标对象：个人或部门 - 部门、执行人、主负责人 - 优先级 - 创建时间 -
截止时间 - 审核人 - 关联工单、Site ID、Region 等业务对象 - 附件

主要操作： - Save Draft - Dispatch - Cancel

### 4.2 My AP（我的 AP）

供执行人查看和处理分配给自己的任务。

建议展示： - AP ID、标题、来源部门 - 优先级、截止时间、剩余时间 -
当前状态、进度 - 主负责人／协作人 - 最近更新时间

主要操作： - Acknowledge - Start - Update Progress - Upload Evidence -
Submit for Review

### 4.3 Department AP（部门 AP）

供部门负责人查看部门任务。

主要功能： - 查看部门全部 AP。 - 指派或调整执行人。 -
设置主负责人和协作人。 - 跟踪部门任务进度。 - 查看逾期任务和待审核任务。

### 4.4 AP Review（审核中心）

供审核人处理待审核任务。

主要信息： - AP 基本信息 - 整改前的问题描述 - 执行过程和进度记录 -
完成说明 - 图片及附件凭证 - 提交人和提交时间 - 历史审核意见

主要操作： - Approve - Reject（必须填写原因）

### 4.5 AP Analytics（统计分析）

建议提供以下指标： - Total AP - Open AP - In Progress - Pending Review -
Completed - Overdue - Completion Rate - On-time Completion Rate -
Average Closure Time - Department Performance

建议支持按时间、部门、区域、优先级、任务分类和状态筛选。

### 4.6 Notifications（通知中心）

集中展示： - 新 AP 下发 - AP 接收确认 - 任务即将到期 - 任务逾期 -
提交审核 - 审核通过 - 审核退回 - 执行人或审核人变更

## 5. 数据字段设计

### 5.1 AP 主表字段

  字段                  类型建议        说明
  --------------------- --------------- --------------------------------
  `id`                  BIGINT / UUID   主键
  `ap_no`               VARCHAR(40)     AP 唯一编号
  `title`               VARCHAR(255)    任务标题
  `category`            VARCHAR(80)     AP 分类
  `description`         TEXT            问题描述和整改要求
  `status`              VARCHAR(30)     当前业务状态
  `priority`            VARCHAR(20)     Low / Medium / High / Critical
  `target_type`         VARCHAR(20)     USER / DEPARTMENT
  `department_id`       BIGINT / UUID   目标部门
  `owner_user_id`       BIGINT / UUID   主负责人
  `reviewer_user_id`    BIGINT / UUID   审核人
  `completion_rule`     VARCHAR(20)     ALL_REQUIRED / SINGLE_OWNER
  `progress`            SMALLINT        进度百分比，0--100
  `due_at`              TIMESTAMP       截止时间
  `created_by`          BIGINT / UUID   创建人
  `created_at`          TIMESTAMP       创建时间
  `updated_at`          TIMESTAMP       更新时间
  `submitted_at`        TIMESTAMP       最近提交审核时间
  `completed_at`        TIMESTAMP       审核通过时间
  `cancelled_at`        TIMESTAMP       取消时间
  `related_ticket_id`   VARCHAR(100)    关联工单
  `site_id`             VARCHAR(100)    关联站点
  `region_id`           VARCHAR(100)    关联区域

用户、部门和关联业务对象的字段类型应以现有系统实际主键为准。

### 5.2 执行人表 `ap_assignees`

用于支持一个 AP 对应多个执行人。

建议字段： - `id` - `ap_id` - `user_id` - `role`：OWNER / ASSIGNEE /
COLLABORATOR - `assignment_status` - `acknowledged_at` -
`completed_at` - `created_at`

### 5.3 审核表 `ap_reviews`

建议字段： - `id` - `ap_id` - `reviewer_user_id` - `decision`：APPROVED
/ REJECTED - `comments` - `submitted_snapshot`：提交审核时的内容快照 -
`reviewed_at` - `created_at`

### 5.4 进度更新表 `ap_updates`

建议字段： - `id` - `ap_id` - `user_id` - `progress` - `update_note` -
`created_at`

### 5.5 附件表 `ap_attachments`

建议字段： - `id` - `ap_id` - `update_id`（可为空） - `uploaded_by` -
`file_name` - `storage_key` - `mime_type` - `file_size` - `created_at`

### 5.6 历史记录表 `ap_history`

建议记录： - AP 创建、编辑、下发和取消 - 执行人分配和变更 - 接收确认 -
进度更新 - 提交审核 - 审核通过／退回 - 截止时间变更 - 附件上传和删除

建议字段： - `id` - `ap_id` - `actor_user_id` - `action` -
`from_status` - `to_status` - `details_json` - `created_at`

### 5.7 通知表 `ap_notifications`

建议字段： - `id` - `ap_id` - `recipient_user_id` - `channel`：IN_APP /
EMAIL - `event_type` - `delivery_status` - `retry_count` -
`last_error` - `sent_at` - `created_at`

### 5.8 模板表 `ap_templates`

用于保存常用 AP 模板，例如： - Site整改 - 设备故障整改 - KPI异常整改 -
网络优化整改 - 流程合规整改

## 7. REST API 设计

建议统一使用 `/api/ap` 前缀。

  方法   路径                         用途
  ------ ---------------------------- -------------------------
  POST   `/api/ap`                    创建 AP
  GET    `/api/ap`                    AP 列表，支持筛选和分页
  GET    `/api/ap/{id}`               AP 详情
  PUT    `/api/ap/{id}`               编辑 AP
  POST   `/api/ap/{id}/dispatch`      下发 AP
  POST   `/api/ap/{id}/accept`        确认接收
  POST   `/api/ap/{id}/start`         开始执行
  POST   `/api/ap/{id}/update`        更新进度
  POST   `/api/ap/{id}/submit`        提交审核
  POST   `/api/ap/{id}/approve`       审核通过
  POST   `/api/ap/{id}/reject`        审核退回
  POST   `/api/ap/{id}/attachments`   上传附件
  GET    `/api/ap/analytics`          统计分析
  GET    `/api/ap/notifications`      通知列表

### 7.1 创建 AP 请求示例

``` json
{
  "title": "Core Site Availability Improvement",
  "category": "Network Optimization",
  "description": "Investigate the site availability issue and complete corrective actions.",
  "priority": "High",
  "target_type": "DEPARTMENT",
  "department_id": 12,
  "owner_user_id": 105,
  "assignee_ids": [105, 106],
  "reviewer_user_id": 21,
  "completion_rule": "SINGLE_OWNER",
  "due_at": "2026-11-05T17:00:00Z",
  "related_ticket_id": "TT-2026-00125",
  "site_id": "LBR-MON-001",
  "region_id": "MON"
}
```

### 7.2 提交审核请求示例

``` json
{
  "progress": 100,
  "completion_note": "The root cause was identified and corrective actions were completed.",
  "evidence_attachment_ids": [501, 502]
}
```

### 7.3 审核通过请求示例

``` json
{
  "comments": "Evidence reviewed. Corrective action verified and accepted."
}
```

### 7.4 审核退回请求示例

``` json
{
  "comments": "Please attach the post-implementation KPI comparison and resubmit."
}
```

### 7.5 API 通用要求

-   使用统一响应结构和错误码。
-   列表接口支持分页、排序和筛选。
-   所有写操作进行身份和权限校验。
-   状态变更使用事务处理。
-   对重复提交使用幂等键或业务去重机制。
-   不接受客户端直接指定任意目标状态。
-   详情接口按用户权限过滤敏感字段和附件。

## 8. 权限角色设计

  角色                 主要权限
  -------------------- ----------------------------------------------
  Admin                全局配置、用户和权限管理、必要时执行管理操作
  AP Manager           创建、下发、编辑和管理 AP
  Department Manager   查看本部门 AP、分配执行人、跟踪部门任务
  Assignee             接收任务、更新进度、上传凭证、提交审核
  Reviewer             审核指定 AP、批准或退回
  Viewer               按授权范围只读查看

### 8.1 权限控制要求

-   前端隐藏无权限按钮只是体验优化，不能代替后端鉴权。
-   后端必须检查当前用户是否为创建人、执行人、部门负责人、审核人或管理员。
-   用户只能查看其授权范围内的 AP。
-   附件下载也必须执行权限检查，不能只依赖不可猜测的文件 URL。
-   审核动作必须校验 AP 当前状态为 `Pending Review`。
-   执行人不得直接调用接口将 AP 改为 `Completed`。

## 9. 邮件与站内通知

### 9.1 通知触发点

  事件       通知对象                         建议通知内容
  ---------- -------------------------------- ----------------------------
  AP 下发    执行人／部门负责人               新任务、截止时间、任务链接
  接收确认   创建人／AP Manager               谁已接收任务
  进度更新   主负责人／部门负责人             当前进度和更新说明
  即将到期   执行人／部门负责人               到期提醒
  任务逾期   执行人／部门负责人／AP Manager   逾期提醒
  提交审核   审核人                           待审核任务和凭证链接
  审核通过   执行人／创建人                   审核结果和关闭信息
  审核退回   执行人                           退回原因和后续要求

### 9.2 邮件发送架构

建议采用异步发送：

``` text
业务 API
   |
   v
数据库事务写入 AP + 通知事件
   |
   v
通知队列 / Outbox
   |
   v
邮件 Worker
   |
   v
SMTP Server
   |
   +---- 成功：更新发送状态
   |
   +---- 失败：记录错误并按策略重试
```

### 9.3 可靠性要求

-   邮件失败不能回滚已经成功的 AP 下发操作。
-   保存发送状态、失败原因和重试次数。
-   采用指数退避重试，例如 1 分钟、5 分钟、15 分钟。
-   对同一事件和收件人做去重，避免重复邮件。
-   邮件正文包含 AP 编号、标题、截止时间、当前状态和系统内链接。
-   邮件不应直接暴露不必要的敏感信息。

## 10. 前端交互与视觉建议

建议沿用现有系统的 HTML、Tailwind CSS 和 JavaScript 技术栈，保持
Workflow 的导航、字体、颜色和交互一致。

### 10.1 AP 列表

建议采用数据表格布局，优先展示： - AP No. - Title - Department - Owner -
Priority - Status - Progress - Due Date - Updated At - Action

建议提供： - 状态筛选 - 部门筛选 - 优先级筛选 - 日期范围 - 关键词搜索 -
分页和排序

### 10.2 状态与优先级视觉

状态颜色应保持全站统一。建议： - Draft：灰色 - Assigned：蓝色 -
Acknowledged：青色 - In Progress：蓝色或紫色 - Pending Review：橙色 -
Completed：绿色 - Rejected：红色 -
Overdue：红色警示标记（作为额外属性显示）

优先级建议使用文字标签与颜色组合，不能只依赖颜色区分。

### 10.3 AP 详情页

建议采用清晰的分区： 1. 顶部：AP 编号、标题、状态、优先级。 2.
基本信息：部门、负责人、创建人、审核人、截止时间。 3.
整改要求：问题描述和目标。 4. 执行进度：进度条和更新记录。 5.
附件凭证：文件列表和预览。 6. 审核区域：审核意见和审核操作。 7. Activity
Timeline：完整操作时间线。

### 10.4 响应式设计

-   桌面端优先保证列表密度和信息可读性。
-   小屏幕将表格转为任务卡片或横向滚动表格。
-   主要操作按钮保持明确，不要在单行中堆叠过多按钮。
-   长描述和历史记录采用折叠展开，避免详情页过长。

## 11. 统计指标定义

建议先统一指标口径，再开发图表。

  指标                      建议计算口径
  ------------------------- --------------------------------------
  Total AP                  当前统计范围内创建的 AP 总数
  Open AP                   尚未 Completed 或 Cancelled 的 AP 数
  In Progress               `status = In Progress` 的 AP 数
  Pending Review            `status = Pending Review` 的 AP 数
  Completed                 `status = Completed` 的 AP 数
  Overdue                   未完成且当前时间晚于截止时间的 AP 数
  Completion Rate           Completed /（Total - Cancelled）
  On-time Completion Rate   截止时间前完成的 AP / Completed
  Average Closure Time      从下发时间到审核通过时间的平均时长

需明确统计时间范围、取消任务是否纳入分母、重开任务如何计算，避免不同页面出现不同口径。

## 12. 安全、稳定性与数据一致性

上线前应落实以下要求：

1.  **唯一编号：** AP 编号由后端生成并建立唯一索引。
2.  **时间统一：** 数据库存储 UTC 时间，前端按用户时区展示。
3.  **事务一致性：** 状态变更、审核记录和历史记录应在同一事务中提交。
4.  **审核快照：**
    提交审核时保存完成说明、进度和凭证引用快照，避免审核过程中内容被静默修改。
5.  **审计日志：** 关键操作不可被普通用户删除或覆盖。
6.  **软删除：** 已下发任务不建议物理删除，应使用取消或归档。
7.  **防重复操作：** 对下发、提交审核、审核等动作实施幂等控制。
8.  **附件安全：**
    校验文件类型、大小和文件名；文件存储路径不可由用户任意指定；下载时校验权限。
9.  **防越权：** 每个 API 都必须检查用户对该 AP 的访问范围。
10. **通知解耦：** 邮件服务异常不得影响核心业务事务。
11. **并发控制：**
    审核和状态转换应防止两个请求同时处理同一任务造成冲突。
12. **备份与恢复：** AP 主数据、附件元数据和操作日志纳入备份策略。

## 13. 分阶段开发计划

### Phase 1：基础框架

-   确认现有用户、部门、角色和认证接口。
-   建立 AP 数据库表和索引。
-   实现 AP 编号生成。
-   实现创建、编辑、列表和详情 API。
-   实现基础权限控制。

**交付：** 可以创建、保存和查看 AP。

### Phase 2：任务流转

-   实现个人和部门任务下发。
-   实现接收确认和执行人分配。
-   实现进度更新和操作历史。
-   实现状态转换校验。

**交付：** AP 可以从下发流转到执行中。

### Phase 3：附件与审核

-   实现附件上传和下载权限。
-   实现提交审核。
-   实现审核通过和退回。
-   实现审核快照和完整审核记录。

**交付：** 完成"执行---提交---审核---关闭"闭环。

### Phase 4：通知与提醒

-   实现站内通知。
-   接入 SMTP 异步邮件发送。
-   实现失败重试和发送日志。
-   实现到期提醒和逾期提醒。

**交付：** AP 可通过 Web 和邮件推动处理。

### Phase 5：统计与优化

-   实现 AP Analytics。
-   实现部门和区域维度分析。
-   优化筛选、分页和性能。
-   完成安全测试、并发测试和用户验收。

**交付：** 可正式投入日常管理使用。

## 15. 需要结合现有项目确认的事项

以下内容需要检查现有代码和数据库后才能最终定稿：

1.  当前后端使用 Flask、FastAPI、Django 还是其他框架。
2.  当前数据库类型及用户、部门、角色表结构。
3.  现有 Workflow 的页面路由和导航结构。
4.  现有登录态如何传递给 API。
5.  现有邮件服务是否已有 SMTP 配置和发送队列。
6.  现有附件上传、文件存储和下载权限机制。
7.  现有用户是否有部门负责人、直属经理等组织关系字段。
8.  AP 是否需要关联现有 Ticket、Site、Region 或其他业务对象。
9.  是否需要多级审核、代理审核或审核人自动分配。
10. 是否需要 SLA、逾期升级和周期性提醒规则。

**集成建议：**
在确认上述信息前，先按本方案完成业务和数据模型评审；不要直接假设现有项目的表名、API
地址或认证方式。

## 16. 推荐的首版范围

为控制开发周期，建议首版优先实现：

-   个人和部门两种下发方式。
-   一个主负责人，可配置协作人。
-   单级审核。
-   接收确认、进度更新、附件上传。
-   审核通过关闭、审核退回重做。
-   Web 站内通知和 SMTP 邮件通知。
-   AP 列表、详情、审核中心和基础统计。
-   完整操作历史及后端权限校验。

暂缓复杂的多级审批、自动升级策略、复杂模板编排和跨系统自动派单，待首版稳定后再迭代。

**最终建议：** 将 AP 作为现有 Workflow
中的一个业务模块建设，复用现有系统基础能力，以"任务责任明确、过程可追踪、凭证可验证、审核后关闭"为核心，先完成可靠的业务闭环，再扩展自动化和分析能力。
