> **触发**：群里 @机器人 问「how mang TT today」「今天多少故障单」，机器人先发垫话，随后回固定故障文案
> 「Sorry, something went wrong on my side. / 抱歉，我这边出了点故障」。

## 0. 一句话结论

**机器人、配置、API Key 全部正常，故障在 Open WebUI 一侧。**
OWU（`192.168.100.27:3000`）在当天 11:06 之后**不再向该静态 API Key 暴露本地 Ollama 模型**，
于是经 `/api/v1` 打 `qwen2.5:7b-instruct` 一律返回 **400 `{"detail":"Model not found"}`**。

**模型确实存在**（Ollama 后端 `192.168.100.27:11434` 上 `qwen2.5:7b-instruct` 可直连调用成功），
**API Key 也有效**（同一把 key 打云端模型 `agnes-2.5-flash` 正常 200）。
坏的是 OWU 的**模型可见性**这一环 —— 属于上游服务端问题，**机器人侧一个字都没改**。

修复动作由用户在 OWU 侧完成（恢复模型暴露），随后机器人无需重启即恢复正常。

### 本次的衍生改动（防复发）

故障期间**整个群的问答全挂**，而本机 WorkBuddy 代理其实一直好着。遂加了一条
**主模型失败 → 自动回退兜底 provider** 的链路（`src/llm.js`，见 §5）。这是本次唯一落地的代码改动。

## 2. 根因排查过程（含一次误判，记录下来避免重走）

### 2.1 先排除了「机器人配置错」

`src/config.js` 的 `loadRuntimeConfig()`（启动时调 `GET {myAppApiBase}/api/ai-model-settings`）
解析结果如下，与 2026-10-12 正常时**完全一致**：

```
[config] 已从 my_app 加载 AI 配置 → qwen2.5:7b-instruct @ http://192.168.100.27:3000/api/v1
providerInfo: {"provider":"openai","model":"qwen2.5:7b-instruct",
              "baseUrl":"http://192.168.100.27:3000/api/v1","keySource":"环境变量 OPENWEBUI_API_KEY"}
```

参数（模型名、地址、key 来源）前后不变 → **不是配置漂移**。

### 2.2 误判：一度以为「模型不存在」

`POST .../api/v1/chat/completions` 打 `qwen2.5:7b-instruct` 得 `400 Model not found`，
第一反应是「模型名写错/模型被删」。**这个判断是错的**，被下面两条实测推翻。

### 2.3 实测证伪「模型不存在」

| 探测 | 结果 |
| --- | --- |
| 直连 Ollama `POST http://192.168.100.27:11434/api/chat`，model=`qwen2.5:7b-instruct` | ✅ 正常返回正文 |
| `GET http://192.168.100.27:11434/api/tags` | ✅ 列出 `qwen2.5:7b-instruct` / `qwen2.5:3b` / `gemma3:4b` / `bge-m3:latest` |

**模型在 Ollama 后端确实存在且可调用。**

### 2.4 实测定位到「OWU 层不再暴露本地模型」

同一把 key、同一时刻，经 OWU `/api/v1` 逐一试探：

| model | Ollama 后端 | OWU `/api/v1`（静态 key） |
| --- | --- | --- |
| `qwen2.5:7b-instruct` | ✅ 存在 | ❌ `Model not found` |
| `qwen2.5:3b` | ✅ 存在 | ❌ `Model not found` |
| `gemma3:4b` | ✅ 存在 | ❌ `Model not found` |
| `bge-m3:latest` | ✅ 存在 | ❌ `Model not found` |
| `auto-chat` / `gpt-5-mini` | — | ❌ `Model not found` |
| `agnes-2.5-flash`（云端模型） | — | ✅ **200** |

**所有本地 Ollama 模型经 OWU 全部失联，唯独云端模型可用。**

### 2.5 再证伪「Key 失效」

| 请求 | 结果 |
| --- | --- |
| 好 key + `agnes-2.5-flash` | ✅ 200，正常返回 |
| 伪造 key（`sk-bogus`）+ 同一请求 | ❌ `{"detail":"Your session has expired or the token is invalid."}` |

两者报错**不同** → 说明好 key 是有效并被 OWU 认下的，**只是认不下那些本地模型**。

### 2.6 结论

- 机器人侧：✅ 正常（配置、key 来源均与正常时一致）　→ **无需改动**
- Ollama 后端：✅ 正常（模型存在且可直连）
- API Key：✅ 有效
- **Open WebUI 的模型可见性：❌ 异常** —— 不再对该 key 暴露本地 Ollama 模型

典型成因（需 OWU 管理界面确认，本次由用户侧修复）：
1. OWU 的 **Ollama 连接（Settings → Connections）断了** —— 掉线后其模型即被注销，症状与此完全一致；
2. 或该 API Key 的**用户/模型权限被改**（仍在共享组外）。

> **与 2026-10-12 那次的区别**：那次是 bot 侧把 UI 地址当 API base → 打到 SPA 路由 → **405**（确定性 bug，改 bot 代码）。
> 本次是 OWU 侧模型可见性变化 → **400 Model not found**（服务端问题，改 OWU 配置）。
> **错误码不同（405 vs 400）就是区分点**，不要套用上一次的修法。

## 5. 衍生改动：主模型失败自动回退兜底（`src/llm.js`）

### 5.1 动机

本次故障期间**整个群的问答全挂**，但本机 WorkBuddy 代理（`deepseek-v4.1-flash @ 127.0.0.1:8788/v1`）
其实一直可用 —— 若能在主模型不可用时自动改打它，群里就不会只收到「something went wrong」。

### 5.2 设计

- `src/config.js` 新增 **`FALLBACK_CONFIG` 快照**：在 `loadRuntimeConfig()` 覆盖 `RUNTIME_CONFIG` **之前**，
  把 config.json / 环境变量的原始对话字段（provider/model/baseUrl/keyEnv/key）留存一份。
  当 my_app API 把主模型切到 OWU 时，这份快照正是「另一个源」（WorkBuddy 代理）。
- `src/llm.js` 的 `chat()`：主 provider 抛错且**错误类别值得回退**时，自动改打 `FALLBACK_CONFIG`，
  并在返回值上挂 `fallback: {from, to, reason}` 便于日志追溯。
- 两条守卫，防止「回退掩盖真问题」：
  - **同源不回退**：主备的 baseUrl+model 相同 → 返回 null，不回退（避免白打两遍）。
  - **鉴权/限流不回退**：401/403/429 **不**回退（那是配置/额度问题，换 provider 掩盖不了）。
  - 另提供 `opts.noFallback` 显式关闭（ping / 测试用）。

**值得回退的错误**（`isFallbackEligible`）：连不上、超时、`模型名或路径不对`、`Model not found`、5xx。
**不回退的错误**：`API Key 无效/无权限`、`限流/额度`。

### 5.3 代码位置

- 快照：`src/config.js` 的 `FALLBACK_CONFIG`（紧随 `RUNTIME_CONFIG` 定义）
- 回退主逻辑：`src/llm.js` 的 `chat()` / `isFallbackEligible()` / `fallbackTarget()`
- 覆盖注入：`openaiChat()` 的 `opts.__override`（用兜底目标的 base/model/key 替换被覆盖的 CONFIG）
- 测试：`scripts/test-llm.mjs` 第 `[8]` 节（9 项：触发回退 / 用兜底模型名 / 结果带标记 / 401 不回退 / 同源不回退 / noFallback 不回退）
