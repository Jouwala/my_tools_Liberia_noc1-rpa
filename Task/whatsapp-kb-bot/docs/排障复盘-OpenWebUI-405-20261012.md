# 排障复盘：Open WebUI 对话返回 405 ／ 群内回「something went wrong」

> **受众**：后续维护本机器人的开发者 / Agent。读完应能**复现现象、定位根因、理解改动、独立验收**。
> **日期**：2026-10-12
> **项目根**：`D:\01_RPA\Task\whatsapp-kb-bot`
> **触发**：群里 @机器人 问「how many tickets creat today」，机器人先发「正在查」垫话，
> 随后回固定故障文案「Sorry, something went wrong on my side.」
> **关联文件**：`src/config.js`、`src/llm.js`、`scripts/test-llm.mjs`、`.env`（不入库）、
> `.env.example`、`config.json`；对照实现 `Task/my_app/backend/services/openwebui_client.py`。

---

## 0. 一句话结论

bot 的对话模型被切到 **Open WebUI**（由 my_app「Settings → AI 模型设置」页驱动），但
`src/config.js` 把页面存的 **网页 UI 地址**（`http://192.168.100.27:3000`）**原样**当 API base，
`src/llm.js` 再拼 `/chat/completions` → 打到 SPA 路由，Open WebUI 回 **405**。

修法：bot 侧把该地址规范化为 **`/api/v1`**（OpenAI 兼容端点），并从环境变量
**`OPENWEBUI_API_KEY`** 读静态 key 作为 `Bearer`。这是**确定性 bug**，不是上游抽风。

## 2. 根因

### 2.1 配置有两条来源，优先级为 config.json < 环境变量 < my_app API

`src/config.js` 的 `loadRuntimeConfig()`（2026-10 新增）在启动时调
`GET {myAppApiBase}/api/ai-model-settings`，用「Settings → AI 模型设置」页存的值覆盖
`RUNTIME_CONFIG`。该页数据落在 `Task/my_app/backend/services/ai_model_config.json`：

```json
{ "provider": "openwebui", "openwebui_model": "qwen2.5:7b-instruct",
  "openwebui_base_url": "http://192.168.100.27:3000" }
```

`config.json` 里写死的 `deepseek-v4.1-flash @ 127.0.0.1:8788/v1`（WorkBuddy 代理）此时**只是兜底**，
并未生效 —— 这是排查时最容易误判的一点（本次先误判成了「上游 405 抽风」）。

### 2.2 补前缀缺位 → 405

- `src/config.js` 原样取 `openwebui_base_url` 当 base；
- `src/llm.js:81` 拼 `${base}/chat/completions`；
- → `POST http://192.168.100.27:3000/chat/completions` → **405**（SPA 路由不吃 POST）。

复现（2026-10-12 实测，与日志逐字一致）：

```
$ curl -i -X POST http://192.168.100.27:3000/chat/completions -d '…'
HTTP/1.1 405 Method Not Allowed
{"detail":"Method Not Allowed"}
```

### 2.3 为什么是 `/api/v1` 而不是 `/api`

Open WebUI 的路径语义（实测）：

| 路径 | 无鉴权 | 静态 API Key | JWT（signin） |
| --- | --- | --- | --- |
| `/chat/completions` | 405 | 405 | 405 |
| `/api/chat/completions` | 401 | **403** | 200 |
| `/api/v1/chat/completions` | 401 | **200** | 200 |

机器人用的是**静态 API Key**（用户选择），所以必须走 **`/api/v1`**。
`/api/chat/completions` 只认网页会话的 JWT，静态 key 在上面是 403。

参考实现：my_app 的 `openwebui_client.py:427` 用 `/api/chat/completions`，
是因为它走的是 `email+password → /api/v1/auths/signin → JWT`（`:189`）那条路，与 bot 不同。

## 3. 修复

### 3.1 `src/config.js`

- 新增 `toOpenWebUiApiBase(url)`：去尾斜杠；若末尾不是 `/api` 或 `/api/v1` 就补 **`/api/v1`**；
  已显式带 API 路径则原样尊重（避免 `/api/v1/api/v1`）。
- 三处「来源是 Open WebUI」的分支（`provider=openwebui`、`local` 回退、`both` 回退）改用它，
  并同时设 `RUNTIME_CONFIG.chatApiKeyEnv = 'OPENWEBUI_API_KEY'`。
- **只对 Open WebUI 套用**：WorkBuddy（`…/v1`）与 custom（用户自填）本就是完整 API base。

### 3.2 `src/llm.js`（无代码改动）

`openaiChat()` 本就是通用「base + `/chat/completions` + `Bearer key`」；
`resolveApiKey()` 读 `CONFIG.chatApiKeyEnv`（现为 `OPENWEBUI_API_KEY`）自动生效；
`validateProvider()` 的错误提示本就插值 `chatApiKeyEnv`，会自动提示正确变量名。

### 3.3 `.env`（不入库）／`.env.example`

- `.env` 新增 `OPENWEBUI_API_KEY=<在 Open WebUI 页面 Settings → Account → API Keys 生成>`。
- `.env.example` 加同名空模板项与说明。**不写任何真值**。

### 3.4 `scripts/test-llm.mjs`（顺带修一个既有回归）

该测试在 2026-10 的 `RUNTIME_CONFIG` 改造后就**已崩溃**（`CONFIG.chatApiKey` 等变成
只读 getter，赋值抛 `Cannot set property … has only a getter`）。与本次 405 无关，
但它在 `npm test` 链里，属「改到就顺手修」。改法：测试里给这些字段赋值改为写
`RUNTIME_CONFIG[key]`（`CONFIG` 的 getter 会实时回读）。

## 5. 附带发现（本次未改，记录备查）

- **规则层拼写容错**：`parseByRule('how many tickets creat today')` 返回 `null`（`creat` 拼写
  不在 `COUNT_INTENT` 内），迫使问题多走一次模型路由；`created` / `TT today` 都能规则直中。
  可考虑给 `COUNT_INTENT` 加常见拼写容错，降低对模型的依赖。见 `src/tools.js:475`。
- **人工选择 OWU 时，本地模型不可用会整体报错**：`config.js` 对 OWU key 只从环境变量取；
  若 `OPENWEBUI_API_KEY` 未配置，`validateProvider()` 会在启动时报错（这是刻意的 fail-fast）。
- **`/api`（JWT 路径）与 `/api/v1`（静态 key 路径）不可混用**：排查时若用 JWT 手动 curl
  `/api/chat/completions` 成功，会误以为「端点没问题」，而 bot 的静态 key 在该路径恒 403。
