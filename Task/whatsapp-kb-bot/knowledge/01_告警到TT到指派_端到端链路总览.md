# 告警→TT→指派 端到端链路总览

> 本知识库由 `Y:\Task\my_app\backend\services\eflow_rules` 下 4 个规则 Excel 自动生成，
> 数据时间：2026-09-07（eflow_push_rules / eflow_TT_rules / eflow_tt_severity_correction）。

## 0. English Summary — How an Alarm Becomes a TT (End-to-End Pipeline)

- **Alarm ingestion**: Alarms from network elements / OSS enter the system
  (domains: RAN / PS / CS / Transmission) and are processed by 17 alarm rule
  classes — filtering, auto-acknowledgement, auto-clear, alarm derivation,
  masking, root-cause, etc. Example: a site-down alarm plus a power alarm
  derives the combined alarm 99933 "Site Down Due To Power Off".
- **TT auto-creation (autoCreateTT)**: A Trouble Ticket (TT) is created
  automatically from the alarm. The TT carries alarmCode, alarmName,
  alarmSeverity, site / NE information, vipSite, siteSubType, assetType and
  downSiteCount.
- **Severity assignment (ttLevelRule)**: The TT priority (P1–P4) is derived
  from the alarm code plus site attributes (siteSubType, assetType, vipSite).
- **Auto dispatch (ttDispatchRule)**: Rule #164 routes the TT to FOAccept
  (field / FO line); rule #165 routes it to BOAccept (back-office / BO line).
- **Group assignment (ttGroupConfigRule / ttGroupDefaultRule /
  ttPushOrderRule)**: Conditional push rules assign the TT to a specific
  group; without a matching push rule the default group takes it.
- **Field work → confirm → auto close**: FOProcess (field handling),
  optional ThirdAccept / ThirdProcess (third party), then Confirm, and
  ttAutoCloseRule closes the TT automatically.

Keywords: how a TT is created from an alarm, alarm to TT pipeline,
end-to-end alarm handling flow, TT auto creation, alarm derivation rules,
TT severity levels, TT dispatch and assignment, FO / BO routing.

## 1. 链路全景（告警进系统 → 派人处理 → 关单）

```
告警源 (NE/OSS, domain=RAN/PS/CS/传输)
   │
   ▼ ①告警处理层 ── 详见 02_告警衍生规则.md（eflow_alarm_rules.xlsx, 规则包 OUTAGE 等）
   │   告警可见过滤/自动确认/自动清除/衍生/屏蔽/根因 等 17 类规则
   │   例: 断站告警+电源告警 → 衍生『Site Down Due To Power』(99933)；断站衍生 9920 CSD
   ▼
② TT 自动创建 ── autoCreateTT 步骤
   │   由告警驱动创建 Trouble Ticket(eflow-tt)，携带 alarmCode/alarmName/alarmSeverity、
   │   site/ne/vipSite/siteSubType/assetType/downSiteCount 等字段
   ▼ ③TT 级别定义 ── 详见 03_TT级别规则.md (ttLevelRule ×15, 全部 ACTIVE)
   │   按告警码+站点属性定级 P1~P4（优先级 1~4, 同级按条件特异性先匹配）
   ▼
④ 自动派发 ── ttDispatchRule (ID 164: 直接派 FOAccept / ID 165: 直接派 BOAccept)
   │   决定 TT 进 FO 线(现场) 还是 BO 线(后台)
   ▼
⑤ 指派/推单 ── 详见 04_TT指派与推单规则.md
   │   · ttGroupConfigRule: 各环节『可处理组名单』(谁有资格处理)
   │   · ttGroupDefaultRule: 各环节『默认指派组』(不配推单时落谁家)
   │   · ttPushOrderRule: 条件推单(满足条件自动推给指定组)
   ▼
⑥ 现场处理(FOProcess) → 第三方(ThirdAccept/ThirdProcess) → 确认(Confirm) → 自动关单
   ttPushOrderRule 119: Confirm,0>Closed; ttAutoCloseRule 117/212
```

## 2. TT 状态流转（来自推单路径与 1000 条真实 TT 样本）

Created → (autoDispatch) → FOAccept / BOAccept → FOProcess / BOProcess
→ [第三方: ThirdAccept → ThirdProcess] → Confirm → Closed

## 6. 这个知识库能回答什么

- 某告警码会衍生成什么告警、创建什么级别的 TT、派给谁（端到端）
- 某状态/环节下有哪些组可以接单、默认是谁
- 某条推单/级别/群组规则的条件是什么、当前是否启用
- 指派是否正常：推单目标组是否在该环节可处理名单里（见 05 校验）
