# 级别缺失与"为什么没有级别"排查

> **本文档回答的问题**：现场经常问「这几个单为什么没有级别 / 没有 Severity / 没有 priority」。
> 这是**级别没算出来**，不是级别算错了 —— 属于「级别缺失」，与「级别判错」是两回事。
>
> 数据来源：`03_TT级别规则.md` 的规则结构与 `eflow_tt_severity_correction.xlsx` 的
> 1000 条回放结论，加上现场提问（2026-09-22 群内）。

## 一、先分清三种情况

级别相关的抱怨有三种，处理方式完全不同，**先确认是哪一种**：

| 现象 | 含义 | 看哪里 |
|---|---|---|
| **级别为空 / 没级别** | 没有任何 ttLevelRule 命中，字段是空值 | 本文档（下面第二、三节） |
| **级别是 P4（最低）** | 命中了兜底规则 #230，属于"有级别但被人质疑太低" | 见第四节 |
| **级别与预期不符** | 命中了规则，但和现场判断不一致 | 见 `03_TT级别规则.md` 的规则明细 |

> ⚠️ 最常见的误解：把「P4」当成「没级别」。
> P4 是**规则正常命中**的结果（兜底规则 #230），不是异常。

## 二、级别是怎么算出来的（决定了它为什么会缺失）

TT 自动创建时（`autoCreateTT` 步骤）按 `ttLevelRule` 匹配定级，**不是**取告警自带的严重度：

- **匹配顺序**：先按 `rulePriority` **升序**；同优先级内，**条件数多的（更特异的）先匹配**。
- **命中即停**：第一条命中的规则决定级别（P1~P4），后续规则不再评估。
- **级别来源是规则表**，告警的 `alarmSeverity`（Critical/Major…）**不参与**定级。

**这一点直接解释了现场最典型的疑问**：
> 「这些站点的告警为什么没有 Severity？」

因为 **TT 的级别来自 `ttLevelRule` 规则匹配，而不是从站点的告警严重度字段继承**。
站点告警上是否有 Severity，与 TT 单上是否有级别，是两条独立的链路 ——
TT 级别由「告警码 + 站点属性（vipSite / assetType / siteSubType）」组合决定。
所以站点告警"没有 Severity"并不必然导致 TT"没有级别"，反之亦然。

## 三、级别为空的四个真实原因（按现场出现频率）

### 原因 1：告警码不在任何级别规则的条件里（最常见）

所有级别规则的条件都锚定在**具体告警码**上，例如：

- 断站类：#227/#228/#229/#233/#244/#225 → 告警码限定在 `9970, 9980, 9990, 9910, 9920, 99933`
- 断小区类：#198/#199 → 告警码限定在 `9971, 9981, 9991, 199087342, 199083022, 198094419, 198094832`
- 特定告警：#234（高温）、#206/#207/#208/#209（MRNC 与其他专业）

**若告警码不在这份清单里，且不属于任何 MRNC 显式枚举，就没有规则能命中 → 级别为空。**

处理：拿告警码去 `TT单-告警码字典.md` 和 `03_TT级别规则.md` 比对；
确认是**新增告警码需要补级别规则**，走 `06_配置巡检与排障SOP.md` 的新告警接入检查单。

### 原因 2：站点属性为空，导致带站点条件的规则全部不匹配

多条规则带站点属性条件：

| 规则 | 依赖的属性 |
|---|---|
| #227 (P2) | `assetType = NORMAL` 且 `vipSite = 0` |
| #228 (P3) | `assetType = COOL` 且 `vipSite = 0` |
| #229 (P3) | `siteSubType = ERA` |
| #244 (P2) | `vipSite = 1` |

**若 `vipSite` / `assetType` / `siteSubType` 取值不是规则里写的那些（例如为空），
这些规则一条都不会命中。**

特别注意 `vipSite`：规则里写的是**字符串** `'0'` / `'1'`。
若实际值是空串或 `NULL`，既不等于 `'0'` 也不等于 `'1'`，
于是 #227/#228（要求 `=0`）和 #244/#226（要求 `=1`）**同时落空**。

已知的兜底行为：`site_type` 为空时，系统回退用 `site_information` 判断 ERA/REGULAR
（影响 #229/#230 的命中）—— 但**只覆盖这一项**，`vipSite` / `assetType` 为空没有兜底。

### 原因 3：兜底规则也要求 vipSite 有值

#230（TT-lowest severity → P4）是兜底规则，条件是 `vipSite in 0, 1`。
**它仍然要求 `vipSite` 是 `0` 或 `1`** —— 所以 `vipSite` 为空时，
连兜底规则都命中不了，级别就是**彻底为空**而不是 P4。

> 这正是「级别为空」和「级别是 P4」的分界线：
> 有 P4 = 兜底规则生效了（`vipSite` 有值，只是告警码没被任何 P1~P3 规则覆盖）；
> 空级别 = 连兜底都没生效（多为 `vipSite` 异常）。

### 原因 4：规则配置本身未启用 / 被改动

级别规则来自配置表，若某条规则被停用、优先级被调整，或新增告警码后**只加了告警字典、
没加级别规则**，也会出现空级别。这类要用 `06_配置巡检与排障SOP.md` 巡检。

## 四、关于「级别是 P4」的正确理解

收到 P4 不等于出问题。P4 有两条来源：

1. **正常低优先级**：#199（断小区）在 `vipSite = 0` 时就是 P4；
2. **兜底**：#230 `TT-lowest severity`，条件是 `vipSite in 0, 1`，
   在所有更特异的规则都没命中时兜底给 P4。

所以**看到 P4 应当先确认是哪条规则给的**（TT 分析回复里的「命中规则」字段会写明）。

## 五、怎么快速定位一个单的级别问题

在群里 @机器人 直接贴单号（TT 或 WO 都可以），例如：

```
@机器人 TT202609220120
```

回复里会包含：

- **级别**：`P4` 这类结论；
- **命中规则**：如 `#230 TT-lowest severity` —— **这是关键**，
  它直接告诉你是哪条规则定的级；
- **判定依据**：逐条列出该规则的条件求值结果，例如
  `vipSite=0 in 0,1 ✓; alarmCode=... ✓`

排查口诀：

| 回复里的现象 | 结论 |
|---|---|
| 级别为空 + 无命中规则 | 告警码不在规则清单，或 `vipSite` 等属性为空（原因 1/2） |
| 级别为空 + 兜底 #230 未命中 | 重点查 `vipSite` 是否为 `0`/`1`（原因 3） |
| 级别 P4 + 命中 #230 | **正常兜底**，不是故障；想提级需补更特异的规则 |
| 级别 P4 + 命中 #199 | 断小区 + `vipSite=0`，符合规则设计 |
| 级别与现场判断不符 | 规则本身的问题，看 `03_TT级别规则.md` 完整条件原文 |

## 六、需要补规则的判断标准

满足以下任一条，应认为**规则缺失**（而非数据问题），需走配置变更：

1. 告警码合法且已产生 TT 单，但不在任何级别规则的枚举里；
2. 该告警码在业务上应有明确优先级（不能一律兜底 P4）；
3. 站点属性（`vipSite`/`assetType`/`siteSubType`）取值正常，但规则条件覆盖不到。

> 注意：不要为了让「级别不为空」而放宽兜底规则 #230 —— 它去掉 `vipSite in 0,1`
> 会让大量本应暴露的数据问题被 P4 掩盖掉。**空级别是一个有价值的信号**，
> 说明这批单的站点属性或告警码需要人工确认。
