## 排查：TT202610280006 本地库查不到，走的是实时 PG（正常行为）

数据链路实测（三个环节，各自独立定时）：

1. eFlow → PG：my_app 任务 `eflow_sync`（delta），cron `0 * * * *`，每次约 4min。
2. PG → 本地 app.db：`pg_to_sqlite_sync`，cron `45 */12 * * *`（每天 00:45 / 12:45），
   全表 DROP+CREATE 重建，单次 640~1020s（app.db 1.5GB / 112 表 / 4.8M 行）。
3. 机器人单票查询：HTTP(PG) 优先 → 本地 SQLite → eFlow 实时兜底（src/tt.js analyzeTt）。

本例时间线：告警 00:10:10、TT 建于 00:25:55 → 01:00 的 eflow_sync 才进 PG
→ 而 00:45 的 SQLite 快照早于它，故本地副本停在 TT202610280002(created 00:13:08)。
09:11 提问命中 HTTP 路径，输出 `[live] served from the live database`。
下次本地刷新 12:45（约 12:57 完成）。

结论：不是故障。SQLite 副本只是 my_app 挂掉时的降级通道，正常路径永远读 PG。
若要让副本滞后从 12h 收窄，建议**只做 eflow_tt 增量同步**（按 created_time 水位，
每 15min 一次，代价秒级），不要把整库快照改成每小时（每次 10~17min，太重）。

## 已实施：单票取数顺序改为 PG → eFlow 实时 → 本地副本（用户要求）

改 `src/tt.js` 的 `analyzeTt`：

1. ① PG（HTTP）命中即回；未命中分 `pgMiss='notfound'|'error'`。
2. ② PG 没给答案 → **直接 eFlow 实时**（`tryLive`），副本不再插队。
   - `hit:'no'` → 直接回 `liveMiss(tt, F.srcPg)`，**不再扫副本**（副本更旧）。
   - `hit:'unavailable'` → 记 `liveFail`，继续 ③。
3. ③ 本地 SQLite 副本 = 最后兜底；`httpOn` 时命中**打 `[stale]` 标记**。
4. `ttAnalysisHttp=false` 保持老顺序 ①→③→② 且不打标记（部署开关不能被悄悄改语义）。
5. 「查无此单」不再重试（重试只针对超时/瞬时读不到）。

**顺带修掉的既有 bug**：`tryLive` 把 `err && !out` 一律判成 `unavailable`，
而 `eflow-live-tt.py` 用**退出码 1** 表示「eFlow 确实没这单」→ 结论被说成「查询出错了」。
现按 `err.code === 1` 识别为 `hit:'no'`。

文案（`FAIL_TEXT`）：新增 `srcPg` / `srcLocal` / `stale`；`goingLive` 改为

### ② 24~58s 慢回复 —— 逐跳计时 + 两个真 bug

给 `analyzeTt` 加了 `timing`（`src/pg/render/live/total`），经 `tools.js` 的
`stats.ttTiming` 传到 `whatsapp.js`，打进 `[回复]` 行：`pg(取行:184/渲染:868) 1053ms`。

实测（空闲，本机）：
- PG 命中 **热 1.0s**（取行 ~180ms + 渲染 ~850ms）；
- PG 命中 **冷启动首单 9.1s**（渲染 8913ms）—— 大头是 Python + openpyxl 首次加载，
  同进程紧接着第二单 0.8s。所以「第一单慢」是冷启动，不是查库慢；
- eFlow 实时兜底 **8.4s**（PG 没有这单时才会走）。

查到的两个真 bug：
1. `data/tt-index.json` 被写成 **1 条**（`{TT202610280006:1}`，锚点 `[1,...]` 全错），
   之后每次查询都「锚点抽查不通过 → 索引作废 → 全表直查」，作废日志刷到 595 行。
   → `npm run tt-index` 重建（0.2s，54873 个单号）；并在 `tt-analyze.py` 加自保：
   重建结果不足旧索引 20% 时**拒绝落盘**且 `mapping={}`+`suspect=True`（退回全表直查），
   避免残缺映射把「有这单」答成「查无此单」。
2. 09:10 那 57.8s 与 my_app 的 7 个并发任务窗口（09:10:13~09:11:11，
   `cxo_dashboard_cache_sync` 58.05s 等）完全重合 —— 主机争用放大了冷启动那一跳。
