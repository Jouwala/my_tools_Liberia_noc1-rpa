# WhatsApp 群知识库助手

在已有的 WhatsApp 群里放一个机器人，群成员 **@它 + 提问**，它就基于你的本地知识库回答。

全程本地运行：嵌入、检索、生成都在你自己的 Ollama 上，资料不出本机。

---

## ⚠️ 先读这一段：风险与前提

**这个方案用的是非官方库（Baileys），违反 WhatsApp 服务条款，号码有被封的风险。**

这不是危言耸听，是选型时必须接受的代价。原因是 Meta 的官方接口**做不到这件事**：

| 方案 | 能否进「已有的群」 | 群里 @它 能收到吗 | 合规性 | 成本 |
|---|---|---|---|---|
| **官方 WhatsApp Business Cloud API** | ❌ 不行 | ❌ | ✅ 合规 | 按条计费，需 OBA 认证 |
| **官方 Groups API（2026 新增）** | ❌ 只能建自己的群，上限 8 人 | ⚠️ 仅限自建群 | ✅ 合规 | 按条计费 |
| **Baileys（本方案）** | ✅ 可以 | ✅ 可以 | ❌ 违反 ToS | 免费 |

关键事实：官方 Groups API 虽然 2026 年上线了，但**每个群最多 8 人**，且只能由商家自己创建、成员凭邀请链接加入——**你无法让它进入一个已经存在的群**。所以「在现有群里 @助手」这个需求，官方路线在能力上就不成立。

**降低风险的做法（不能消除，只能降低）：**

1. **用一个副号，不要用你的主号。** 这是最重要的一条。
2. 新号先「养」1–2 周再加机器人，别一注册就上自动化。
3. 只做**被动响应**（被 @ 才回），绝不主动群发。本方案默认就是这个行为。
4. 保持回复简短、频率低。配置里 `cooldownMs` 默认 4 秒，就是干这个的。
5. 社区经验值：单号自动化发送量远低于每天 1000–2000 条。WhatsApp 官方从未公布阈值，民间经验只能降低而非消除风险。

**如果你的场景能接受「一对一群发」而不是「群里协作」**，那应该改用官方 Cloud API，本方案不适用。

## 架构

```
WhatsApp 群
    │  用户 @机器人 + 提问
    ▼
Baileys 客户端（Node.js，扫码登录，作为「已关联的设备」）
    │  识别 @提及 → 抽取问题
    ▼
工具路由（src/tools.js）—— 先判断「查数据」还是「查资料」
    │
    ├─ ① 带 TT/WO 单号 ───────────► 单票通道（src/tt.js）
    │      查这一单的详情 + 级别判定依据（答案在库里，不在语料里）
    │
    ├─ ② 区间统计 ─────────────────► 工单统计通道（src/ttquery.js）
    │      「今天有几个 P1」「昨天未闭环多少单」「X 站昨天几单」
    │      HTTP 优先：my_app /api/tt-wo-dashboard（PG 实时）
    │      降级兜底：scripts/tt-query.py 读本地 SQLite 副本
    │      ← 数字全部由脚本渲染，模型不参与
    │
    └─ ③ 其余 ─────────────────────► RAG 知识库检索
           bge-m3 嵌入问题 ───────► 本地 Ollama /api/embed   ← 资料不出本机
           与知识库向量做余弦相似度
           叠加字符 bigram 字面重合度（混合检索）
           命中判定：top1 ≥ minAbs 且 (top1 − 中位数) ≥ minGap
           ├─ 命中 → 组装上下文 ──► 对话模型（本地 Ollama 或云端 OpenAI 兼容接口）
           └─ 未命中 → 直接回「知识库里没有」
    ▼
回复到群里（引用提问者消息）
```

只有「你的问题 + 命中的片段」会离开本机（且仅在你选择云端对话模型时）。

### 工具路由怎么决定走哪条通道

路由分两层，**规则先行、模型兜后**：

| 层 | 做什么 | 为什么 |
| --- | --- | --- |
| 规则层 | 正则抽单号、日期、级别、闭环状态 | 模型不知道今天几号，问它「今天」只能得到瞎猜；日期错了后面查得再准也是错的答案。规则能定的就不花模型调用，顺带省一次往返延迟 |
| 模型层 | 规则抽不准时（尤其**站点名**），让模型返回 `{tool, args}` | 站名是开放集合（`Wood camp`、`Qcell R.I.A`、纯站号都有），正则猜边界必然误伤 |

两条硬规矩：

1. **数字由脚本渲染，模型不参与。** 群里同事会把机器人的话当依据去派单催单，
   模型一旦自由发挥，「0」可能被说成「有几个」——那是编造。
2. **答错不如弃权。** 规则层剥掉日期/级别/数量词后若还剩解释不了的专名
   （`leftoverTerms`），说明有额外条件，此时主动交给模型层，
   而不是带着空参数硬答一个偏大的数。

> 2026-10-07 实测踩坑：「Wood camp 这个站**昨天**有几个单」被规则层短路，
> 带着 `site:''` 答成了**全网 94 单**。答错而不报错，是最危险的一类。
> 现在规则层遇到残余专名会弃权，且日期由规则层解析后**注入**给模型，
> 保证「弃权」不会连带丢掉日期。

## 快速开始

### 0. 前置条件

- Node.js ≥ 20（本机 22.22.2 已验证）
- Ollama 正在运行，且已拉取嵌入模型：
  ```bash
  ollama pull bge-m3
  ```
  只需嵌入模型。对话模型可走本地（再 `ollama pull qwen3:4b-instruct`），
  也可走云端（见下方 provider 配置）。
- 若用云端对话模型：一个 API Key（当前配置指向 Agnes AI，免费）

### 1. 装依赖

```bash
npm install
```

只装两个包：`baileys`（WhatsApp 协议）和 `qrcode-terminal`（终端显示二维码）。
**没有引入任何向量数据库或 Ollama SDK** —— 向量检索是纯 JS 实现的余弦相似度，Ollama 走原生 fetch。索引规模在几千块以内时，这比引入 Chroma/Qdrant 更简单，也更快。

### 2. 放你的资料

把你的文档（`.md` / `.txt`，支持多层子目录）放进 `knowledge/`：

```
knowledge/
├── 产品手册.md
├── 内部规范/
│   ├── 报销制度.md
│   └── 考勤说明.txt
└── FAQ.md
```

仓库自带三份示例语料，可以先跑通再替换。

### 3. 建索引

```bash
npm run ingest
```

输出示例（本机实测）：

```
[2/4] 扫描知识库…
  · knowledge/01_告警到TT到指派_端到端链路总览.md  →  15 块（3169 字符）
  · knowledge/02_告警衍生规则.md  →  51 块（13567 字符）
  · knowledge/03_TT级别规则.md  →  32 块（10094 字符）
  · knowledge/04_TT指派与推单规则.md  →  51 块（14614 字符）
  · knowledge/05_指派一致性校验.md  →  14 块（3436 字符）
  · knowledge/06_配置巡检与排障SOP.md  →  9 块（1767 字符）
  · knowledge/07_iMind-eFlow-Function-Operation-Guide.md  →  421 块（100527 字符）
  · knowledge/TT单-告警压缩规则.md  →  110 块（23516 字符）
  · knowledge/TT单-告警码字典.md  →  107 块（11582 字符）
  合计 9 个文件 / 810 个知识块
[3/4] 生成向量（bge-m3:latest）…
  ✓ 810 条向量，维度 1024，耗时 31.3s
    平均 39 ms/块
```

**每次改完资料都要重跑这一步**，否则机器人还在用旧索引。

> ⚠️ **而且必须重启进程。** 索引是**进程启动时一次性读进内存**的，
> 之后无论 `index.json` 怎么更新，跑着的进程都还在用内存里那份旧快照。
> 2026-09-15 踩过这个坑：索引 15:22 就重建好了（249 块），
> 但进程是 14:42 启动的，群里提问一直按旧的 10 块占位内容检索，
> 表现是「资料明明放进去了，机器人还是说没有依据」，排查了半天。
>
> **正确顺序：改资料 → `npm run ingest` → 重启进程。**

### 4. 校准命中阈值（重要，别跳过）

这一步决定机器人**能不能正确说出「我不知道」**。跳过的话大概率会变成「什么问题都硬答」。

```bash
node scripts/calibrate.mjs \
  --label hit  "年假有几天" \
  --label hit  "报销多久能到账" \
  --label hit  "接口限流是多少" \
  --label miss "今天北京天气怎么样" \
  --label miss "帮我写一首关于春天的诗" \
  --label miss "推荐几家深圳的火锅店"
```

用你**自己的资料**出题：5–8 条「资料里明确有答案的」+ 5–8 条「资料里绝对没有的」。

脚本会分别评估两个判据的判别力，输出建议阈值。本机实测结果：

```
单信号判别力：
  top1  命中下界 0.4760 ｜ 未命中上界 0.3779 ｜ 间隔 0.0981  ✓ 可单独依赖
        最优阈值 0.4270（两侧余量各 0.0490）
  gap   命中下界 0.0922 ｜ 未命中上界 0.0859 ｜ 间隔 0.0063  ! 间隔过窄，不可单独依赖

结论：
  主判据 = top1 → minAbs = 0.427
  次判据 gap 间隔过窄，退化为兜底下限 → minGap = 0.046
  回测：14/14 正确（100.0%）
```

把建议值写回 `config.json`。

### 5. 启动

```bash
npm start
```

终端会打印一个二维码：

1. 手机 WhatsApp → **设置 → 已关联的设备 → 关联设备**
2. 扫码
3. 凭据存到 `data/auth/`，之后不用再扫

然后把机器人拉进群，在群里发：

```
@机器人 年假有几天？
```

### 6. 先测 ping，再问问题

群里 @机器人 发 `ping`，应当立刻收到：

```
pong ✅ 机器人在线
知识库：10 块 / 3 个文件
对话模型：[openai] agnes-3.0-flash
嵌入模型：bge-m3:latest（本地）
对话走云端，本地无模型互挤，响应通常 1–3 秒
```

**这个顺序很重要**：`ping` 走的是「@到了 + 能回消息」这条链路，不碰检索。
- `ping` 有回应、提问没回应 → 故障在检索侧（看 `ask --debug`）
- `ping` 也没回应 → 故障在传输层（看日志里的 `[未匹配]` 诊断）

另有 `help` 命令，返回一段给群成员看的用法说明。

> 首次登录后 WhatsApp 会先断开一次（日志里 `code=515`）再重连，**这是正常的配对流程**，不是故障。

## 配置说明（`config.json`）

### 对话模型 provider

对话模型可以走本地，也可以走任意 OpenAI 兼容的云端接口。**嵌入始终在本地**——这是刻意的：
资料向量化不出本机，只有「你的问题 + 命中的片段」会离开。

| `chatProvider` | 说明 |
|---|---|
| `ollama` | 全本地，离线可用。首次响应 8–12 秒（受本地模型重载影响） |
| `openai` | 任意 OpenAI 兼容接口。首次响应 1–3 秒 |

当前配置指向 **Agnes AI**（新加坡 Sapiens AI，OpenAI 兼容，当前免费）：

```json
"chatProvider": "openai",
"chatModel": "agnes-3.0-flash",
"chatBaseUrl": "https://apihub.agnes-ai.com/v1",
"chatApiKeyEnv": "AGNES_API_KEY"
```

**密钥必须通过环境变量提供**，不要写进 `config.json`（那个文件容易被误提交）：

```bash
# Bash / Git Bash
export AGNES_API_KEY="你的key"
npm start

# PowerShell
$env:AGNES_API_KEY="你的key"
npm start

# 或写进项目根目录的 .env（npm start 会自动加载）
echo 'AGNES_API_KEY=你的key' > .env
```

启动时会**先校验密钥并真实调用一次**，密钥错、模型名错、被限流都会在启动阶段就报出来，
不会等到群里有人提问才发现：

```
✓ 对话 provider：openai 兼容接口（密钥来源：环境变量 AGNES_API_KEY）
  ✓ 连通性正常：agnes-3.0-flash 响应正常（812ms）：ok
```

## 命中判定为什么要用「相对基线差值」

这是本方案最容易被做错的地方。

稠密嵌入模型对中文的余弦相似度被压缩在一个很窄的高位区间：**完全无关的问题，top1 也有 0.33–0.40**。所以如果你把阈值设成 0.42 这种「看起来合理」的值，无关问题会全部通过，机器人就变成了「什么都敢答」。

本方案对每个查询额外算一个**自适应基线**：

```
baseline = 该查询与全库相似度的中位数   ← 代表"这个查询对这批语料的泛化水位"
gap      = top1 − baseline

命中 ⟺ top1 ≥ minAbs 且 gap ≥ minGap
```

`gap` 是逐查询归一化的量，比绝对阈值稳定得多——换模型、换语料时它比 `minAbs` 更不容易失效。

**但要注意：`gap` 的判别力取决于语料。** 本机实测发现，语料同质化高（都是公司文档）时，所有查询的基线水位都偏高，`gap` 被压平到只有 0.0063 的间隔，几乎不具判别力，此时**起决定作用的是 `minAbs`**。所以校准脚本会分别评估两个信号，谁余量大谁做主判据，另一个退化为兜底下限。

**条目数少于 10 块时，`gap` 尤其不可信**，建议先补充语料再校准。

### 精确 ID 查询的盲区（`idBonus`）

「告警码 `198094422` 会被压缩成什么」这类问题，纯向量检索答不对——**正确答案压根进不了 topK**。

原因是语料里存在大量结构高度同质的块：

```
- 规则 101 → 压缩后的父告警码是 9970（4G site down）
- 规则 102 → 压缩后的父告警码是 9980（4G cell down）
...
```

它们只差几个数字，嵌入向量几乎重合。查询问的是「哪个数字」，而语义相似度对数字不敏感。
`lexicalWeight` 只有 0.22 的字符 bigram 权重，压不过这种同质化带来的语义噪声。

修法是给**字面精确命中**额外加分：

```
查询里出现 ≥4 位数字（告警码 / 单号）
且候选块原文包含该数字  →  base += idBonus（默认 0.15）
```

这个加权只在「查询里确实有长数字」时激活，对普通自然语言问题零影响。
`idBonus: 0` 可关闭；用 `ID_BONUS` 环境变量可临时试值。

> 顺带一提：同质化还会让**分块边界**变成陷阱。早期版本把「标题 + 说明 + 首条记录」合并成一块，
> 首条记录被挤到块尾甚至截断（块尾是 `Site break alarm code(siteA` 这种半截串）。

## 性能调优（本机实测数据）

### 实测延迟

| 场景 | 耗时 |
|---|---|
| 嵌入（bge-m3 已加载） | 80–130 ms |
| 嵌入（被卸载后重载） | **3700–4200 ms** |
| 检索 + 命中判定（纯内存） | < 5 ms |
| 本地对话生成（qwen3:4b-instruct，约 500 token 上下文） | 210–2100 ms |
| **完整回答（本地对话 + 模型都在内存）** | **约 1 秒** |
| **完整回答（本地对话 + 模型需重载）** | **约 8–12 秒** |
| **完整回答（云端对话 + 本地嵌入）** | **约 1–3 秒** |

### 本地对话时的瓶颈：Ollama 默认只常驻一个模型

**`OLLAMA_MAX_LOADED_MODELS` 默认为 1。** 本机（31.7GB 内存，i7-14700，无独立显卡）实测：
加载对话模型会把嵌入模型踢出内存，下次提问又要重新加载，每次多花 3–5 秒。

启动时会自检并提示：

```
! 本地两个模型无法同时常驻 —— 每次提问都要重载模型，实测每次多花 3~5 秒
  已常驻：qwen3:4b-instruct
  修复：给 Ollama 服务设置环境变量 OLLAMA_MAX_LOADED_MODELS=2 后重启 Ollama
```

算一下内存：`qwen3:4b-instruct ≈ 3.25GB` + `bge-m3 ≈ 1.16GB` ≈ **4.4GB**。
只要空闲内存够，设 `OLLAMA_MAX_LOADED_MODELS=2` 并**重启 Ollama** 即可消除这个开销。

### 换云端对话模型后这个问题就消失了

对话走云端时，本地只需要常驻嵌入模型，**不存在模型互相挤占**。
启动日志会直接确认这一点：

```
✓ 对话走云端，本地仅需嵌入模型（1.16 GB），无模型互挤问题
```

这也正是换用 Agnes 3.0 Flash 的收益之一——除了 252.7 token/s 的输出速度，
还顺手消掉了本地最贵的那段延迟。

### 其他可调项

- `topK` 从 4 降到 2：减少提示词长度，生成更快，但可能漏掉细节。
- 换更小的嵌入模型（如 `nomic-embed-text`，274MB）：重载更快，但**必须重新校准阈值**。
- 机器人内部对提问做了**串行队列**，避免多人同时提问把本地 CPU 打满。
  并发高时会排队，超过 `maxQueue` 会直接回提示。

## TT / WO 单分析（实时查工单库）

除了知识库问答，机器人还能**实时分析工单**。群里 @机器人 并带上单号即可：

```
@机器人 分析TT单TT202609150073
@机器人 WO202609220055 Please analyze this Work Order.
```

**TT 和 WO 单号都支持。** WO 号会自动回溯到它的父 TT 单再分析（工单库里
`eflow_tt.wo_no` 列可反查），回复格式与直接查 TT 一致。

> ⚠️ **WO 曾是个静默错误**：早期正则只认 `TT\d{6,}`，`WO202609220055` 抽不出来
> → 落到知识库通道 → 模型看到 `WO` 前缀把它当成 **PCT 专利文献号**，
> 一本正经地回答「资料里没有该专利的技术内容」。是**自信的跨领域错误答案**，
> 比"查不到"危险得多。现在 `TT_RE = /\b(?:TT|WO)\d{6,}\b/gi`。
> 回归测试见 `scripts/test-tt-extract.mjs`。

机器人会去 my_app 的工单库查这一单，套用 eFlow 的 TT 级别规则，回出：

### 为什么走独立通道而不是知识库

知识库适合回答「规则是什么」（静态知识），但「这一单现在什么情况」的答案在库里、且随时在变。
把工单快照塞进知识库只会得到过期数据，所以单号查询走**实时查库**。

> 同一个道理也适用于**区间统计**（「今天有几个 P1」）——见下一节。
> 那是 2026-10-06 补上的第三条通道。

## 工单统计（「今天有几个 P1」）

### 为什么需要单独一条通道

2026-10-06 群里的真实提问：

```
@~olbr_assistant 今天有p1的单子吗
```

机器人回了知识库里 P1 规则（ID 225 / 226）的**定义**，并说「资料里没有实际工单数据」。

它没有答错——知识库里确实没有实际工单数据。**是路由错了**：
这句话被整句塞进向量检索，而它问的是**事实**，不是**规则**。
这类问题的答案在数据里，无论在知识库里放多少文档都答不出来。

所以判断标准很简单：

| 问法 | 通道 | 例子 |
| --- | --- | --- |
| 规则是什么 | 知识库 | 「P1 是什么级别」「告警码 198094422 会被压缩成什么」 |
| 这一单什么情况 | 单票通道 | 「分析 TT202610060087」 |
| **有几个 / 有没有** | **统计通道** | 「今天有p1的单子吗」「昨天未闭环多少单」 |

前两者只差几个字，判反了就完全答错，而且看起来都"跑通了"。
分流判断的回归测试在 `scripts/test-tools.mjs`。

### 两条数据源：HTTP 优先，SQLite 降级

| 通道 | 来源 | 口径 | 何时用 |
| --- | --- | --- | --- |
| 主 | my_app `/api/tt-wo-dashboard/overview` | 生产库 **PostgreSQL**，实时 | 默认 |
| 降级 | `scripts/tt-query.py` 读 `my_app/db/app.db` | SQLite **同步副本**，有延迟 | my_app 没起 / HTTP 超时 / 按站点过滤 |

**降级时必须如实标注口径**，回复里会带一句「（本地副本口径，可能有同步延迟）」。
实测同一天同一口径两边会差几单（2026-10-06：PG 侧 94 单，本地副本按
`alarm_occur_time` 只有 82 单）——差几单是正常的，**不说是错的**。

为什么必须有降级：`src/tt.js:9` 写过「之所以不用 HTTP 接口，那要求 my_app 服务在跑」。
机器人要保持独立可用，my_app 挂了也得能答，只是答得旧一点。

> **站点过滤只有降级通道支持**：`overview` 接口要 JOIN 站点表才能按站名过滤，
> 参数走的是 `adv` JSON（白名单见 `tt_wo_dashboard.py:69`），
> 对"群里随口说个站名"这种用法太重。所以带站名的提问直接走本地库
> （那里 `site_name` / `site_id` 能做模糊匹配）。

### 时间字段统一用 `alarm_occur_time`

两条通道都按 `alarm_occur_time` 过滤，因为 my_app 的 `_time_filter`
（`backend/routers/tt_wo_dashboard.py:92`）用的就是它。

**两条通道若各用一个时间字段，同一个问题会得到两个不同的数** ——
那是最难排查的一类故障：两边都"能跑"，只是数对不上
（实测 2026-10-06 按 `created_time` 是 87 单，按 `alarm_occur_time` 是 82 单）。

### 要单号名单时才会去下钻

「本月有几个 P1」只要个数，「…**请输出TT单的ID给我**」要的是名单。
两者取数代价差很多，所以分开处理：

| 问法 | 走哪个接口 | 代价 |
| --- | --- | --- |
| 不限级别，只要总数（「昨天一共多少单」） | `/overview` | 轻量聚合 |
| 指定级别，或点名要单号 | `/drilldown` | 把符合条件**全部**行捞回来，本地截断 |

判据是 `parseListIntent`（见 `ttquery.js`）。踩过的坑：

- **漏判**：用户说「请输出TT单的ID给我」，只回了「P1 单 6 个」——要 ID 却一个没给。
- **两条通道给出不同长度的名单**：HTTP 侧内部按 `ttStatsSampleLimit`(3) 截断，
  渲染层却想展示 `ttStatsListLimit`(10) 条，切不出来；而降级侧按 10 取了 6 条。
  同一个问题两条通道结果不一致，是最难排查的一类。现在两侧都按**两者中的较大值**取。
- **站名显示成裸站号**：`/drilldown` **不返回 `site_name`**（只有 `site_id`），
  于是回复里出现 `TT202610020060（5021）` —— 群里没人认得出 5021 是哪个站。
  现在回本地表按 `tt_no` 补真值（见下）。

### 问单号名单时，未闭环的会就地标出来

```
问：本月有几个P1的单子，请输出TT单的ID给我
答：2026-10-01 ~ 2026-10-07 P1 单 6 个
    其中未闭环 1 个
    单号：TT202610020060（Cooper Hill）、TT202610020035（Cooper Hill）、
          TT202610020013（SKD boulevard 3）、TT202610020012（LBS）［未闭环］、
          TT202610010038（Morris Farm）、TT202610010015（LAWA 2）
```

**为什么每条后面缀一个状态**：第一版只说了「其中未闭环 1 个」，
用户立刻追问「那个单子未闭环」——名单都打出来了，状态却藏着。

只在**混合状态**时才逐条标：全部未闭环（或全部已闭环）时每行都缀同一个词是噪声，
上面那句「其中未闭环 N 个」已经把话说尽了。

### 追问：「那个单子未闭环」

实测第二问曾被答成「今天全网 36 单」——**答的是另一个问题，而且不报错**。

原因：这句话单看没有主语——没有日期、没有级别、没有站点。
规则层抽不出东西，模型层也只能猜，于是兜底成「今天」。

修法是把**会话历史**接进来（`whatsapp.js` 按 `chatJid` 存最近 5 轮）：

- 路由时把最近几轮喂给模型，让它把上一轮的日期/级别/站点**照抄**过来；
- 知识库通道同样受益：`rag.js` 里 `resolveFollowUp` 早就写好了，
  但**一直没人调用**——没有 `history` 传进来，是段死代码。现在接上了。

现在「那个单子未闭环」会落到 `TT202610020012 · LBS`，正是上一轮标了
［未闭环］的那一单。

> 答不上来的轮次**不进历史**：「资料里没有」留在上下文里，
> 只会把下一轮也带偏。

### 日期是猜的时候，必须说

谁都没给日期时（追问没带日期、模型也没抄到），会兜底成**今天**，
此时回复末尾加一句「（提问里没给日期，按今天算的）」。
**猜的日期不能装成用户给的** —— 否则用户会以为查的就是他要的那天。

### 站名为什么回本地表补，而不是从 title 里抠

第一版是在 HTTP 通道里用正则从 `title`（格式 `<站号>.[<站名>]<告警名>`）
抠站名。实测这个做法**有静默失效面**：

| 口径 | 覆盖 |
| --- | --- |
| `title` 里没有方括号的行 | **241 / 37223**（抠不出站名） |
| 本地 `eflow_tt.site_name` 为空的行 | **0 / 37223** |

也就是说 0.65% 的单子会显示成 `TT2026...（5021）`——**不报错，只是悄悄退化**。
而 `eflow_tt` 表里本来就有 `site_name` 这一列，且 `tt_no` 是主键。

所以改成：**计数走 HTTP（PG 实时），站名回本地表按单号点查补齐**
（`tt-query.py --site-names`）。代价是每列一次名单多约 1 秒（起一次 Python），
且**只在真的要显示单号时才付**——`overview` 那条路径仍是 ~70ms。

补不到就退回站号：站名只是展示字段，不能因为它让整个查询失败。

### 工作原理

`scripts/tt-analyze.py`（纯 Python，只依赖标准库 + openpyxl）：

1. 只读打开 `Y:/Task/my_app/db/app.db` 的 `eflow_tt` 表，按 `tt_no` 取这一单；
2. 读 `eflow_TT_rules.xlsx`，解析每条规则的条件表达式；
3. 按优先级从小到大匹配，第一条命中即判定级别（与规则一致 / 建议调整 / 无法判定）。

匹配逻辑**精确复刻** my_app 的 `eflow_rules_matcher.py`（该模块依赖 pandas，
本机未安装，故用纯 Python 重写，口径保持一致）。

### 回复里包含什么

TT 单的回复是**脚本直接渲染、不过 LLM** 的（`src/answer.js` 里 TT 通道 `text: r.text` 原样返回）——
要的是「这一单现在什么情况」的**事实**，不是模型润色过的转述。

```
TT202609160068 · Wood camp（4406）｜Montserrado｜站点类型 NORMAL｜站点子类型 REGULAR
标题：4406.[Wood camp]3G CELL DOWN
告警：9991（Critical）｜RAN｜Communication Alarm
告警对象：Wood camp｜10.17.75.163/129.0.1.1｜Cell is out of service
影响：3G 中断｜站点退服｜断站 1｜VIP No
级别：P4（与规则一致，正常）
命中规则：#199 无线断小区级别重定义-P4
判定依据：alarmCode=9991 in 9971,9981,9991,... ✓; vipSite=0 = 0 ✓

【处理链路】
1. 创建  2026-9-16 08:51:07  assign_rule(assign_rule) → #164 TT单直接派FO accept
2. FO 受理  2026-9-16 08:51:08  FE Robot(fe_robot) → 派 P:FE Robot(fe_robot)
3. FO 处理  2026-9-16 08:51:09  FE Robot(fe_robot) → 派 G:ZTE_NOC_FO(ZTE_NOC_FO)
当前环节：FOProcess(WO Dispatched FE Handling)
处理方 G:ZTE_NOC_FO

【派单依据】
创建：#164 TT单直接派FO accept（autoDispatch·P3） → 走 FO（无条件，兜底默认）
派单：#204 小区故障派ZTE WO（FOAccept·P2） → ZTE_NOC_FO
命中条件：alarmCode=9991 in 9971/9981 等 7 个

【时效】
SLA：未超期（Within SLA）｜时长 2d0h0m｜截止 2026-09-18 08:35:42｜剩余 1d22h3m
故障：时长 0d1h57m｜发生 2026-09-16 08:35:42｜未恢复
数据同步：2026-09-16 10:38:23
```

**抬头怎么拼。** `单号 · 站点(站号)｜区域｜站点类型｜站点子类型`。后两项分别取
`site_type` / `site_information` 两列，**归一化后**才显示（`site_type` → `NORMAL` / `COOL`，
`site_information` → `REGULAR` / `ERA`）—— DB 里混着 `REGULAR（Normal)` 这类脏值，
直接端出去不好看。哪一列为空就省掉那一段，不留下空标签。
（原先这里显示的是「站点等级 P2」，按需求已替换。）

**链路从哪来。** `eflow_tt` 有一组 `*_detail` 列，每列存一段操作流水原文：

```
Operation Step:FO Process. Operation Result:8. Operation Time:2026-9-11 03:14:09.
Operator:FE Robot(fe_robot). Operator Group:G:ZTE_FE_FE(ZTE_FE_FE).
Next Status:Waiting for FO Process. Assign To:G:ZTE_NOC_FO(ZTE_NOC_FO). ...
```

`_chain_steps()` 把它解析成结构化步骤，按官方口径排序（与
`knowledge/01_告警到TT到指派_端到端链路总览.md` 一致）：

```
创建 → FO 受理 / BO 受理 → FO 处理 / BO 处理 → [第三方受理 → 第三方处理] → 确认 → 关单
```

只显示**实际发生过**的步骤 —— 没走过的环节 detail 列为空，自然跳过。
所以一张单子可能只有 3 步，也可能 9 步全有。

**「派给谁」有两个来源，互相印证**：链路里每次操作的 `Assign To`（这一步派给了谁）
和 `current_handler`（当前落在谁手里）。

> 注意 `current_handler` 是**当前**处理人，不是「派单当时派给了谁」。
> 中转组（如 `3rd_Power`）会把单子再转出去，所以拿它跟规则的目标比会误判
> —— 实测一致率只有 61%。判断派单是否对得上，要比**触发那一步的 `Assign To`**。

### 派单依据：从「派给了谁」到「依据哪条规则」

工单库里**不记录命中了哪条派单规则**，只能反推：

| 位置 | 实际内容 |
|---|---|
| `eflow_tt.creator` | 写死 `assign_rule` |
| `create_detail` 的 `Operator` | 只有 `assign_rule(assign_rule)` |
| 有没有 rule_id 列 | **没有** |

所以「具体哪个规则」是拿**推单规则表**（`eflow_push_rules.xlsx`，由 my_app 的
`eflow_Push_Rule_Collector.py` 导出）逐条比对本单字段反推出来的。

规则分两个阶段，各管一件事：

| 阶段 | 规则类型 | 触发步骤 | 决定什么 |
|---|---|---|---|
| 一 | `ttDispatchRule` | `autoDispatch` | 创建时走 **FO** 还是 **BO** |
| 二 | `ttPushOrderRule` | `FOAccept` / `BOAccept` / … | 派给**哪个组** |

**条件命中只是必要条件，不充分** —— 所以每阶段都要过三道：

1. **条件命中**（`build_rule_match`）；
2. **触发步骤本单真的走到过**（`_TRIGGER_TO_STEP`）——
   `FOAccept` 的规则不会套到只走 BO 的单上；
3. **规则的 `目标处理人` 真的落在本单派单链路上** —— 这条最关键，
   它是**工单现场**的事实（`Assign To` / `current_handler`），与规则表无关，不会自证。

阶段二还分三档可信度（规则表的 `状态` 列明显滞后）：

| `tier` | 含义 | 措辞 |
|---|---|---|
| `active` | 启用的规则命中且目标落在链路上 | 直接给规则名 |
| `stopped` | 没有启用的规则说得通，但**停用**的规则说得通（如 #201） | 给规则名 + 标注「规则表快照里状态为 STOP，可能已停用或快照滞后」 |
| `none` | 都不成立 | 「未匹配到推单规则（可能由人工派单或默认流程决定）」，**不硬猜** |

> **为什么停用的规则也要留着用**：实测 500 张单里有 **75 张（15%）**只能靠
> `状态=STOP` 的规则解释（典型是 #201「Regular断站故障手动到FO」，
> 它的目标 `ZTE_NOC_FO` 真的出现在这些单的派单链路上）。
> 直接丢弃会让这批单误报成「无匹配规则」。

**准确率（500 张单实测）**：

| 指标 | 结果 |
|---|---|
| 确认项「规则目标 == 触发时实际指派」一致率 | **496 / 496 = 100%** |
| 整体可解释率 | **99.2%**（4 张 `alarmCode=762103` 的单规则表里根本没引用过） |

**⚠️ 已知的坑：`siteSubType` 与 `assetType` 是两个不同的字段，别合并。**

曾经（照抄 my_app 的 `eflow_rules_matcher.build_value_frame`）两者都取 `site_type`，
注释写的是「目前 DB 只有 site_type 一列承载资产类型」—— **那是错的**：

| 规则里的字段 | 实际 DB 列 | 值域 | 规则表里用过的值 |
|---|---|---|---|
| `assetType` | `site_type` | `NORMAL` / `COOL` | 只用过 NORMAL / COOL |
| `siteSubType` | `site_information` | `REGULAR` / `ERA` | 只用过 REGULAR / ERA |

三路取证：① 两张规则表里两个字段的**值域完全不重叠**；
② DB 交叉表显示是两列（`NORMAL×REGULAR` 24664、`None×ERA` 6607、`COOL×REGULAR` 3003）；
③ `eflow_data_mapper.py:304` 写着 `"assetType": "site_type"`，且 `TT_FIELDS` 里没有 siteSubType。

合并的后果：**`siteSubType='REGULAR'` 的规则永远不可能命中**
（REGULAR 站点的 `site_type` 是 NORMAL/COOL，取不到 `REGULAR`），
典型受害规则是 #200「Regular电源故障推送TT到IPT」—— 大批单子被误判成「无匹配规则」。
ERA 站点因为 `site_type` 为空、回退到 `site_information` 拿到 `ERA` 而**歪打正着**，
所以这个 bug 一直没暴露。修正后 `assetType` 的取值**没变**（仍来自 `site_type`），
已验收的级别规则 #227/#228 判定不受影响。

**⚠️ 另一个已知缺口：`alarmName` 字段没进 value frame。**
规则 #161「IP_DWDM告警推单给WO」的条件用了 `alarmName = 'Fiber Break'`，
而 `build_value_frame` 不产出这个键 → `eval_one` 对缺失字段返回 `False` → 该规则**永不命中**。
实测 `Fiber/Link Break` 出现在 `title` / `description` / `specific_problem` /
`alarm_description` 四列里（各 9 行），但**无法确定**配置中心取的是哪一列，
所以先不猜（该规则是 STOP，影响面小）。

**长度**：加上派单依据段后，实测 300 张单输出 535 ~ 1688 字符
（zh 最长 1463 / en 最长 1688），由 `config.json` 的 `maxReplyChars`
（**2000**）兜底。

> ⚠️ `maxReplyChars` 超了是**从尾部截断**（`src/whatsapp.js` 的 `truncate`），
> 会先把最后的「时效」段整段砍掉 —— 而那正是用户要看的信息。
> 原来是 1500，加段后实测 79/300 的英文回复会超（最长 1688），故提到 2000。
> `scripts/test-tt-lang.py` 的 `[5b]` 段用「最坏情况」（10 条条件 + 停用档）
> 压了一条护栏断言，以后加字段撑长回复会先红。
> 另外 `_cond_brief()` 自己有**长度预算**（110 字符）——
> 规则 #154 有 10 条 `alarmCode = X` 条件，逐条列光一行就 250+ 字符。

**超期判定：两个信号互证，不要自己算。** 实测 60 张单子两个信号 **100% 一致**：

| 信号 | 超期 | 未超期 |
|---|---|---|
| `sla_status` | `Failed` | `Pass` |
| `sla_remain_time` | 负数（如 `-0d1h19m`） | 正数（如 `0d6h48m`） |

> ⚠️ **不要拿 `sla_deadline` 跟当前时间比来判断超期。**
> `Pass` 的单子截止时间可能早已过去 —— 告警清除后 SLA 时钟就停表了。
> 实测 TT202609110023 截止 `2026-09-11 15:13:53`（早已过期），
> 但 `sla_status` 仍是 `Pass`，因为告警在 08:25 就清除了。自己算必然误报。

**多值字段要压平。** `sub_alarm_ne_name` / `sub_alarm_ne_ip` 这类字段是
`BSC1(1);\nKileaken` 这种「分号 + 换行」的多值格式，直接塞进回复会把一行拆成好几行。
`_multi()` 负责折叠（最多两个，多的显示「等 N 个」/ `(N total)`），
`_one_line()` 兜住其余含换行的字段。

### 为什么工单查询会慢（以及已经怎么解决）

`eflow_tt` 表上**一个索引都没有**，任何单号查询都是全表扫描。实测（1.58GB / 34676 行，库在 Y 盘网络盘上）：

| 操作 | 耗时 |
|---|---|
| 全表扫描取一行 | **12 ~ 100 秒**（随网络盘波动） |
| 按 `rowid` 取整行 | **0.003 秒** |
| `rowid > ?` 范围扫描（676 行） | 2.9 秒 |
| `max(rowid)` | 0.02 秒 |

差了约 6000 倍。所以做了一层**本地单号索引**（`data/tt-index.json`，约 1.1MB / 4.7 万个单号）：

1. 构建一次：全表扫一遍，导出 `单号 → rowid`（首次约 10~30 秒）；
2. 之后查单号：本地映射查到 rowid → `WHERE rowid = ?` 精确取行，**3 毫秒**；
3. 索引超过 `TT_INDEX_TTL` 后：用 `rowid > 上次最大 rowid` 做**增量同步**（只读新增行），
   而不是重新扫全表。

也可以随时手动重建：

```bash
npm run tt-index     # 重建本地单号索引
```

> **索引过期但单号命中时，仍然直接用旧索引返回。** 数据晚几分钟，远好过让用户等一次全表扫描。
> 只有「索引新鲜但查不到」才会直接答「没找到」——所以刚同步进来的新单号，
> 最多有 `TT_INDEX_TTL`（默认 10 分钟）的不可见窗口。急着查新单就先跑一次 `npm run tt-index`。

### ⚠️ rowid 不稳定：索引必须自带失效检测（踩过的坑）

**这是本项目最危险的一个 bug，比「查不到」严重得多。**

`rowid` 只在**同一次写入布局**下稳定。工单库会被整体重写（某次同步后 rowid 全部重新分配），
此时：

- `max(rowid)` 看起来仍在正常增长（实测 34676 → 34702），
- 增量同步只追加 `rowid > max` 的行，

所以**增量机制完全察觉不到**，而索引已经 100% 错位。实测抽样对比：

| | 抽样 200 个单号 | 结果 |
|---|---|---|
| 事故索引 | 正确 0 / 指向错行 200 | **正确率 0.0%** |
| 重建后 | 正确 200 / 指向错行 0 | **正确率 100.0%** |

错位的后果不是报错，而是**静默返回别人的工单**——实测 `TT202609110023` 被解析成
`TT202603120041`（`9181.[Bologoidu]Complete site down`），字段齐全、不报任何错，
机器人会把这一单的级别和状态当成那一单发到群里。

**现在有两道防线：**

1. **锚点抽查（识别失效）** —— 索引里存 3 个「rowid → 该行应含哪个单号」的对照样本，
   每次读索引时花约 3 毫秒核对一遍。对不上就认定索引作废，**整表重建**
   （失效时做增量是没意义的，因为 rowid 已全部重排）。
2. **行级复核（识别错行）** —— 按 rowid 取回整行后，再确认这一行的
   `tt_no`/`ticket_no`/`wo_no` 里确实有目标单号；没有就丢掉索引走重建。
   宁可当「没命中」，也绝不报错单。

> `builtAt` 会被增量同步刷新，所以「索引新鲜」**不等于**「索引正确」——
> 库被整体重排后索引会一直显得新鲜。**只有锚点能识破这一点。**

### ⚠️ 子进程输出必须显式指定 UTF-8

Windows 上 Python 的 `stdout` 默认跟随系统代码页。机器人是 Node 从 Windows 启动的，
环境里**没有 `LANG`**，编码会退化成 cp1252（实测），脚本一 `print` 中文就抛：

```
UnicodeEncodeError: 'charmap' codec can't encode characters in position 28-30
```

表现为群里收到「分析 XX 时出错了：UnicodeEncodeError: ...」。

**为什么本地测不出来**：在 Git Bash 里手跑时 `LANG` 是存在的，Python 会开 UTF-8 模式
（`sys.flags.utf8_mode = 1`），输出完全正常。**只有机器人那条路径会踩到。**

现在两处双保险：

- `src/tt.js` 拉起子进程时显式传 `PYTHONUTF8=1` / `PYTHONIOENCODING=utf-8`；
- `scripts/tt-analyze.py` 开头对 `stdout`/`stderr` 做 `reconfigure`：
  被管道接走（机器人在用）时强制 UTF-8；人在控制台看时保留原编码，只保证不因个别字符崩掉。

### ⚠️ my_app 路径的自动定位（换机后 TT 分析 Errno 2 的治本项）

**症状**（2026-10-03 实际发生，把本项目拷到另一台机器后）：

```
Something went wrong while analyzing TT202610020060:
[Errno 2] No such file or directory:
'Y:/Task/my_app\\backend\\services\\eflow_rules\\eflow_TT_rules.xlsx'
```

报错里那个 **`/` 与 `\\` 混用**的路径就是这个 bug 的指纹 ——
它是「硬编码的正斜杠盘符」+「`os.path.join` 拼出来的反斜杠」凑成的。

**根因**：`tt-analyze.py` / `export-tt-knowledge.py` / `eflow-live-tt.py` 都把
my_app 路径**写死**成 `Y:/Task/my_app`。`Y:` 是 `192.168.100.19` 那台的 E 盘
网络映射（`\\192.168.100.19\e`）。换到别的机器后：
* 若没挂 `Y:` → 直接失败；
* **更糟的情况**：像本机 .20 这样 `Y:` 挂着、但 `Y:\Task\my_app` 不存在
  （那台的 my_app 在 D 盘）—— 失败得更隐蔽，因为盘符看起来是"在的"。

**修复**：路径解析统一收进 `scripts/my_app_paths.py`，按优先级定位：

1. 环境变量 `MY_APP_DIR`（显式指定，运维可覆盖）；
2. **从本仓库自身位置推导** —— `../../my_app`，与本项目并列。**与盘符无关**，
   拷到任何机器都成立（前提是两项目按仓库布局并排放）；
3. 候选盘符回退：`Y:` → `D:\01_RPA\Task\my_app` → `C:\01_RPA\Task\my_app`。

命中后会**校验规则表文件确实存在**（不只看目录在不在）—— 目录在但缺文件
照样会让下游抛那个含糊的 `Errno 2`，那正是要消灭的故障形态。全都不可用时，
抛的是一个说清「怎么办」的错误（含已尝试的路径清单），而不是把底层 `Errno 2`
原样丢进群里。

> **换机部署清单**：拷完项目后直接跑一次 `npm run tt -- <任一TT单号>` 验证。
> 正常应输出分析结果；若报「找不到 my_app 目录」，按提示设 `MY_APP_DIR` 即可。
> 顺带说明：`Y:` 在 .19 那台是**正常**的（my_app 确实在它的 E 盘），
> 所以本改动对那台机器是**行为不变**的 —— 它仍会命中候选 1 或 3。

### ⚠️ 工单库在网络盘上，必须用 `immutable=1` 打开

这不是性能优化，是**正确性修复**。SQLite 的 WAL 模式依赖共享内存（`-shm` 文件），
在网络文件系统上不可靠。实测用 `mode=ro` 打开会触发 Windows `page error`：

```
Windows fatal exception: page error
```

**整个 Python 进程被直接干掉，连 traceback 都留不下**——这正是群里那句
「分析 XX 时出错了：Traceback (most recent call last):」的来源（那行 traceback 是
子进程残留的 stdout，真正的异常信息根本来不及输出）。

改成 `immutable=1`（告诉 SQLite「文件不会被修改」，跳过全部 WAL 与加锁处理）后实测稳定。
代价：若 my_app 正在写入，可能读到稍旧的快照，对本用途可接受。

### 查不到单号时：先回 eFlow 实时查

工单库同步有延迟，用户报的单号常常比库里最新的还新。**这种情况下不能只说一句
「库里没有」就完事** —— my_app 本身就有实时按单号查 eFlow 的能力
（`eflow_data_mapper.fetch_tt_live`，见 my_app 的
`.trae/documents/eflow-tt-real-time-fallback.md`），只是机器人这条通道以前没接上。

现在的行为：本地 miss → **先垫一句**再实时查 → 拿到就把完整分析回给用户。

```
本地工单库还没有 TT202609290052（同步有延迟），我去 eFlow 实时查一下，请稍等…
```

垫话是必须的：实时查询要登录 eFlow（OAuth2 + RSA）再分页扫描（每页 2000 行 / ~4s / 3MB），
比本地查询慢一个数量级。不垫这句，用户看到的就是十几秒静默，只会以为机器人掉线了。

实时命中的报告**会标出来源**，让用户知道这不是本地快照：

```
⚡ 本地库暂无此单，已实时查 eFlow
TT202609290052 · Bokessa(3283)｜Lofa｜站点类型 NORMAL
...
```

三种收尾，都不会让用户误判：

| 情形 | 回复 |
|---|---|
| 实时命中 | 完整报告 + `⚡ 已实时查 eFlow` 标记 |
| 本地 + 实时都没有 | 「本地库和 eFlow 实时都没查到 X，请核对单号」+ 库内最新单号 |
| 实时通道不可用/出错 | 说明「实时没查成」+ **保留**原来那句「库里没有 + 库内最新单号」 |

> ⚠️ **第 3 行是关键，也是最容易写错的地方。** 实时通道会因为「my_app 的解释器
> 装不齐 pandas/sqlalchemy」「eFlow 登录失败」等原因不可用。这时如果直接把
> 「库里没有找到」当成最终答案，用户会以为**实时也确认过了**，从而得出「这单不存在」
> 的错误结论。所以必须显式区分「查过了没有」和「没查成」。

实现拆成两段，各管一件事：

- `scripts/eflow-live-tt.py` —— **桥接**。用 my_app 自己的 `fetch_tt_live` 取数，
  只往 stdout 吐 JSON。它**自己探测**一个能 import `pandas` + `sqlalchemy` 的解释器
  （my_app 的内嵌 venv 在部分机器上是坏的，不能假定某个固定路径可用），
  探测不到就以退出码 2 表示「永久不可用」，绝不重试、也绝不影响本地查询。
- `scripts/tt-analyze.py --live-row -` —— **渲染**。实时行从 stdin 喂进来，
  与本地行**共用同一套**规则匹配和渲染代码，避免两种格式并存。

> 凭据只读 my_app 那一份（`backend/services/eflow_config.json` + `EFLOW_*` 环境变量），
> 机器人侧不另存密码 —— 免得以后改密码漏改一处。

`eflow-live-tt.py` 的退出码（与 `tt-analyze.py` 同一套语义）：

| 码 | 含义 | 上游怎么处理 |
|---|---|---|
| `0` | 实时命中，stdout 是单行 JSON | 交给 `tt-analyze.py --live-row` 渲染 |
| `1` | 实时也查无此单 | 回「本地和实时都没有」，**不重试** |
| `2` | 实时通道不可用（缺解释器/依赖） | 降级回原来那句「库里没有」，**不重试** |
| `3` | 实时查询真出错（登录失败/网络异常） | 告知「实时没查成」，属暂时性 |

> ⚠️ **`1` 和「取数进程崩溃」必须分清。** 早期实现让取数子进程用 `sys.exit(1)`
> 表示「没查到」，但 Python 遇到未捕获异常（比如 `ImportError`）**也是退出码 1**。
> 两者撞车后，my_app 依赖装坏时机器人会对客户说「本地和实时都没有这一单」——
> 明明一次都没查成。现在「没查到」改用 stdout 哨兵表达，非零退出码**一律**当出错。
> 回归测试见 `scripts/test-tt-live-bridge.py`。

实时兜底可以关（`config.json` 的 `ttLiveFallback: false`，或环境变量
`TT_LIVE_FALLBACK=0`），关掉后行为与改造前完全一致。

排障：`node scripts/run-py.mjs eflow-live-tt.py --which` 会打印探测到的解释器，
或告诉你实时兜底为什么不可用。

#### ⚠️ 实时行的字段比本地行少得多（级别判定会明确说「没核对成」）

eFlow 的 `base/list` 只返回 **24 个紧凑字段**（见 my_app `_TT_LIVE_COL_MAP`），
而 `eflow_tt` 有 67 列、级别规则要用其中的 `vip_site` / `down_site_count` /
`domain` / `site_information` —— **这些实时行里根本没有**。

后果一度很严重：`build_value_frame` 总是输出全部键，缺的字段变成空串，
而 `eval_one` 对空串返回 `False`，与「字段有值但不匹配」**无法区分**。
于是 15 条级别规则里有 **11 条静默失配**，报告一律显示「规则未命中，需人工确认」。
实测同一单号 `TT202609290052`：本地判「与规则一致，正常」，实时判「需人工确认」。
**同一张单，两种口径** —— 而「规则未命中」读起来像是已经核实过了。

现在把「判不了」和「没命中」分开：

| 情形 | verdict | 输出 |
|---|---|---|
| 字段齐全、规则不匹配 | `unknown` | `级别：P4（规则未命中，需人工确认）` |
| 字段缺失、规则没被真正评估 | `incomplete` | `级别：P4（实时数据不含级别判定所需字段，未能核对规则）`<br>`缺失字段：downSiteCount、vipSite、netWorkType、siteSubType` |

`--json` 调用方可以读 `verdict` 与 `missing_rule_fields`。

> 实时报告**仍然有用**：站点、告警码、状态、时间线、派单依据都是真的。
> 只有「级别判定」这一段在实时通道下不可靠 —— 现在它会如实承认，
> 而不是给一个看不出来的错结论。要准确判定级别，等本地库同步后再查一次。
>
> 回归测试见 `scripts/test-tt-live.py` 的 `[7]`/`[8]`：`[7]` 用**真实** eFlow 字段集
> 复现该场景，`[8]` 反向确认字段齐全时判定不受影响（防止修复矫枉过正）。

### 查不到单号时（本地库视角）

工单库里没有、且实时通道也没查到时，顺带告知**库内最新单号**，
让用户自己判断是等一等还是核对单号：

```
工单库里没有找到单号 TT202609150077。
库内最新单号是 TT202609150073。若你发的单号比它新，多半是数据还没同步过来
（工单库同步有延迟），稍后再试；若比它旧很多，请核对一下单号有没有写错。
```

实现上，「查无此单」用退出码 `1` 表示、stdout 里是给用户看的话；真正的故障用退出码 `2`/`3`、
stderr 里是原因。`src/tt.js` 优先采信 stdout —— 否则「没找到」会被误报成
`Command failed: C:/Users/.../python.exe ...` 这种带内部路径的噪音。

这段文案按提问语言渲染（见「回复语言」）：

```
Ticket TT202609150077 not found in the ticket database.
The newest ticket in the database is TT202609150073. If yours is newer it is most
likely not synced yet (sync has a delay) — retry later. If it is much older,
please double-check the number.
```

### 一次可以问多个单

用户经常一次贴好几个单号：

```
@机器人 check these TTs TT202609140078, TT202609140077
```

机器人会**逐个分析**，用分隔线隔开，每个单前面标出单号：

```
【TT202609140078】
TT202609140078 · Bokessa(3283) | Lofa | ...
────────
【TT202609140077】
TT202609140077 · Green Forest Comm(4588) | Montserrado | ...
```

> ⚠️ **旧实现只取第一个单号，后面的一个字都不提** —— 用户无从知道被漏了，
> 只会以为其余单子也查过了。这比报错更危险。

**上限 3 个单**（`MAX_TICKETS_PER_QUESTION`）。超过时明确告知，把选择权交回用户：

```
（你一次提了 4 个单，这里只分析了前 3 个。其余请分开问，或再 @我 一次。）
```

上限定在 3 是因为单个分析就要回上千字，再堆会让聊天窗口没法读。
**超限必须显式告知** —— 静默截断等于变回旧行为。

### 失败会自动重试一次

工单查询失败多是**暂时性**的（Y 盘网络盘首次建索引实测 11s~100s 波动、瞬时不可达），
再跑一次通常就好。日志里能看到用户为同一单**连问 5 次**（`TT202609110023`，
前 3 次都失败）—— 让用户手动重试等于把基础设施抖动转嫁成人工成本。

现在失败时自动重试一次，重试前先发一条垫话：

```
分析 TT202609220113 没成功，正在自动重试一次…
```

**只有「值得重试」的失败才重试**（超时 / 真异常 / 空结果 / 库读不到）；
**「查无此单」不重试** —— 那是数据还没同步，重试没有意义，直接返回
带最新单号的提示文案。

| 失败类型 | 会重试吗 | 理由 |
|---|---|---|
| 超时（timeout） | ✅ | 几乎总是首次建索引慢 |
| 真异常（exit 2/3） | ✅ | 多为库忙 / 网络盘瞬时不可达 |
| 返回空结果 | ✅ | 瞬时读失败 |
| 查无此单（exit 1） | ❌ | 数据未同步，重试无用 —— **改走 eFlow 实时兜底**（见上文） |

> 「查无此单」不重试、但**会去实时查**：重试只是把同一个本地快照再读一遍，
> 而实时查能真正拿到本地还没有的数据。两者是互补的，不是二选一。

## 回复语言（中英双语）

**回复语言跟着提问语言走。** 群里中英文混用（导入的 iMind 官方手册本身就是英文，现场同事
也常用英文），英文提问收到中文回复会很难用。

```
@bot please analyze TT202609110023        → 英文回复
@bot 分析下TT202609110023                  → 中文回复
```

### 判定规则故意做得很朴素

`src/lang.js` 只有一行判定：**出现汉字就算中文，否则算英文。**

- 这个语料只有中英两种，上语言检测库（或让模型判）都是过度设计；
- 判定是**同步、零成本**的，不额外占一次模型调用。

> ⚠️ **「英文提问还是收到中文回复」先查进程，别先查代码。**
> 这套适配是「改文件 + 重启」才生效的，而跑旧代码时**一点报错都没有**。
> 实测踩过两次。群里 @ 机器人发 `ping`，看它有没有报
> 「⚠️ 磁盘上的代码比本进程新」—— 见「常见问题 → 改了源码没生效」。

两个刻意的取舍：

| 情形 | 判定 | 为什么 |
|---|---|---|
| `analyze TT202609110023？`（英文句子 + 中文输入法的全角问号） | **en** | 只把**汉字**当中文信号，**不把全角标点算进去** —— 否则有人用中文输入法打英文句子就会被误判 |
| `@bot`（只有 @，没写内容） | **zh**（回退默认） | 没有语言信号。若不特判，空串会因为「不含汉字」被判成英文，`@bot` 就会莫名收到英文回复 |

### 三条路径，三种机制

这是本节最需要注意的地方 —— **不能只改 systemPrompt**：

| 路径 | 机制 | 怎么适配 |
|---|---|---|
| TT 单通道 | 脚本渲染的**模板**，没有模型参与 | 显式把语言传给脚本（`--lang zh\|en`） |
| 知识库通道 | **LLM 生成** | ① `systemPrompt` 里写明「用与提问相同的语言回答」；② 在消息序列**末尾**再追加一句语言要求（`LANG_HINT`） |
| **固定文案** | 不经模型，直接发出 | `config.json` 的 `*Text` / `*TextEn` 成对配置，用 `pickText()` 取 |

第 ① 条为什么不够、要加第 ② 条：`systemPrompt` 本身是**中文写的**，模型容易被它带偏成中文输出。
把「本次请用英文」放到消息序列**最后**（离生成最近）最不容易被忽略。这是两道保险，不是重复。

第 ③ 条最容易被漏。以下几句都**不经过模型**，改 prompt 完全管不到：

- 知识库未命中 → `notFoundText` / `notFoundTextEn`
- 程序故障兜底 → `errorText` / `errorTextEn`
- 排队已满 → `busyText` / `busyTextEn`
- 「只 @ 了机器人没提问」→ `whatsapp.js` 里的内联中英对
- TT 子进程超时 / 出错 / 空结果 → `src/tt.js` 的 `FAIL_TEXT`
- TT 脚本级失败（缺 openpyxl / 缺工单库）→ 脚本内按 `--lang` 取

漏翻的表现是「**偶尔冒一句中文**」，很难归因，所以 `npm run test:lang` 专门锁这类问题。

### 失败文案只包一层前缀

脚本级失败（退出码 2/3）走 stderr，由 `tt.js` 按语言包一层「分析 X 时出错了：」。
所以**脚本这边只输出原因**，不带自己的前缀 —— 两边都加会变成套娃：

```
✗ 分析 TT202609110023 时出错了：读取规则表失败：缺少 openpyxl…
✓ 分析 TT202609110023 时出错了：缺少 openpyxl，无法读取规则表（…）
```

### 数据里的中文不算「没翻译」

规则名、判定依据这些字段来自规则表，**照实呈现不做臆造翻译**：

```
Matched rule: #229 无线断站级别重定义-P3-rule2
```

「派单依据」段同理 —— 规则名来自配置中心，是**标识符**而不是界面文案，
英文提问时也照原样保留（规则名本身就有中英混排，如 `#164 TT单直接派FO accept`、
`#119 TT_push_confirm_to_close`）：

```
[Assignment basis]
Create: #164 TT单直接派FO accept(autoDispatch·P3) → route to FO (no conditions — catch-all default)
Dispatch: #204 小区故障派ZTE WO(FOAccept·P2) → ZTE_NOC_FO
Matched: alarmCode=9991 in 9971/9981 (7 total)
```

所以英文输出的验收标准不是「一个汉字都没有」，而是「**除了数据行，界面文案里没有汉字**」——
`test-tt-lang.py` 就是按这个口径写的（剔除数据行后零中文残留；
`[5b]` 段另有一组用 ASCII 规则名做的「零中文」断言，把文案和数据分开测）。

### 已知未适配

- **内置命令的回复**（`ping` / `help`）：命令词本身就是英文，没有语言信号可判，仍是中文。
  如果现场同事需要英文版 `help`，在这里说一声即可加。

### 把 docx 手册转成可检索的 markdown

`07_` 那份由 `scripts/docx-to-md.py` 从官方 docx 转换而来：

```bash
python scripts/docx-to-md.py 输入.docx 输出.md
```

纯标准库（不装 `python-docx`），三个刻意取舍：

1. **保留标题层级** —— 分块器按 Markdown 标题强制断块，标题一丢整节内容会粘成一块；
2. **整段丢弃目录**（`toc 1/2/3` 样式）—— 目录条目是正文标题的副本，
   不丢的话同一批文字在索引里出现两份，白白挤占 topK（实测丢了 146 段）；
3. **图片只留 `[图]` 占位** —— 检索是纯文本的，图片内容进不了向量，
   但留占位能提示「此处原本有图」，避免截图前后的说明被割裂。

**必须做 HTML 实体解码**：Word 把 `&` 存成 `&amp;`，不解码会得到
`Trouble Ticket&amp;&amp;Work Ticket` 这种标题，既难读又会让字面检索失配。

> 这份手册是**英文**的，而群里提问多为中文。实测跨语言检索有效
> （问「怎么创建一个用户组」能命中 `Creating A User Group` 章节，`lex=0`，纯靠语义匹配）。

### 索引去重（`dedupeChunks`）

建索引时同一段文本只保留一份，落库前按**删除所有空白后的全文**比对。

```
去重：移除 9 个重复块 → 822 块（省下 1.1% 检索名额）
```

为什么必须做：重复块的危害**不是占空间，而是吃掉 topK 名额**。
实测查 `Prerequisite for eFlow deployment` 时 topK=6 **全部命中同一段重复文本**
—— 6 个名额只带回 1 条信息，模型看到的"资料"严重退化。

两个实现上的坑：

1. **归一化要删空白、不能只压缩**。分块器会在断点处重新拼接，同一段原文可能落成
   `系统\n部署成功` 与 `系统部署成功` —— 压成单空格时两者仍然不相等
   （`系统 部署成功` ≠ `系统部署成功`），重复块会漏网。中文语料里空白不承载语义。
2. **只做精确匹配，不做模糊匹配**。宁可漏合并，不可误合并：
   把两段不同的级别规则当成一段，比留几份重复严重得多。
   实测「告警码 X → 父告警码 Y」这类高度同质的规则条目**一条都没被误合并**。

> ⚠️ **别用「前缀相同」判断重复**。`chunkOverlap=80` 的滑动窗口会让相邻块开头
> 相同而结尾不同 —— 那是**有意保留的上下文**，不是重复。
> 按前 120 字符比对会得出"73 块重复"的错误结论（真实值 9 块）；
> 按 120 字符前缀删会误删大量有用上下文。必须比全文。

回归测试：`node scripts/test-dedupe.mjs`（含用线上 `data/index.json` 实测的用例）。

## 运维与排障

### ⚠️ 连接反复断开、code=440：同号双开互踢（2026-10-03 事故）

**症状**：日志里 `! 连接断开（code=440），2s 后第 1 次重连…` 与 `✓ 已连接` 交替刷屏，
大约每 3~4 秒一轮，看起来「一直在重连、其实从没稳定过」。机器人**完全不回消息**，
而且重连次数始终显示「第 1 次」——因为每轮都真的连上过，退避被重置了。

**根因**：`src/index.js`（知识库机器人）与 `src/notify.js`（P1 告警推送）**共用
`data/auth/` 同一份凭据**。两个进程等于同一个 WhatsApp 号双端登录，服务端不断把
其中一方顶掉（`connectionReplaced` = 440），而两边的重连逻辑又互相把对方顶回来，
于是**无限互踢**——两个进程都收不到消息。

**定位方法**（本次就是这么找到的）：

```powershell
# 看有几个 node 进程在跑本目录的东西
Get-CimInstance Win32_Process -Filter "Name='node.exe'" |
  Where-Object { $_.CommandLine -match 'whatsapp-kb-bot' } |
  Select-Object ProcessId,CreationDate,CommandLine
```

本次实测：`index.js` 与 `notify.js` 同时在跑，时间戳完全吻合 —
bot 每次 `16:xx:40` 连上，notify 就 `16:xx:44` 断；notify `16:xx:48` 连上，
bot `16:xx:51` 断。**杀掉 notify.js 后，bot 数秒内即稳定，不再出现 440。**

**修复**（两层，都已落地）：

1. **进程层**：`notify.js` 改用独立凭据目录 `data/auth-notify/`（可用环境变量
   `NOTIFY_AUTH_DIR` 覆盖），两个进程各自持有一个独立的「已关联设备」，互不干扰。
   首次启用直接跑 `npm run notify` —— **它会自己打出二维码**让你扫。
2. **代码层**：两个入口都**不再对 440 重连**，而是打印排查指引后 `exit(2)`。
   440 继续重连既救不活自己、又会让对方也收不到消息，还会把「同号双开」这个真实
   故障伪装成「网络不稳」。退出才能让看门狗和值班人看到。

#### 首次登录：谁负责出二维码

**`npm run notify` 自己出二维码**，不需要先跑 `relogin`。

> ⚠️ 这里曾经有个死循环，2026-10-03 实测踩到：`relogin.mjs` 发现目录不存在时说
> 「直接运行 `npm run notify` 扫码即可」，而 `notify.js` 又说「请执行
> `npm run relogin:notify` 扫码登录」—— **两个脚本互相指向对方，用户卡在中间无路可走。**
>
> 根因是职责搞混了：`relogin` 的职责是**清掉旧凭据**（换号用），它**不产生**新凭据；
> 新凭据是 Baileys 连接时通过二维码生成的。所以「首次登录」只能由目标进程自己承担 ——
> 现在 `notify.js` 发现目录不存在就建一个空的，正常出码。

二维码是否打印**取决于有没有人看得见**（判据：`stderr` 是否 TTY），而不是取决于它是哪个进程：

| 运行方式 | 行为 |
|---|---|
| 前台 `npm run notify` | 打印二维码，扫码即登录 |
| 计划任务隐藏拉起（无 TTY） | 不打印（打出来只会污染日志），记录指引后退出 |

计划任务拉起时若发现未登录，日志会明确写「请在可见的终端里手动执行 `npm run notify`」。

> 顺带修正一处 API 误用：本仓库装的 baileys 6.7.24 里 440 的枚举名是
> **`DisconnectReason.connectionReplaced`**，**没有 `conflict` 这个成员**
> （写 `conflict` 会得到 `undefined`，判断永远不成立）。改动这块前先
> `node -e "import('baileys').then(m=>console.log(m.DisconnectReason))"` 核对一遍。

### ⚠️ 连接反复断开（code=408/428）：状态被清零 + 拿死 sock 发包（2026-10-06 事故）

**症状**：心跳显示 `connected: true`、进程也活着、端口正常，但机器人**就是不回消息**。
日志里只有一串「已连接」，既没有 `[提问]` 也没有报错，看起来一切正常。

**实测数据**（2026-10-06，bot 进程 2 小时内）：

```
15:48:58 → 15:50:50   112s      16:08:50 → 16:24:25   935s
15:50:50 → 15:53:30   160s      16:24:25 → 16:37:18   773s
15:56:06 → 15:56:42    36s      16:56:07 → 17:20:55  1488s
```

同期 `notify.js` 断了 26 次，码分布 **`408 timedOut` 23 次 + `428 connectionClosed` 3 次**。
两个进程同机同网同号，说明是**链路层**在掐长连接，不是某一方的代码写错。

**根因（两个独立缺陷叠加）**：

1. **业务状态是 `startWhatsApp` 的局部变量，重连即清零。**
   重连走的是 `setTimeout(() => startWhatsApp(...))` —— **递归调用整个函数**，
   于是 `selfIds` / `botMessageIds` / `lastReplyAt` / `chain` / `queued` 每次都重建：
   - `botMessageIds` 清空 → 用户「引用回复机器人」时认不出被引用的是自己，不响应；
   - `lastReplyAt` 清空 → 冷却失效；
   - `chain` / `queued` 归零 → 上一个 socket 里**还在跑**的提问与新一轮并发，串行保护形同虚设。

2. **发送用了闭包里的 `sock`，重连后它已经死了。**
   串行队列与垫话定时器是在**旧的** `startWhatsApp` 调用里创建的，闭包捕获旧 `sock`；
   旧 `sock` 已在 close 分支被 `sock.ws.close()` 杀掉，拿它发包抛 `Connection Closed`。

> 缺陷 2 与 `notify.js` 在 `9ccfed0f` 修的是**同一个 bug**（那里是轮询定时器拿着死 sock）。
> 当时只改了 notify.js，whatsapp.js 漏了 —— 这类「修了一处忘了另一处」正是下面
> 第 5、6 组单测存在的理由。

**修复**：

| 项 | 改动 |
|---|---|
| 状态跨重连保持 | `selfIds` / `botMessageIds` / `lastReplyAt` / `chain` / `queued` 提升为**模块级** |
| 不再拿死 sock | 新增 `liveSock()`，所有发送/`sendPresenceUpdate` 都经它取当前 socket |
| 保活可见 | 两个进程都**显式**写 `keepAliveIntervalMs: 30_000`、`connectTimeoutMs: 60_000` |
| 失败可见 | `send()` 失败不再被 `.catch(()=>{})` 吞掉，记一条 `[发送失败]` 并计数 |
| 断连窗口可见 | 重连成功时打印断开时长与期间发送失败条数 |

> `keepAliveIntervalMs` **只是显式写出来**，值等于 Baileys 默认值（30s）——
> 目的是让「多久探活一次」在代码里可见，不必再翻 `node_modules`。
> **不要调更短**：更频繁的 ping 不会更稳，反而更容易被服务端限流。

**排查这类问题的顺序**（心跳会骗人，别只看它）：

1. `data/bot_heartbeat.json` 的 `at` 是否在 30s 内 → 只能证明**进程活着**；
2. 看 `lastMessageAt` / `messagesHandled` → 这才是**消息进没进来**的证据；
3. 数日志里 `已连接` 的次数 → 次数多说明在**反复重连**，这才是病根；
4. `data/logs/bot-<日期>.log` 里搜 `[提问]` → 一条都没有 = 消息根本没进来；
5. `data/auth/sender-key-*.json` 的 mtime → 晚于进程启动 = 确实解密过消息（链路通）；
6. `git log` 看同类 bug 是否在另一个进程里修过而这里没修。

#### 以后怎么避免同类问题（2026-10-06 复盘）

**一、看门狗判不出来「连上了但收不到消息」。**

这是本次事故能持续这么久的结构性原因。`autostart.ps1` 的 `Test-Healthy`
只看两件事：心跳 `connected` 是否为 `true`、`at` 是否在 300s 内。
而**重连循环恰好满足这两个条件** —— 每次重连成功都会把 `connected` 写回 `true`，
心跳一直新鲜。所以看门狗认为「健康」，永远不会重启它。

```powershell
# autostart.ps1 的判据（简化）
if (-not $hb.connected) { return $false }   # 重连循环里这里恒为 true
return ($age -le $staleSeconds)             # 心跳也一直新鲜
```

**判断「真的在工作」而不是「看起来在连」的正据是：最近有没有成功处理过消息。**
心跳只能证伪「进程死了」，不能证明「消息能进来」。

**已于 2026-10-06 落地**：心跳新增 `lastMessageAt` 与 `messagesHandled`，
看门狗新增 `Test-Deaf`，在「连接正常但 ≥6 小时零消息」时**告警**（不重启）：

```jsonc
// data/bot_heartbeat.json
{
  "at": "2026-10-06T18:04:10.869Z",   // 传输层：心跳新鲜度
  "connected": true,                   // 传输层：连接状态
  "pid": 19388,
  "lastMessageAt": null,               // 业务层：最近一次**成功处理完**消息
  "messagesHandled": 0                 // 业务层：累计处理条数
}
```

`lastMessageAt` 记在**处理成功之后**（`whatsapp.js` 里 `[回复]` 日志之后），
不是收到消息就记 —— 收到但抛异常说明链路仍是坏的，不该让指标好看。

`null` 表示**从未处理过消息**，刻意不伪造成当前时间：看门狗必须能区分
「刚启动还没人说话」和「一直在正常工作」。这两种情况都不该告警。

手动查看：

```powershell
.\autostart.ps1 -Status
# lastMessageAt     : (never)  handled=0
# healthy           : True
```

命中时会打印（纯 ASCII，因为 PS 5.1 会把无 BOM 的 UTF-8 当 GBK 读）：

```
WARNING: whatsapp-kb-bot is connected but has not handled a message for 8h.
         Connection is up, so Test-Healthy says healthy - but messages may not be arriving.
         Check: count reconnect cycles (a reconnect loop keeps connected=true forever)
```

> **为什么只告警、不重启**：群里几小时没人说话是**完全正常**的（本机器人只在被
> @ 时才答），自动重启会造成无谓的中断；而且「连着但收不到消息」重启**治不好**。
> 这个检查的价值在于**让静默故障可见**，不是自动治愈。
> 阈值 6 小时可在 `Test-Deaf -DeafHours` 调整。

**二、重连路径必须当成一等公民来设计。**

本次两个缺陷都在重连路径上，而重连路径**平时跑不到** —— 只有断线时才触发，
于是它成了仓库里最少被验证的代码。写重连逻辑时守住三条：

1. **状态放哪，先问「断线后它该不该还在」。** 该在的（会话标识、冷却、队列、
   已发消息 id）一律模块级；只有「每次连接必须重算」的（如 `selfIds`）才在函数内。
2. **永远不要用闭包捕获的连接对象发包。** 通过 `liveSock()` / `sockRef` 这种
   **取值函数**拿当前连接。闭包捕获的 socket 活不过一次重连。
3. **重连不要递归调用「整个启动函数」。** 本次是
   `setTimeout(() => startWhatsApp(...))` —— 它等于把所有初始化副作用重放一遍。
   `notify.js` 靠模块级状态 + `if (!pollTimer)` 判重才没出事，属于**碰巧安全**。

**三、这类 bug 必须靠断言守住，不能靠人记得。**

真实 WhatsApp 连接无法在单测里复现，所以 `scripts/test-runtime.mjs` 的第 [5][6] 组
做的是**源码级断言**：状态变量不许退回函数内、发送不许直接用 `sock.`、
`liveSock()` 必须存在、notify 的判重逻辑不许改回。

> 这套断言的写法**从本次事故起成为本仓库的惯例**：某个缺陷无法用行为测试覆盖时，
> 就用源码级断言把它钉住，并在注释里写清「为什么不能只靠 review」。
> 断言**必须反向验证过** —— 临时把修复改回去，确认断言真的会失败。
> 本次已验证。

**四、同一个 bug 在两个进程里出现时，两边都要改。**

`notify.js` 在 `9ccfed0f` 修死 sock 时只改了 notify。这不是疏忽，
而是**缺少一个「还有谁在用同一模式」的检查动作**。本仓库有 `index.js` 与 `notify.js`
两个 Baileys 进程，`whatsapp.js` 与 `notify.js` 是同一模式的两次实现 ——
**改连接/重连/发送这三处时，默认要同时看另一个文件。**

**五、报障时先分清「进程活着」和「功能可用」。**

服务状态页显示的「heartbeat: connected」容易被读成「机器人正常」，
但它读的是 `notify_heartbeat.json`（推送进程），**根本不是问答机器人的心跳**。
两者的心跳文件是分开的：

| 文件 | 谁写的 | 说明什么 |
|---|---|---|
| `data/bot_heartbeat.json` | `index.js`（问答） | 问答进程存活 + 连接状态 |
| `data/notify_heartbeat.json` | `notify.js`（推送） | 推送进程存活 + 连接状态 |

> 状态页只看后者。看到「connected」时，先确认它说的是**哪一个进程**。

### 健壮性设计（都是踩过的坑）

- **分块长度不变量**：任何输入下每块 ≤ `chunkSize`。早期版本对**无句末标点的长文本**（长列表、代码块、无标点中文）会原样成块——实测 5000 字符变成一块，严重稀释检索精度。现在有硬切兜底，并加了回归测试。
- **重叠量的 `slice(-0)` 陷阱**：`String.slice(-0)` 等价于 `slice(0)`，返回**整个字符串**。当 `chunkOverlap=0` 时重叠量会变成 100%，内容成倍膨胀。已显式判断 `overlap > 0`。
- **重连退避**：`2s → 4s → 8s → 16s → 32s → 60s` 封顶。计数变量必须放在模块级——放在函数内会随每次重连重置，退避永远停在 2 秒，等于断网时每 2 秒狂试。
- **440 不重连，直接退出**（`connectionReplaced`）：440 是「同账号另一个会话把我顶掉了」，不是网络抖动。重连只会互相顶号，让两个进程都收不到消息，还把故障伪装成「一直在重连」。改成打印排查指引后 `exit(2)`。**注意枚举名是 `connectionReplaced`，6.7.24 里没有 `conflict`。**
- **两个 Baileys 进程绝不共用凭据目录**：`index.js` 用 `data/auth/`，`notify.js` 用 `data/auth-notify/`。共用即同号双开，必然 440 互踢（2026-10-03 事故）。
- **内存上限**：记录机器人消息 id 的集合做 FIFO 淘汰（上限 500），会话冷却表上限 1000。否则长期运行会持续增长。
- **队列保护**：串行处理下排队时间会累加（单次回答 1~10 秒）。队列超过 `maxQueue`（默认 3）时直接回 `busyText`，而不是让第 4 个人等几分钟。
- **顶层 `import` 会绑住整个模块**（`tt-analyze.py`）：openpyxl 只被 `load_rules()` 用到，但早期写在模块顶层。后果有两个，都很难排查 ——
  ① 纯渲染逻辑（`render_text` / 链路解析）根本不碰 Excel，却因为缺 openpyxl 连 `import` 都失败，于是**没法离线单测**；
  ② `test-tt-rules.py` 里那段「规则表不可达就 SKIP」的降级逻辑**永远走不到**（崩在 import 上，而它本意是优雅跳过）。
  改成 `_import_openpyxl()` 按需导入后才真正生效。附带一条：默认参数在**函数定义时**求值，所以 `DEFAULT_LANG` 这类被用作形参默认值的常量必须放在文件**顶部**，放后面会直接 `NameError`。
- **优雅退出**：`Ctrl+C` 会走 `stopWhatsApp`，正常结束 Baileys 会话再退出。直接杀进程可能让凭据写入中断，导致下次要重新扫码。

> Windows 提示：`Ctrl+C` 在控制台里能正常触发上述处理。但从其他进程发信号（如脚本里的 `child.kill('SIGINT')`）不会触发——Windows 没有真正的信号机制，这种情况会被直接终止。

### 常见问题

**@了机器人但完全没反应，日志里一片空白**

这是最隐蔽的故障。现在日志会主动诊断——去日志里找 `[未匹配]`：

```
[未匹配] 群 120363xxx@g.us 中有人 @了 12345678@lid
         机器人标识：8615638281623@s.whatsapp.net / 8615638281623
         若这条本该是 @机器人，说明提及 JID 形态没被识别。
```

如果 `@了` 后面的 JID 形态不在「机器人标识」列表里，就是识别失败。可能原因：

1. **LID 未下发**：WhatsApp 越来越多地使用 LID（`xxx@lid`）而非手机号。代码已改为**每条消息实时重算**自身标识，并在标识变化时打印 `↻ 机器人标识已更新`——所以正常情况下会自动适应。
2. **凭据里有 LID、但 `sock.user` 上没有**：这是 2026-09-15 换号后实测到的真实故障。换到新号码后 `sock.user.lid` 为空，而凭据 `creds.me.lid` 有值（`91019685171349:1@lid`），结果群里用 LID 形式 @机器人时完全识别不到。现已把 `state.creds.me` 一并纳入标识来源——**凭据比 socket 字段更可靠**。修复后启动日志里的「机器人标识」会列出 4 个形态（手机号 JID、纯号码、LID、LID 纯数字）。
3. 若长期不匹配，把 `[未匹配]` 那几行贴出来，需要针对该形态扩展匹配规则。

> 换号后建议先看一眼启动日志的「机器人标识」那一行：**如果里面没有 `@lid` 形态，
> 而群里 @ 用的又是 LID，就会静默失效**。正常应该能看到类似
> `231776990822@s.whatsapp.net / 231776990822 / 91019685171349@lid / 91019685171349`。

**扫码后一直连不上**
手机端检查「已关联的设备」是否出现新设备。若反复失败，删掉 `data/auth/` 重新扫码。

**连接一直断、一直重连，而且完全不回消息（code=440）**
同号双开互踢，几乎总是 `notify.js` 和 `index.js` 同时跑。见前面
「⚠️ 连接反复断开、code=440：同号双开互踢」一节。
先确认并只保留一个进程：

```powershell
Get-CimInstance Win32_Process -Filter "Name='node.exe'" |
  Where-Object { $_.CommandLine -match 'whatsapp-kb-bot' } |
  Select-Object ProcessId,CommandLine
```

修好之后 `notify.js` 用独立凭据 `data/auth-notify/`（需 `npm run relogin:notify` 扫一次码），
两个进程就不再有冲突。

**回复「知识库里没有找到依据」，但资料里明明有**
说明检索没命中。用 `node scripts/ask.mjs --debug "你的问题"` 看 `top1` 和 `gap`：
- `top1` 接近 `minAbs` 但没到 → 适当下调 `minAbs`
- `top1` 很高但 `gap` 不够 → 下调 `minGap`，或该问题与资料的表述差异过大，考虑补充语料

**回复内容像是编的**
检查 `systemPrompt` 是否被改动。默认提示词强制「只依据资料作答」。同时确认命中的块确实包含答案——用 `--debug` 看候选来源。

**云端模型报「返回空内容（finish_reason=stop）」**

现象是 key 有效、模型名正确、HTTP 200，但 `message.content` 是空串。这个报错本身不说明原因，**必须做对照实验**才能区分。跑：

```bash
npm run diag
```

它会用同一把 key 发 6 组变量受控的请求（模型名 / thinking 开关 / token 预算三个维度各隔离一次），最后自动给结论。常见成因：

| 现象 | 根因 | 处理 |
|---|---|---|
| 小预算失败、1024 成功 | `max_tokens` 太小，被思考过程吃光 | 保持 `maxTokens: 512`；启动自检已提到 256 |
| 只返回 `reasoning_content` | 模型把输出全放进思维链 | 保留 `"enableThinking": false`；若服务端不认这个参数就删掉该行 |
| 主模型全失败、对照模型正常 | key 没有该模型的访问权限 | 去控制台确认模型权限，或暂时换模型 |
| 带 `system` 消息才失败 | 消息格式不被接受 | 精简 `systemPrompt`，或改用 `/v1/messages` 端点 |

> 启动时的连通性探测**不再因失败而终止进程**。原因是探测用的 token 预算比真实问答小，
> 失败不代表问答一定失败；而且群里先用 `ping` / `help` 就能验证传输层，
> 把用户完全卡在启动阶段反而让人连排查入口都进不去。现在只在控制台给警告，然后继续启动。

**API Key 每次重启终端都要重设**

`AGNES_API_KEY` 如果只在当前 PowerShell 会话里 `$env:AGNES_API_KEY="..."`，关掉窗口就没了。
写进项目根目录的 `.env`（已被 `.gitignore` 排除，不会进版本库）：

```bash
# .env
AGNES_API_KEY=你的key
```

`npm start` 等命令都带 `--env-file-if-exists=.env`，会自动读取。

**被登出（日志提示 code=401）**
手机端把设备移除了。删掉 `data/auth/` 重新扫码。

**改完资料没生效**
没重跑 `npm run ingest`。

**改了源码没生效 —— 「改了没效果，但一点报错都没有」**

需要**重启进程**。改资料只需 `npm run ingest`，但改代码必须 Ctrl+C 后重新 `npm start`。

这是这个项目**最容易白排查半天**的坑：进程跑着旧代码时，日志正常、接口正常、
回复也正常，只是内容是旧的。实测踩过两次 —— 语言适配是 `09:19` 写进文件的，
而进程是**前一天 `21:19`** 起的，于是英文提问一直收到中文回复，日志里却看不出任何异常。

现在**不用登机器翻日志**：群里 @ 机器人发 `ping`，输出里直接给出判断。

```
pong ✅ 机器人在线
知识库：810 块 / 9 个文件
对话模型：[openai] agnes-3.0-flash
嵌入模型：bge-m3:latest（本地）
回复语言：中 / 英自动适配
已运行：13 小时 8 分钟（启动于 2026-09-15 21:19:57）
⚠️ 磁盘上的代码比本进程新 —— 现在跑的是旧代码，重启后新改动才生效
```

判断依据是**代码指纹**：取 `src/*.js` 与 `scripts/*.py` 的最大修改时间，
和进程启动时间比。磁盘更新 → 跑的是旧代码。启动横幅里也会打印一次：

```
✓ 回复语言：中 / 英自动适配（按提问语言判定）
  代码指纹：2026-09-16 11:31:58（本进程启动于 2026-09-16 11:33:28）
```

两个注意点：

- **每次调用都重新扫盘**，不是启动时冻结的值 —— 否则判断永远返回「最新」，形同虚设
  （`scripts/test-runtime.mjs` 的 `[4]` 段专门钉住这一点）。
- 指纹是**保守**的：改任何源文件（包括测试文件）都会让它变新，可能提示「需要重启」
  而实际不必。宁可贵一点，也不要漏报 —— 漏报的代价是继续白排查。
- 时间显示用的是**机器本地时间**（与日志里的 `Z` 时间同一基准）。

> **哪些改动其实不用重启。** `scripts/*.py` 是**每次查询现拉现跑**的
> （`src/tt.js` 里 `execFile(PYTHON, [SCRIPT, ...])`，一个请求一个子进程），
> 所以改 `tt-analyze.py` 这类脚本**立刻生效**，不用重启。需要重启的是
> **Node 侧**：`src/*.js`（模块只加载一次）和 `config.json`（`CONFIG` 启动时读进内存）。
> 于是指纹报警时先看改的是哪一边 —— 只改了 `.py` 的话可以直接忽略这条警告。
> （指纹本身分不清这一点，它是按「任何源文件」取最大 mtime 的。）

## 环境变量覆盖

`config.json` 里的字段都可以用环境变量临时覆盖（优先于文件），便于调试和容器化部署。见 `.env.example`。

注意：本机若设置了 `HTTP_PROXY`，它会劫持 localhost 请求。Node 的原生 `fetch` 默认不走代理，所以本方案不受影响；但用 `curl` 手工测试 Ollama 时需要加 `NO_PROXY='*'`。
