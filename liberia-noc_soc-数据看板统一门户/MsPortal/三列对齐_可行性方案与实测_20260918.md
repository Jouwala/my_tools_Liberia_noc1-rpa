## 一、结论（先看这段）

1. **三列对不齐的根因有两条，且都在 CSS 层，不在内容层。**
   ① 三列高度完全由内容决定，而内容量天生不等：中列被「地图画布写死 860px + 升级机制表 420px」顶到最高，
   右列被「BO View 折叠到 6 张」压到最矮；
   ② `index.html` 的三列容器写了 Tailwind 的 `items-start`，**三列各自收缩到内容高** ——
   谁矮谁就在列尾留下一整块空白（1920px 下右列留白 **424px**）。
2. **只调内容（藏卡片 / 挪区块）解决不了**：8 个区块按原顺序连续切分重新分列的**最优解就是现状**
   （极差仍是 424px）；任意装箱的理论最优也只能到 41px，代价是把升级机制表、BO View 挪到左列，
   把 FO View 挪到中列，彻底打乱 MS/FO/BO 的分组语义。
3. **CSS 层兜底才是"一次改对所有情况"的解**：把三列改成等高 + 列内区块均摊，
   实测 **8 组（1280 / 1440 / 1920 / 2560 四个宽度 + 1920px 下的深色 / 英文 / 字号 +20% / 筛选 myapp），
   极差全部 = 0，横向溢出全部 = 0**；纯 CSS 变体另在 4 宽度 × 4 状态 = 16 组上复测，同样全 0。
   内容方案做不到这点（换语言/调字号后极差就从 284 跳到 429）。
4. **唯一需要做的取舍**是中列"富余/亏空由谁吸收"，三种接法实测见第五节；**已采用 M3**
   （地图卡定高、升级机制表自适应）—— 对齐之后**地图一点没变小**（仍 860px），
   只是升级表的可见行数从 420px（≈12 行）变成 232px（≈7 行），其余靠滚动或已有的「放大查看」。
5. 右列仍比左列天然矮 235px，这部分由右列 3 张卡各均摊 ~78px 吸收（不是列尾空白，而是卡片底部留白）。
   想连这 78px 也消掉，可把 BO View 默认展示从 6 张提到 12 张 —— 但实测**只在 1920/2560 成立，
   1440 下会过头**，因此不建议写进全局默认（见第六节）。

## 二、现状量化（问题到底是什么）

headless Chrome 实测 `main > div.grid` 三个列容器的高度（默认折叠态，浅色/深色同值）：

| 视口 | 左列 MS+FLM+SP | 中列 拓扑+升级 | 右列 BO+FO+Admin | 高度极差 | 列尾空白（左/中/右） |
| --- | --- | --- | --- | --- | --- |
| 1280px | 1524 | 1699 ※ | 1386 | **313px** | 175 / 0 / 313 |
| 1440px | 1524 | 1670 | 1386 | **284px** | 146 / 0 / 284 |
| 1920px | 1422 | 1611 | 1187 | **424px** | 189 / 0 / 424 |
| 2560px | 1422 | 1574 | 1187 | **387px** | 152 / 0 / 387 |

> ※ 1280px 恰好是拓扑标题栏那组按钮（实时状态 + 4 个页签 + 刷新 + 新窗口）换不换行的临界宽度，
> 重复实测中列会在 1670~1699 之间波动（±29px）。不影响任何结论 —— 改后三列在该宽度恒为 1524。

同一页不同界面状态下还会变（1920px）：

| 状态 | 左 / 中 / 右 | 极差 |
| --- | --- | --- |
| 中文默认 | 1422 / 1611 / 1187 | 424 |
| 英文 | 1422 / 1650 / 1221 | 429 |
| 字号 +20% | 2012 / 2057 / 1747 | 310 |
| 筛选 `myapp` | 577 / 1611 / 577 | **1034** |

> 「极差随语言/字号/筛选变化」这一条很关键：**任何写死数字的内容再平衡都会在换语言、调字号、
> 搜索筛选、新增看板之后失效**，只有 CSS 兜底能一直成立。

### 2.1 每个区块的高度是怎么构成的（1920px）

| 列 | 区块 | 高度 | 构成 |
| --- | --- | --- | --- |
| 左 | MS View | 626 | 标题 40 + 8 张行卡（每张 61px，间距 6）|
| 左 | FLM View | 474 | 标题 40 + 默认 5/8 张行卡 + 「展开全部」行 40 |
| 左 | SP View | 291 | 标题 40 + 3 张行卡 |
| 中 | 拓扑地图 | 1012 | 标题 98 + **地图画布 860（CSS 写死）** |
| 中 | 升级机制 | 583 | 标题 81 + **表格滚动区 420（CSS 写死）** + 脚注 18 |
| 右 | BO View | 475 | 标题 40 + 默认 6/16 张（每张 63px，两列一行）+ 展开行 40 |
| 右 | FO View | 395 | 标题 40 + 8 张（每张 93px）|
| 右 | System Admin | 286 | 标题 40 + 6 张（每张 58px）|

列间距 16px。左列 626+474+291+32 = 1423≈1422；中列 1012+583+16 = 1611；右列 475+395+286+32 = 1188≈1187。

### 2.2 「对齐」的两种读法

- **列底对齐（本次主攻）**：三列下边缘在同一条水平线上 → 消除列尾空白。
- **跨列行对齐**：让 MS / 拓扑 / BO 三张卡同高、FLM / 升级 / FO 同高……
  这条路**按每排取该排最高卡推算**（未实施，只做了算术）：第 1 排会被 1012px 的拓扑卡顶住，
  于是左列 1012+583+291+32=1918、中列 1012+583+16=1611、右列 1012+583+291+32=1918，
  **极差反而 307px**；而且 BO/FO/SP/Admin 都要被灌到拓扑卡的高度，卡内空白比现在更大。**不采纳**（见第十节）。

## 四、推荐方案：CSS 兜底（三列等高 + 列内均摊 + 中列单独接）

### 4.1 要落地的 CSS（6 条规则，追加到 `MsPortal/assets/portal.css` 末尾）

```css
@media (min-width: 1280px) {
  main > div.grid { align-items: stretch; }
  main > div.grid > div { display: flex; flex-direction: column; }
  main > div.grid > div > section { flex: 1 1 auto; }
  #secTopo { flex: 0 0 auto; }
  #secEsc { display: flex; flex-direction: column; flex: 1 1 0; min-height: 300px; }
  #secEsc .esc-scroll { flex: 1 1 auto; min-height: 160px; max-height: none; }
}
```

同一份文本也存成 `TMP/align3_fix.css`，可直接 `Get-Content ... | Add-Content portal.css`。

**为什么是这几条**

| 规则 | 作用 |
| --- | --- |
| `main > div.grid { align-items: stretch }` | 压掉 `items-start`（Tailwind 工具类在 `@layer utilities` 里，无层级 CSS 无条件胜出，**不用改 index.html**）|
| `> div { display:flex; flex-direction:column }` | 三列变成纵向 flex 容器，列内区块才有"吸收富余"的能力 |
| `> section { flex: 1 1 auto }` | 列内所有区块共同承担富余/亏空 → 没有哪一张卡被拉出 235px 的大洞（对比方案 A：单卡最多 594px，本方案最多 78px）|
| `#secTopo { flex: 0 0 auto }` | 中列的地图卡**定高**，对齐时不参与伸缩 → 地图尺寸完全不变 |
| `#secEsc { flex: 1 1 0; min-height:300px }` | 中列的富余/亏空全部由升级机制表吸收（`flex-basis:0` 让它不参与决定行高，只填剩余空间）|
| `#secEsc .esc-scroll { flex:1 1 auto; max-height:none }` | 表格滚动区跟着卡片高度走（原 CSS 写死 `max-height:420px`），列高够就多显示几行 |
| `min-height: 300px / 160px` | 唯二的"魔法数"：防止筛选后左右列塌到 577px 时把升级表压没（实测筛选态表格停在 160px 下限）|

> 只在 `≥1280px`（`xl` 断点，也是三列真正成立、`col-span-4` 生效的断点）生效，
> **1024px 以下一行都不改**；底部「知识问答 + 友情链接」那一行、`#secExtra` 用户自建分组都不在选择器范围内。

## 六、内容旋钮的实测：BO / FLM 默认展示条数（不建议进全局默认）

在 M2 基础上再拧内容旋钮（几何等价模拟：点开折叠 + 隐藏多余卡片）：

| 变体 | 1440 行高 / 地图 / 真拉伸（左·中·右） | 1920 | 2560 |
| --- | --- | --- | --- |
| +BO 12 张 | 1614 / 984 / 90·124·0 | 1422 / 852 / **0·-9·7** | 1422 / 888 / 0·28·7 |
| +FLM 8 张 | 1725 / 915 / 0·55·339 | 1623 / 873 / 0·12·436 | 1623 / 909 / 0·49·436 |
| +FLM 8 + BO 16 | 1749 / 939 / 24·79·0 | 1623 / 873 / 0·12·**73** | 1623 / 909 / 0·49·73 |

读法：

- **BO 6→12 在 1920/2560 近乎完美**：右列自然高度 1415 ≈ 左列 1422，需要均摊的只剩 7px。
- **但 1440 下 BO 12 会过头**：右列涨到 1614 > 左列 1524，于是变成"左列均摊 90px + 地图被撑到 984px"，
  行高整体抬高 90px、页面变长。**一个常量无法同时满足三个宽度**（右列卡片高度对列宽比左列敏感得多）。
- FLM 5→8 会把行高抬到 1623（地图涨到 873~909，比 860 还大），代价是右列要多均摊 436px；
  且 FLM 只有 8 张，展开后折叠功能等于失效。

**结论**：内容旋钮只能"优化某一个宽度"，而且会动到用户之前明确要求的"默认只展示最常用的几个"，
所以**默认方案里一条都不加**；需要的话在预览页里现拧（见第七节）。

## 十、未采纳的方案（附理由，避免以后重复讨论）

| 方案 | 为什么不用 |
| --- | --- |
| 卡片间距均摊（`space-between`） | 极差确实 0，但右列卡间距被撑到 200+px，看起来像"卡片飞散了" |
| 跨列行对齐（同排卡片等高） | 每排高度被该排最高的卡（拓扑 1012px）顶住，极差反而 307px，卡内空白更大 |
| 砌体布局（CSS `columns` / JS masonry） | 会把区块按高度切到不同列，阅读顺序与分组语义全乱（门户是"按角色分组"的导航页）|
| 三列各自内部滚动 | 与"门户一屏看全"的定位冲突；且 3 条滚动条很难操作 |
| 每列固定高度 + 空白留在列内 | 只是把空白藏起来，滚动条还在，等于没解决 |
| 只调折叠条数（E） | 实测越调越差（藏卡让列更矮）|
| 重新分列（F′/F″，极差 41px） | 唯一代价是语义：升级机制表/BO 挪左列、FO 挪中列，与"MS 左 / 拓扑中 / BO 右"的分组约定冲突 |
| 写死地图高度（D，860→672） | 只解决中列，右列仍矮 236px；且地图变小不可逆 |
