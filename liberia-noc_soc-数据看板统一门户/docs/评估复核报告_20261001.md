## 0. 一句话结论

原评估**方向正确**（数据严谨、视觉专业、工程偏传统），但其**事实基准偏了**——
它描述的其实只是门户的**一个子集**（`olbrportal/` 原生 JS 版 + `MsPortal/`），
**完全没有覆盖真正在迭代的 React 主门户（`src/`）与模块化后端（`server/`）**。

结果导致它：

- **误报了三处"没有"**：无构建链、无类型系统、无模块化 —— 三者**均已存在**；
- **漏掉了三件大事**：React 主门户、模块化鉴权后端、以及**团队自查出的 6 项 P0 安全阻塞**；
- 把"安全/部署"列为"未评估、分数悬置"，而仓库里**已有实测证据表明这块是致命短板**。

**修正后总分：约 75–78**（原判 85 仅在"纯前端体验"口径下勉强成立）。

## 2. 原评估"漏掉的重大事实"

### 2.1 真实主门户是 React 19 应用，不是单文件原生 JS

```
src/
├── App.tsx                 (43KB，状态中枢)
├── auth/AuthContext.tsx
├── components/  (27 个 .tsx：Navbar, DashboardCard, UserManagementModal, WhatsAppTasksView …)
├── data/initialDashboards.ts  (1140 行，与渲染分离)
├── i18n.tsx                (117KB，zh 字典 20–553 行 / en 字典 554–1999 行，≈1091 个 key)
├── config.ts               (环境"单一真相源"：主机/URL 前缀)
└── types/dashboard.ts      (类型定义)
server/
└── auth/  (guard / index / password / routes / store / types + authDb.ts + authSwitch.ts，共 2183 行)
```

技术栈（`docs/AGENTS.md` 原话）：**React 19 + Vite 6 + Tailwind CSS v4 + lucide-react + TypeScript**；门户自身后端在 `server/`（Express/TS）。

### 2.2 工程实践比原评估以为的**成熟**（这些原评估都没提）

- **环境单一真相源**：`src/config.ts` 顶部注释写明"所有主机/域名只在此处定义"，优先级 `localStorage > VITE_* > 硬编码兜底`；
- **有机器守卫的整洁度**：`scripts/check-cleanliness.mjs` + `.git/hooks/pre-commit` 拦截探针/快照入库；
- **已知架构坑有正式文档**：`/uniplam` 前缀为什么必须（防 `405 Method Not Allowed`），写在 `config.ts` 注释里；
- **注释质量高**：`tsconfig.json` 甚至记录了"2026-09-25 实测：`TMP/probe_color_inventory.cjs:54 TS1005` 打挂 lint"这种具体排障记录。

### 2.3 安全不是"没验证"，而是**已查出致命问题**（关键）

仓库内 `MsPortal 商用就绪度检测 —— 结论与整改方案.md` 明确结论：
**「按现状不能商用交付」**，列 6 项 P0：

| 编号 | 问题 | 实测数据 |
|---|---|---|
| **B4（最严重）** | **7090 端口 = 匿名管理员出口** | 从 LAN 零凭据 `GET :7090/api/credentials` → **200 / 5,494 字节，凭据库直读**；`/api/auth/me` 回 `{"role":"admin"}` |
| B1 | 生产跑在 Vite **dev server** 上 | 响应含 `@vite/client` + `react-refresh`；登录/鉴权全在此 dev 中间件里 |
| B2 | **全站无 TLS** | `https://localhost/` 直接失败，仅 80 与 8081-8088 明文 |
| B3 | 匿名接口泄漏完整目录 | 零凭据 `GET /uniplam/api/portal-default` → 200 / 47,696 字节，含 **51 处内网 IP + 30 条带 token 的 URL** |
| B5 | **备份文件可公网下载** | `portal_bak_*.js`(135,804B)、`index_bak_*.html`(19,579B) 等直接可下 |
| B6 | `/api/tasks` **轮询风暴** | 10 分钟内 212 次请求（≈每 2.7s 一次），单响应 77KB → **单标签页 ≈100MB/小时** |

> 结论：原评估把安全"悬置为未评估"，等于**把最影响商用性的部分排除在分数之外**。若按它自己写的"若这些偏弱，总分应再降"的规则，**分数必须下修**。

## 4. "想上 90+" 的优先级（修正版）

原评估给的 TOP3 是「模块化+构建 / 最小测试 / a11y」——**其中第 1 项已经不成立（构建链和模块化都有）**。修正优先级：

| 优先级 | 事项 | 理由 |
|---|---|---|
| **P0（先做）** | **安全整改 B1–B6**：关 7090 匿名出口、上 TLS、删可下载备份、修轮询风暴 | 直接决定"能不能商用交付"，当前结论是**不能** |
| **P0** | **生产脱 dev server**：改为 nginx 直出 `dist/` 静态产物 | dev server 崩溃即全站掉登录 |
| P1 | **补最小测试**（数据口径单测 + 渲染快照） | 守住"数字绝不撒谎"这一核心价值 |
| P1 | **清理仓库**：归档/删除 123 个 `*.bak_*`；补齐 `.git` 与 pre-commit 守卫落地 | 快照入库是维护隐患 |
| P2 | **拆分 `App.tsx`(43KB) / `i18n.tsx`(117KB)** | 规模再大成本上升 |
| P2 | 主门户 a11y（aria/role/对比度系统校验） | 桌面门户专业短板 |

> 把安全与测试按团队自有证据纳入后，真实落地分数约 75–78，
