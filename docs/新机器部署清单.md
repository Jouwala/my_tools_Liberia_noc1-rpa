### 一点六、一次真实事故：`/Scripts/` 的大小写不敏感匹配

第 5 条不是理论风险，**本次调查中就真的发生了一次**，值得完整记下来。

**起因**：写 `clone_doctor.py` 时把它放在 `Task\my_app\scripts\`。改完后按惯例想确认新文件会不会入库，跑出来是：

```
$ git check-ignore -v -- Task/my_app/scripts/clone_doctor.py
Task/my_app/.gitignore:9:/Scripts/    Task/my_app/scripts/clone_doctor.py
```

**Windows 上 git 的路径匹配是大小写不敏感的** —— `.gitignore:9` 那条本意是忽略 venv 的 `/Scripts/`，却把新建的 `scripts/` 一并吞了。也就是说：**这两个救命脚本按原计划写下去，一个都进不了库，别人 clone 后根本拿不到。**

**紧接着的失误**：把脚本挪到 `tools/` 后，顺手 `Remove-Item scripts` 想清掉空目录 —— 但它**不是空目录**。`scripts\` 是那个 venv 的 launcher 目录（`pyvenv.cfg` 的 venv 根是 `my_app\`，所以 `Lib\` 在顶层、`scripts\` 放 `python.exe` / `pip.exe` / `activate.*`），同时**装着两个实时代理脚本与它们的会话文件**。这一删掉了：

| 丢失内容 | 能否重建 | 处置 |
| --- | --- | --- |
| `realtime_proxy.py`（940 行，FMS 8787） | 靠隔离区的 `.pyc` 反推 | **已恢复** |
| `realtime_proxy_vmax.py`（~400 行，VMAX 8790） | 同上 | **已恢复** |
| `start-app.mjs` | `.workbuddy` 技能目录留有同源副本 | 已复制回来（其 `PROXIES` 与 `realtime_proxy_ctl.py:26-29` 完全一致，可确认同源） |
| `pip.exe` / `pythonw.exe` / 各 `.exe` launcher | `Lib\site-packages` 67 个包**完好**，launcher 只是入口壳 | 已用 `pip --force-reinstall` 逐个重建 |
| `activate.bat` / `deactivate.bat` | venv 标准模板 | 已从 Python 安装目录模板重建 |
| `fms_session.json` / `vmax_session.json` | 运行时自动重写 | 下次登录自动生成，无需处理 |

**为什么能恢复**：这三个文件从未入库，唯一副本是 `_quarantine_20260925\...\C_pycache\Scripts\__pycache__\` 里的 `.pyc`。PyPI 上所有反编译器（`uncompyle6` / `decompyle3` / `pycdc`）**都还不支持 3.13 字节码**，只好用 `dis` 导出全部指令 + 常量，再逐函数重构。恢复后逐项与 `.pyc` 的 `co_consts` 对照：

- `PORT` = 8787 / 8790，`TARGET_HOST`、`SESSION_FILE`、30 余个日志文案、URL 路径**全部逐字一致**；
- `_load_cred` 走通的真实凭据库 `backend\services\credential_store.py:424`（该函数返回的账号与 `.pyc` 里的内置默认值完全吻合，反向印证恢复正确）；
- 新脚本在临时端口起的实例，`/health` 响应与线上**逐字节相同**；`/proxy` 的 400 / 403 / 404 分支与 `.pyc` 常量表一致。

**三条教训（比事故本身重要）：**

1. **改完文件先 `git check-ignore -v` 确认它进得了库**，别等 clone 才发现。`scripts\` 这个名字在本仓库是**陷阱**。
2. **删目录前先 `Get-ChildItem -Force -Recurse` 看清楚**。`Remove-Item` 对非空目录不报错，`-Force` 更是静默递归。本次若先列一眼，就没有后面这些事。
3. **`Scripts\` 不是废 venv，`scripts\` 里也不是只有 venv。** 它同时装着 FMS/VMAX 两个实时代理脚本。这个目录里既有可重建的（launcher）也有**不可重建的（代理脚本）**，而后者恰恰被 `.gitignore` 挡住了。

> **已落地（2026-10-03）**：三个脚本已迁到 **`tools\`**（不被忽略）并纳入版本控制 —— `realtime_proxy.py`、`realtime_proxy_vmax.py`、`start-app.mjs`。
> 配套改动：
> - `realtime_proxy_ctl.py` 把原来一个 `_SCRIPTS` 常量**拆成两个**，因为二者生命周期不同：
>   `_TOOLS = _ROOT/"tools"`（脚本源码，随 git）与 `_RUNTIME = _ROOT/"scripts"`（venv 解释器 + 进程 cwd，本机状态）；
> - `start-app.mjs` 同样拆 `TOOLS` / `RUNTIME`，并改为传绝对脚本路径、`cwd` 仍用 `RUNTIME`；
> - `.gitignore` 补 `/tools/*_session.json` —— 会话文件按 `dirname(__file__)` 跟着脚本落到 `tools\`，
>   旧的 `/Scripts/` 规则**不再覆盖它**，而它内含上游登录 Cookie（等同凭据），必须挡住。
>
> **验证**：以 `tools/` 的脚本 + `scripts/` 的 venv 冷启动，`/health` 立即 `ready` 且日志出现 `[login] ok`；
> 线上两个代理调 `ensure_proxy` 返回 `reuse`，**未重启、未扰动**。

### 一点七、同一次事故里的第二个坑：`python -m venv --upgrade` 会覆盖 `.gitignore`

恢复 launcher 时执行了一次 `python -m venv --upgrade D:\01_RPA\Task\my_app`（想重建 `activate.*`）。它除了重写 `pyvenv.cfg`，**还把 `Task\my_app\.gitignore` 覆盖成 venv 的 2 行样板**：

```
# Created by venv; see https://docs.python.org/3/library/venv.html
*
```

**这个 `*` 比它看起来严重得多**：它把 `my_app\` 下**所有未跟踪文件**静默忽略。已跟踪的 714 个文件不受影响（git 不对已跟踪文件应用 ignore），所以 `git status` 看起来一切正常 —— **但任何新写的源码都不会出现在 `??` 里，自然也永远不会被提交**。这个仓库的 `.gitignore` 注释里恰好记着同一个坑曾经发生过：

> 历史：本文件原先只有 venv 自动生成的两行（内容为 `*`），它把 my_app 下所有未跟踪文件都屏蔽了 —— 包括新写的 backend 模块。git status 因此看不到漏提交，**已连续三周**。

**两个后果：**

1. 该文件**在 HEAD 里是完好的 146 行版本**，工作区被改坏 → `git diff` 立刻可见 148 行变更。已用 `git checkout HEAD -- Task/my_app/.gitignore` 恢复，现与 HEAD **逐字节一致**。
2. 本次新建的 `tools\clone_doctor.py` / `tools\pg_migrate.ps1` 一度全被忽略；恢复 `.gitignore` 后**已验证可正常入库**。

**教训：`venv --upgrade` / `venv` 不能对已有项目目录随便跑。** 它按「这是我来管的目录」处理，会重写 `.gitignore` 与 `pyvenv.cfg`。只想补 launcher 时，改用逐包 `pip install --force-reinstall`（本次最终就是这么做的），或直接复制 `activate.*` 模板。

## 二、nginx 为什么不上传

### 2.1 已实测的依据

```
$ git check-ignore -v nginx-1.28.0
.gitignore:264:/nginx-1.28.0/    nginx-1.28.0
```

忽略规则在根 `.gitignore:246-264`，理由是三条：

1. **它是可重新下载的第三方发行包**（nginx.org 的 Windows 版，79MB，含 `nginx.exe` + 一堆 `.conf` / `.pl` / `docs`），不参与本项目任何构建。
2. **`.gitignore` 的 `*.exe` / `*.dll` 规则本就会逐个挡掉二进制**（根 `.gitignore:8-13`），整目录忽略只是把这件事一次做完。
3. **它是本机线上服务目录**，`AGENTS.md` 第四节 6b 条已写明「忽略跟踪 ≠ 可以删除」。

### 2.2 但配置不能靠「重新下载」

这是最容易出事的一点：**nginx 发行包可以重下，`conf\nginx.conf` 不能。** 那份配置里有 200 余行、精心维护的路由规则，全部是本项目积累下来的，包括：

| 配置位置 | 内容 | 丢了会怎样 |
| --- | --- | --- |
| `nginx.conf:434-438` | `location /v1/olbrportal/` 的 alias | **就是你问的那个页面，直接 404** |
| `nginx.conf:406-421` | `/MsPortal/`、`/olbrportal/` 静态壳 | 页面加载不到 `/MsPortal/assets/*`，界面错乱 |
| `nginx.conf:320-357` | `/api/` 兜底 + 按 Referer 分发门户请求 | 所有接口 502 或串到错误上游 |
| `nginx.conf:109-114` | 80→443 强制跳转（B2 安全整改） | 口令明文过网 |
| `nginx.conf:145-148` | `_bak_` / `.map` 等敏感文件 deny（B5） | 历史快照可被任意下载 |
| `nginx.conf:496-514` | `location ^~ /tiles/`（含 `^~` 的**必要理由**） | 地图全白 |
| `nginx.conf:223-242` | 门户 eFlow 反代 + `sub_filter` 注入 | 门户登录不可用 |
| `conf\portal_ports.conf` | 8081~8087 六个端口反代 | 门户各分站打不开 |
| `conf\portal_eflow_common.conf` | Cookie 域改写、去 secure、摘 HSTS | 门户登录后立刻掉线 |

> **注意：`conf\portal_ports.conf` 与 `conf\portal_eflow_common.conf` 同样是未跟踪的**（实测 `git ls-files` 对二者均无输出）。它们和 `nginx.conf` 一起构成「无任何入库副本」的配置集合。

**该怎么处理（已落地一种）：**

- ✅ **已做：把配置文本纳入版本控制。** 三份配置的副本已提交在 **`docs\nginx-reference\`**（`nginx.conf.txt` / `portal_ports.conf.txt` / `portal_eflow_common.conf.txt`，共约 48KB），每份头部都注明了生效路径与同步约定。**上传的是配置文本，不是 79MB 的二进制包** —— 不违反「不上传发行包」的原则。
- 备选：把这些配置贴进本文档附录（缺点是 diff 不友好）。
- 不推荐：让新机器自己重写一遍 nginx 配置（几乎必然漏掉上面表格里的某一项，且现象往往很隐蔽）。

> ⚠️ **副本是「参考」不是「生效」**：真正的生效文件仍是 `nginx-1.28.0\conf\` 下那三份。改完生效配置并 reload 成功后，**必须同步回 `docs\nginx-reference\`**，否则又变成新的分叉源。加上 `.19` 那份，实际是**三份**需要一致。

### 2.3 千万不要踩的两个坑

1. **`.19` 那台用的是另一份配置**（`\\192.168.100.19\e\01_RPA\nginx-1.28.0\conf\nginx.conf`）。本机 `.20` 改的是 `D:\01_RPA\nginx-1.28.0\conf\nginx.conf`。两份**必须同步维护**，`AGENTS.md` 第四节 6b 条记录过因两份分叉而出的事故。
2. **`-s reload` 必须先进到 nginx 自己的目录**，否则信号发给已死的 pid，**命令不报错、只在日志里留一行**：

   ```
   cd D:\01_RPA\nginx-1.28.0
   .\nginx.exe -t              # 改配置后先验证
   .\nginx.exe -s reload
   ```

## 三、最关键的一条：真实数据在 PostgreSQL，不在 `app.db`

这一条**推翻了**「把 `db\app.db` 拷过去就有数据」的直觉，必须单独说明。

### 3.1 实测证据

```
$ Invoke-RestMethod http://127.0.0.1:7038/api/health
{"status":"ok","db_mode":"pg","database":"postgresql","db_exists":true}
```

```
$ (backend\.env) MY_APP_DB_MODE=pg
$ (backend\.env) DATABASE_URL → host=192.168.100.20  port=5432  db=myapp
$ 服务 postgresql-x64-16 = Running，5432 在听
$ database myapp = 2183 MB，最大表 packet_loss_data 1,608,708 行
```

对应代码：`Task\my_app\backend\database.py:27` 读环境变量，`:37` 据此选连接串。

**结论：那 1.58GB 的 `db\app.db` 在当前 pg 模式下根本没有被读取。** 它仍然是 `MY_APP_DB_MODE=sqlite` 熔断回退（R7，`database.py:23-26`）的落点，也是历史真相源，**不可删除**，但拷它到新机器**不会**让页面出数据 —— 这是最容易浪费半天的地方。

### 3.2 数据不可由仓库重建

```
$ ls alembic\versions\  → 0001_baseline / 0002_task_queue / 0003_alarm_epoch_columns_bigint
                          / 0004_reflected_real_to_double / 5415704359dc_phase4_coverage
$ grep "bulk_insert|INSERT INTO" alembic\versions\  → 无匹配
$ grep "op.execute"              alembic\versions\  → 26 处，全部是 CREATE INDEX
$ git ls-files db/     → 0
$ git ls-files data/   → 0
```

**迁移只建表结构，零业务数据，且没有任何 seed/fixture。** 所以 PostgreSQL 库只能靠 `pg_dump` / `pg_restore` 迁移。

### 3.3 迁移命令（已封装成脚本）

**推荐直接用新增的 `Task\my_app\tools\pg_migrate.ps1`** —— 它把下面这些坑都处理好了：
自动读取 `backend\.env` 的连接串（口令不打印、不进命令行）、列出全部 11 个 schema、
检测建库权限、`--exit-on-error` 防静默失败。**实测 2183MB → 81.8MB / 19 秒。**

```
# 源机器：导出
cd Task\my_app
.\tools\pg_migrate.ps1 dump -Out D:\myapp.dump

# 新机器：导入（库不存在时需指定超级用户，因为业务账号没有建库权限）
.\tools\pg_migrate.ps1 restore -In D:\myapp.dump -SuperUser postgres

# 只想看会执行什么
.\tools\pg_migrate.ps1 dump -Out D:\myapp.dump -WhatIf
```

手工等价命令（脚本不可用时照这个来）：

```
# 源机器（.20）——注意**不要**加 -n public
"C:\Program Files\PostgreSQL\16\bin\pg_dump.exe" -h 192.168.100.20 -U <用户名> -F c -d myapp -f myapp.dump

# 新机器——建库需要超级用户，恢复数据用业务账号
psql -U postgres -c "create role <用户名> login password '<口令>'"
psql -U postgres -c "create database myapp owner <用户名>"     # owner 必须是业务账号
"C:\Program Files\PostgreSQL\16\bin\pg_restore.exe" -h 127.0.0.1 -U <用户名> -d myapp \
    --no-owner --no-privileges --exit-on-error myapp.dump
```

**三个必须知道的坑（都是 2026-10-03 实测）：**

1. **不要只备份 `public`。** 表根本不在 `public` —— `search_path` 是
   `app, eflow, lte_pl, battery, ms_sla, fw, ipran_ume, ran_ume, public`。
   按 `public` 备份会得到「成功但空」的 dump（`pg_dump -t 'public.*'` 直接报
   `no matching tables were found`）。
2. **业务账号没有建库权限。** 实测 `myapp` 的角色属性是 `rolcreatedb=f / rolsuper=f`，
   `createdb -U myapp` 报「创建数据库权限不够」。建库必须用超级用户，
   而**恢复数据仍用业务账号**（它对自己的库有权限 —— 已验证能建 schema、能写表）。
3. **新库的 owner 必须是业务账号**，否则恢复后应用连不上或无权建表。

> **不得把 `myapp.dump` 提交进仓库**（含生产业务数据，且 81.8MB 已接近 GitHub 100MB 单文件上限）。

## 四、第二个坑：启动脚本用的是**系统 Python**，不是仓库里的 `Scripts\`

> ✅ **2026-10-03 已修。** 本节记录问题与修复后的行为，便于理解为什么代码长那样。
> `start_hidden.ps1` 现在**逐个探测依赖**（`import fastapi, uvicorn`），
> 选中的仍是同一个解释器（本机行为不变），但**不再盲选**，且全部不可用时显式报错。

### 4.1 实测证据

修复**前** `Task\my_app\start_hidden.ps1:102-119` 的选择顺序是：
「① PATH 里的 `pythonw`/`python` → ② 4 个硬编码系统路径 → ③ 仓库内 `Scripts\pythonw.exe`」，
**只看文件存不存在，不看它有没有依赖**。

**仓库内的 `Scripts\` 是第三顺位，实际根本没用上。** 三重实测印证：

```
$ 7038 端口进程  →  pythonw  Id=72776  Path=C:\Users\...\Programs\Python\Python312\pythonw.exe
$ python.exe -c "import psycopg2"   →  OK（系统 Python312）
$ .\Scripts\python.exe -c "import psycopg2"  →  ModuleNotFoundError: No module named 'psycopg2'
```

**并且 `Scripts\` 不是「废 venv」，而是另一个用途的 venv**（这点容易误判）：

```
$ .\Scripts\python.exe -c "import fastapi"     →  ModuleNotFoundError
$ pyvenv.cfg  →  home = C:\Users\...\.workbuddy\binaries\python\versions\3.13.12
```

它由 `.workbuddy` 的 Python **3.13** 创建，`site-packages` 里是 numpy / opencv / pywin32，
且同目录放着 `realtime_proxy.py`、`fms_session.json` —— 它服务 **8787 端口的 FMS 实时代理**
（`Get-NetTCPConnection -LocalPort 8787` 的进程正是它），**不装后端依赖**。
所以「回落仓库 venv」这个思路在本项目里本就不成立。
**连 `psycopg2` 都只装在系统 Python 里** —— 这直接证明后端跑的不是仓库 venv。

### 4.2 后果与正确做法

新机器上，如果只 `cd Task\my_app` 然后往 `.venv\` 或 `Scripts\` 里 `pip install`，**装的地方是错的，后端依然起不来**。必须：

```
# 先确认哪一个是「会被选中的」解释器
python -c "import sys; print(sys.executable)"

# 依赖装进那一个
pip install -r requirements.txt
playwright install          # 浏览器二进制要另跑，requirements.txt 装不到
```

修复后，脚本在**找不到任何带依赖的解释器**时会这样报（不再是含糊的「45 秒内未监听」）：

```
[FAIL] No Python interpreter with backend dependencies (fastapi, uvicorn) was found.
       Install deps into ONE of the interpreters below, then re-run this script:
         - D:\01_RPA\Task\my_app\Scripts\python.exe  ->  ModuleNotFoundError: No module named 'fastapi'
       Correct command (pick the interpreter you want to use):
         <that python.exe> -m pip install -r requirements.txt
```

正常启动时它会明确告诉你选中了谁（这条日志是排查「装错地方」的第一手证据）：

```
[OK] Python selected: C:\Users\...\Programs\Python\Python312\pythonw.exe
     (skipped 4 interpreter(s) missing backend deps; see below)
```

> `requirements.txt`（39 行，含 `playwright>=1.40.0`、`psycopg2-binary==2.9.12`）与 `requirements.lock.txt` **均已跟踪**，可重建。
> Playwright 浏览器在 `%LOCALAPPDATA%\ms-playwright`（实测 ~1386MB），在仓库外，天然不入库。

## 六、容易被漏掉的两处「隐形大头」

### 6.1 `Task\my_app\data\`（1821MB）—— 被**根**规则忽略

它**不是**被 `my_app\.gitignore` 忽略的，而是被根 `.gitignore:119` 的 `data/` 挡住的。里面是页面直读的派生数据仓：

| 文件 | 体积 | 谁在读 |
| --- | --- | --- |
| `ran_kpi_avalability_1day.sqlite3` | 826MB | 可用率页 |
| `bp_report.sqlite3` | 196MB | `bp_report` 页（`main.py:196`） |
| `olib_soc_report.sqlite3` | — | `/api/olib-soc-dashboard/overview`，路径见 `services\olib_soc_report\olib_soc_kpi_store.py:37` |
| `progress.sqlite3` / `mttr_tt.sqlite3` / `avail_recon.sqlite3` | 22MB / 9MB / 0.9MB | 各自页面 |

**漏掉 `data\` 的典型症状：页面能正常打开、但上排卡片是空的。** 这种「半可用」状态比彻底打不开更难排查。

### 6.2 门户 `auth-data\` —— 缺了**能登录**，但老账号全丢

与直觉相反，`auth-data\` 不是阻断项：

- `server\authDb.ts:707` 会 `fs.mkdirSync(..., {recursive:true})` **自动建目录，不报错**；
- 全新目录 → `fresh=true` → `server\auth\store.ts:56-89` **自动播种 admin**，随机口令写入 `<auth-data>\initial-admin-password.txt`，且 `mustChangePassword: true`。

所以新机器**可以登录**（用户名 `admin`，口令去读那个 txt），但**所有历史账号与看板权限全部丢失**。

若要原样还原，必须**连 `-wal` / `-shm` 一起拷**（`authDb.ts:9` 用 WAL 模式，只拷主 `.db` 可能丢最近未 checkpoint 的写入）。

> **`auth-data\` 严禁入库**（含加盐密码哈希，门户 `.gitignore:14` 已明写）。若为省事把它提交，等于把生产口令哈希推到远端 —— 这是硬性约束，没有例外。
